title: How a conversation survives between runs
description: Why Spotlight keeps a task's whole workspace between runs and stations, why the workspace is always /workspace, and why the work survives losing a conversation.
---

A task's runs share a sandbox while it is up, and the sandbox is destroyed
once nothing has used it for a while
(see [Why a sandbox belongs to one
task](/docs/hosts/why-a-sandbox-belongs-to-one-task)). Yet an agent
that asked a person a question can pick up its conversation once the answer
arrives, with its reasoning, its edits and its half-finished plan intact, even
days later. By then it may be in a different container, and possibly on a
different machine. The mechanism behind that starts with where a harness keeps
a conversation.

## Where a harness keeps a conversation

A harness such as Claude Code or Codex keeps its conversations in files. To
resume one, the harness is started with the conversation's id and reads those
files back.

Everything else follows from how the harness finds them. Claude Code files a
conversation under a directory named after the working directory it was started
in. The same files under a different working directory are invisible to it:
told to resume, it answers that the session does not exist. A conversation is
therefore tied to a path, whatever machine the path is on. Move the working
directory and the harness's state together, to the same path on another machine,
and the conversation moves with them. Nothing else needs to go.

## Keep the workspace, and the conversation comes with it

Spotlight builds on that. It points each harness's state directory into the
workspace itself, under `.spotlight/state`, so a run's workspace contains both the
checkout the agent worked in and the harness's record of the conversation.

When an agent asks a person something, or needs a tool call approved, its run
is suspended: it gives up its place in the sandbox, and the sandbox stays with
the task. At the end of the turn, the runner packs the workspace into an
archive and stores it. The archive belongs to the task (or to a chat, for the
agent's planning chats). When the answer arrives, the same run carries on as
its next attempt, and the harness resumes the conversation it left. If the
task's sandbox is still up, the run goes back into it, and the workspace is
already there. If the sandbox has gone, any runner that meets the run's
placement restores the archive into a new sandbox before the harness starts.

The runner also stores the workspace at the end of every other turn, and when
a sandbox is drained after edits a person made in it. Every later run of the
task starts from the newest archive, unless it runs in the task's live
sandbox.

The archive contains the whole workspace, checkout included, and the two belong
together. A conversation refers to files: what the agent read, what it changed,
what it meant to run next. Restoring the conversation without the checkout it
was about would hand the agent a memory of work that is no longer there.

## One workspace for the task, one conversation for each station

A task keeps one workspace for as long as it lives. When a station passes the
task on, the next station's run restores the same archive. Its agent finds the
checkout as the last agent left it, with changes that were never committed and
any files written beside the checkout.

The conversation does not cross stations. Each station has its own prompt, and
may have its own harness and model, so the next station's agent opens a new
conversation and learns what was done from the notes on the task. A run resumes
a conversation only at the station that started it, while the task is still
there. The earlier station's conversation files stay in the workspace, under
`.spotlight/state`, and nothing resumes them.

The alternative is to give each station a fresh clone of the task's branch.
Then only what an agent pushed reaches the next station, and work it left
uncommitted is lost at every handover. Sharing the workspace has a cost of its
own: a station meant to judge the work independently, such as a review, sees
whatever the earlier agent left lying there.

A shared workspace could also hand a station things meant for another, so the
runner clears them at the start of every run: the skills an earlier station was
given, the files a harness profile laid, and an outcome file an earlier agent
left. It also brings the checkout's branch up to date with what was pushed to
it since, for example a fix a person committed on the pull request. If the
branch has moved both in the workspace and on GitHub, or uncommitted changes
block it, the runner leaves the workspace as it is and says so in the run's `prepare` step. [Inside a
sandbox](/docs/reference/hosts/sandbox#run-phases) lists each phase.

## Why the workspace is always /workspace

A conversation is filed under its working directory, so resuming needs the same
directory every time. In Spotlight that directory is `/workspace`, for every run
and check, wherever it runs. Each repository is checked out beneath it, at
`/workspace/<name>`.

Because the path is fixed, resume is safe on any host: the harness state lives
inside the task's own archive and lands at the same place wherever the archive
is unpacked. It also gives teams something stable to build on. An image built
from the runner image can bake a checkout, with its dependencies installed, at
the path the run will use, so the run only has to fetch and switch branches.
[Run a line in your own runner image](/docs/hosts/run-a-line-in-your-own-image)
covers that.

The checkout is just as portable, since a run's clone does not depend on the
host's git mirror once it is made (see [Fresh, not
cold](/docs/hosts/why-a-sandbox-belongs-to-one-task#fresh-not-cold)).

## Resume on any host

Put together, this means a conversation does not belong to a host. The host
that ran the first turn may be busy, stopped or gone by the time a person
answers. The run's next attempt, or a later run, can go to any host that is
able to take it, restores the workspace and carries on.

The alternative would be to send every follow-up run back to the machine that
started the conversation. That would make an answered question wait for one
particular machine, and it would lose the conversation whenever that machine
was replaced. Spotlight prefers the machine only while the task's sandbox is
still up on it, and past that relies on the archive, which avoids both.

## When a session is lost

Resume can fail. The archive may be gone or fail to restore, or the harness may
not recognise the session it is told to resume. When the harness says the session is
gone, the runner logs it and starts a new conversation instead of failing the
run.

That is safe because the conversation was never what carried the work. What
carries a task from run to run is the briefing, which includes the notes every
earlier agent left when it handed over. A new conversation starts with less
context than a resumed one, but it starts with what it needs. [Lines, stations
and tasks](/docs/getting-started/lines-stations-and-tasks) explains the notes. A
resumed conversation is an improvement on top of that, and Spotlight treats it
as one.

## Chats take back what was not read

Planning chats with the agent have a variant of the same problem. A person
sends messages, a run is started to answer them, and the run fails before the
agent has a session, for example because its setup failed. From the person's
side the messages were sent. From the agent's side they were never read.

Spotlight decides by the session. When a chat run ends without a
session, the chat takes back the messages that went to it, and
they go again with the person's next message. The rule is on the cautious side.
A run that fails after the agent read the messages but before it reported a
session sends them a second time. Spotlight accepts that, because a duplicate
beats a loss.

## What an archive keeps, and for how long

Spotlight retains a task's archive for as long as the task is unfinished. It expires some
days after the task finishes, and a chat's some days after the chat leaves its
conversation. Both go at once when their task or chat is deleted. A run that
finds no archive starts from a fresh checkout of the task's branch and a new
conversation, and the notes carry the work as above. An archive a task's run
started from is also retained for 30 days after that run started, and while the run is in a
replay set, so the run can be
[replayed](/docs/improvement/why-changes-are-replayed-on-past-tasks). How long each
kind of archive is retained, and how large one may be, is in [Limits and
timeouts](/docs/reference/limits-and-timeouts#workspace-archives).

An archive also leaves things out when something else can put them back. When a
repository has a setup command, the archive skips the files the repository
ignores, such as installed dependencies and build output, since the image and
the setup command lay them down again in the next sandbox. That keeps archives
small and restores quick, at the price of rebuilding those files in every new
sandbox. The setup command runs in every run in any case. Build output kept outside the
checkout, where restoring the checkout does not touch it, survives a restore;
[Run a line in your own runner image](/docs/hosts/run-a-line-in-your-own-image) covers building such an
image.
