A [search](/docs/reference/glossary#search) has an agent propose changed
configs for a work station, called candidates, and
[replays](/docs/reference/app/replays) each on the searched tasks of the
station's replay set. The best are then replayed on the set's
[held-out tasks](/docs/reference/glossary#held-out-task). Spotlight starts
searches itself, from the line's [`search`](/docs/reference/terraform/line)
policy, and when a search finishes, it picks a candidate and opens a pull
request in the line's Terraform repository, or says why it did not. See
[How Spotlight improves a station](/docs/improvement/how-spotlight-improves-a-station).
The same data is read through the [Searches API](/docs/reference/api/searches).
A search's candidates also show under
[Candidates](/docs/reference/app/insights#candidates) on the Insights Stations
tab, beside the team's other replayed candidates.

Only people on the team, the workspace's owners and admins, and workspace
tokens with the `read` scope can read a team's searches. Anyone else is
answered `404`, and the web app reads `Only team members can see its
searches`. Stopping a search also needs `plan`. See
[Team outcomes](/docs/reference/roles-and-permissions#team-outcomes).

## Improvement status [#improvement-status]

A work station's page opens with "What needs attention". At the right of that
title, one line says what Spotlight does to improve the station: an icon, a
short fact, and an ⓘ that shows the detail on hover. The same is read through
`GET /api/teams/<teamId>/lines/<lineId>/stations/<stationId>/improvement`. The
first status that applies decides:

| `status` | Fact | Links to | When |
| --- | --- | --- | --- |
| `searching` | "Searching" | The search's page. | A search of the station is in progress. |
| `picking` | "Choosing a config" while Spotlight [picks](#spotlights-pick) a candidate of the last search, then "Opening a pull request" once it picked one that has no pull request yet | The search's page. | The station's newest search finished and its pick, or the pull request for it, is not done yet. |
| `pull-request-open` | "Pull request open", or "Opening a pull request" while it is not on GitHub yet | The pull request on GitHub, once it is there. | A [config pull request](#config-pull-request-states) of the station is `opening`, `opened` or `closing`. |
| `off` | "Not searching" | Nothing. | The station's [search policy](/docs/reference/terraform/line#search-fields) is off. |
| `not-started` | "No runs yet" | Nothing. | The station has no replay set yet, or its set has no runs. |
| `not-improving` | "Not improving", with an amber warning icon | The replay set's page. | The station's newest config pull request `failed` after the last search started and after the station last improved; or Spotlight's last check [skipped](#skip-reasons) a search, after the station last improved, for `no-agent`, `no-scoring`, `ceiling-too-low`, `noisy`, `judge-unstable` or `flaky-checks`. |
| `improved` | "Improved" | The merged pull request on GitHub. | A config pull request of the station merged after its last search started. |
| `waiting` | "Waiting for next check" | The replay set's page. | Otherwise, as after a skip for `cooldown`, `pull-request-open`, `set-too-small`, `no-fresh-held-out`, `monthly-ceiling` or `no-headroom`. |

Hovering over the ⓘ shows:

| `status` | Text |
| --- | --- |
| `searching` | `Spotlight searches for a better config of the station.` |
| `picking` | `The last search finished. Spotlight picks its best config.`, or `Spotlight picked a config of the last search. It opens a pull request for it.` |
| `pull-request-open` | `Spotlight opened a config pull request. Please review it on GitHub.`, or `Spotlight opens a config pull request on GitHub.` while it is not on GitHub yet. |
| `off` | `The search policy of the station is off. Spotlight does not search the station.` |
| `not-started` | `Spotlight keeps a replay set from the runs of the station. The set has no runs yet.` |
| `not-improving` | `Spotlight could not open the config pull request of the station.` for a failed pull request; else `Spotlight did not start a search: ` and the [reason](#skip-reasons). |
| `improved` | `A merged config pull request improved the station.` |
| `waiting` | `Spotlight searches the station on a schedule and when a station alert fires.` |

Then these rows, each when known: "Reason", the message of a failed pull
request; "Improved", when the pull request merged; "Last search", when the
last search started; and "Next check", when Spotlight looks at the station
next, or "due" once that time has passed, left out while the policy is off.
Once the station has a replay set, "Replay set" and "Searches" link to the
set's page and to its [Searches card](#searches-card). "Replay set" is left
out when the fact already links to the set's page.

While the status cannot be read, the line reads "Status unavailable", with
"Try again".

improvement", after "Line": "On", with `Up to <ceiling> a search · every
<period>`, as in `Up to $10 a search · every 7 days`, or "Off", with `No

config of this station and opens a pull request for it.`, then:

| Row | Shows |
| --- | --- |
| Line ceiling a month | The line's `monthly_ceiling`. |
| After an alert | "Starts a search" or "Doesn't start a search", from `on_alert`. |
| Cooldown | The `cooldown`, in words, as in `3 days`. |
| Agent | The search agent's harness, model and effort, or "Spotlight picks". |
| Iterations | The station's `iterations`, or "Spotlight picks". |
| Repeats | The station's `repeats`, or "Spotlight picks". |
| Objective | "More success" or "The same success for less", or "Station health picks". |

See [`search`](/docs/reference/terraform/line#search-fields) on the line.

## Searches card [#searches-card]

The [replay set page](/docs/reference/app/replays#replay-set-page) has a
"Searches" card, under "Replays", at `#searches`. Its ⓘ reads `Spotlight
starts a search on a schedule and when a station alert fires. A search agent
proposes configs and replays each on the replay set of the station.` It lists
the station's searches, newest first, one row each:

| Column | Shows |
| --- | --- |
| Search | `Search <n>`, numbered from the station's first search, linked to its page. |
| State | Its [state](#search-states). Hovering over it shows its [stop reason](#stop-reasons), once it has one. |
| Best | Its [best candidate](#best-candidate)'s name, or "Live config", with its [overfit status](#overfit) when it has one, and a warning icon when it is [over the regression limit](#regressions-against-the-live-config). Without one, "No best candidate yet", or `No candidate matches the live config’s success yet` for a search that aims for the same success for less. |
| Success | The best candidate's score as a percentage, or `–`. Hovering over it shows `This score is from the held-out tasks.` or `This score is from the searched tasks.`, with `Likely range: <range>`. |
| Iterations | `<run> / <budget>`. |
| Spent | `<spent> / <ceiling>`. |
| Started | When it started. |

With no searches, the card reads "No searches yet" and `Spotlight searches the
station on a schedule and when a station alert fires.`, or, once Spotlight has
[skipped](#skip-reasons) a search of the station, `Spotlight did not start a
search: ` followed by the reason. To a person who may not read the team's
searches, it reads `Only team members can see its searches`.

## Automatic searches

Spotlight looks at each work station that has a replay set and a search
policy that is on, and starts a search when one is due:

| Trigger | `trigger` | Shown | When |
| --- | --- | --- | --- |
| Schedule | `schedule` | "On schedule", with `Spotlight started this search. The period of the search policy ran out.` on hover | The policy's `period` has passed since the station's last search started, or the station has had no search. |
| Alert | `alert` | "After a station alert", with `Spotlight started this search. A station alert fired.` on hover | One of the station's [alerts](/docs/reference/terraform/line) fired since its last search, and `on_alert` is `true`. The period need not have passed. |

A search is not started while another search of the station is in progress;
Spotlight looks again an hour later. Before a search starts, Spotlight
[refreshes the set](/docs/reference/app/replays#how-spotlight-keeps-the-set).
A search that starts takes:

| Part | Value |
| --- | --- |
| Iterations | The station's `iterations`, else 3. |
| Candidates per iteration | 2. |
| At once | 4 replay runs. |
| Repeats | The station's `repeats`, else 1. |
| Ceiling | The station's or the line's `ceiling`, in the line's `currency`. |
| Aim | The station's `objective`, else [chosen](#aims) from the set's health. |
| Agent | The station's `agent`, else the station's own harness, model and effort. |
| Held-out tasks | Drawn from the set's tasks that no earlier search of the station searched on. |

### Skip reasons

While the station's search policy is off, Spotlight starts no search, records
no reason, and looks again a day later. When a due search cannot start for
another reason, Spotlight records why and looks again later: a day later for
most reasons, an hour later for `pull-request-open`, at the end of the
cooldown for `cooldown`, and on the first day of the next month, in UTC, for
`monthly-ceiling`. The [improvement status](#improvement-status) and the
[Searches card](#searches-card) show the last reason, as `Spotlight did not
start a search: <reason>`, until a search starts. The first row that applies
decides:

| `reason` | Shown | When |
| --- | --- | --- |
| `no-scoring` | `the station has no judge and no check.` | The station has no `judge`, and no `check` with `diffs`. |
| `cooldown` | `the last search of the station started too recently.` | The `cooldown` has not passed since the last search started, or since a person last closed a config pull request of the station on GitHub. |
| `pull-request-open` | `a config pull request of the station is open.` | A [config pull request](#config-pull-request-states) of the station is `opening`, `opened` or `closing`. |
| `monthly-ceiling` | `the searches of the line spent the monthly ceiling of its search policy.` | What the line's searches started this month spent, plus one more `ceiling`, is over `monthly_ceiling`. |
| `set-too-small` | `the replay set has too few tasks. Minimum tasks: 5` | The set cannot give at least 2 held-out tasks and 3 searched tasks. |
| `noisy` | `success moves too much between repeats of the same runs.` | At the search's repeats, the set's [noise](/docs/reference/app/replays#noise) is more than the line's `min_gain`. |
| `judge-unstable` | `the judge does not give the same verdict twice.` | The set's newest [calibration](/docs/reference/app/replays#calibration) found the judge agreeing with itself less than 80% of the time. |
| `flaky-checks` | `the check flips on changes that it ran twice.` | The set's newest calibration found a flaky check. |
| `no-headroom` | `the live config does not do better on the set when it gets the answer.` | The newest [replay with the answer](/docs/reference/app/replays#replay-with-the-answer) found little [room to improve](/docs/reference/app/replays#room-to-improve). |
| `no-fresh-held-out` | `earlier searches searched on too many tasks of the set. A search needs new tasks to hold out.` | Fewer of the set's tasks than a search holds out are ones no earlier search of the station searched on. |
| `ceiling-too-low` | `the search ceiling is too low to replay each task once per candidate.` | The `ceiling` cannot give each replay run at least 0.01 of its currency. |
| `no-agent` | `no runner can start the harness of the search agent.` | The search agent's harness is not one a runner can start, its model or effort is not valid, or neither the station's `search` nor the station names a harness. |

`no-scoring`, `set-too-small`, `no-headroom`, `ceiling-too-low` and `no-agent`
also send the team a [notice](#notices).

## Search page

`/w/<slug>/team/<teamId>/lines/<lineId>/stations/<stationId>/searches/<searchId>`

To someone who may read the team's searches, an unknown search, or one of
another station, reads "Search not found" and `No search at this address. It
may belong to another station.`, with "Open the station", which opens the
station's page. When the search cannot be
loaded for another reason, the page reads `The search could not be loaded.`,
with "Try again".

The header shows `Search <n>`, or "Search" while its number is not known, and, for some [stop reasons](#stop-reasons), a pill,
such as "Stalled", whose hover gives the stop reason in words. Under it, joined by
` · `:

| Part | Shows | On hover |
| --- | --- | --- |
| "On schedule" or "After a station alert" | Always. | `Spotlight started this search. The period of the search policy ran out.` or `Spotlight started this search. A station alert fired.` See [Automatic searches](#automatic-searches). |
| "Replay set" | Always, linked to the set's page. | |
| When | How long ago the search ended, or started while it has not ended. | `Started <when>, ended <when>`, or `Started <when>`. |
| "Picked by Spotlight" or "No pull request" | Once Spotlight has [picked](#spotlights-pick) a candidate or declined to. | What Spotlight decided, in words. |

While the search is in progress, "Stop" opens `Stop this search?`: `The search
agent stops and no more candidates replay. Finished replays keep their scores.
Spotlight opens no pull request for a stopped search.`, with "Keep it searching" and
"Stop search", which reads "Stopping…" while it is sent. A stopped search gets
no [pick](#spotlights-pick) and no pull request.

Below the header are its tiles, a "Why it stalled" card per
[reflection](#reflections), the "Candidates" card and the "Success against
cost" card.

### Tiles

An ⓘ beside a tile's label shows its note on hover.

| Tile | Shows | Note |
| --- | --- | --- |

Without one, `–` and "No best candidate yet". Labelled "Cheapest" when the search aims for the same success for less, and then `No candidate matches the live config’s success yet` without one. | `The search aims for <aim>.` and the aim's note, `Spotlight ranks candidates by how often they succeed.` or `Spotlight ranks candidates by cost per run. Only candidates that match the live config's success, within noise, count.`, then `Likely range: <range>.` |
| Live config | The live config's search score as a percentage, and `of <n> runs scored`; or `–` and "Not scored yet". | `Likely range: <range>.` and `Minimum real gain: <min_gain>.`, as in `+5 pts`. |
| Iterations | `<n> of <m>`, the iterations run of its budget, and `<n> candidates proposed` ("candidate" for 1). | `Each iteration tries <n> candidates, <n> at once. Each run once. Search agent: <harness> · <model> · <effort>`, with `Each run <n> times` for more repeats, and only the parts its agent has. |
| Tasks | The searched tasks, and `searched · <n> held out`. | `The search agent sees only the searched tasks and their scores. It doesn't see the held-out tasks. After the search, the best candidates replay on the held-out tasks to check that they don't only fit what the agent saw.`, then `Held out: <titles>.` with each held-out task's title in the set, or `Task <first 8 characters of its id>`. |
| Spent | What it spent, and `of <ceiling>`. | |

### Why it stalled

One card per [reflection](#reflections), newest first, under the tiles,
headed `Why it stalled (iteration <n>)`. The page opened with
`#why-it-stalled-<n>` scrolls to it.

| Part | Shows |
| --- | --- |
| Whose failures | `Looked at why <name> failed`, or `Looked at why the live config failed`, once the reflection knows the config it looks into. |
| While it runs | `Two iterations in a row found nothing better. The search agent is looking into why the remaining tasks fail.` |
| Once it ended | `Two iterations in a row found nothing better. The search agent sorted the <n> tasks that the best config still failed by cause.` ("task" for 1) when it had tasks, then its [result](#reflection-results). |
| Causes | One group per [cause](#causes) recorded, in the order task, judge, check, infra, config: its title, what it means and what to do, then each task the cause was given for. |
| No cause recorded | Once it ended, the tasks it looked into without recording a cause: `The search agent looked into these tasks but recorded no cause.` |

Each task shows its title in the set, or `Task <first 8 characters of its id>`,

### Candidates

The "Candidates" card's note reads `Configs that the search agent proposed, by
iteration. Select a candidate to see its hypothesis, results and pull request.`
It is one table:

| Column | Shows |
| --- | --- |
| Candidate | Its name, or "Live config"; a blue lightning icon for a [frontier](#frontier) point, whose hover reads "On the frontier" and `No other candidate succeeds more for less.`; its [overfit status](#overfit) when it has one; and a warning icon when it is [over the regression limit](#regressions-against-the-live-config). Selecting the row opens its [details](#candidate-details), and selecting it again closes them. |
| Searched | Its replay's [state](/docs/reference/app/replays#replay-states) until that replay has finished, "Not scored yet", or its [search score](#scores) as a percentage, with `Likely range: <range> · of <n> runs scored` on hover. |
| Held out | Its held-out score, with its range on hover; "Replaying" while its held-out replay is queued or running; "Not held out" for a candidate that was not replayed there; else `–`. |
| Gain | Its [gain](#gains) over the live config on the searched tasks, as in `+12 pts`, green when its significance is `better` and red when `worse`. Hovering shows `Gain over the live config, searched: <gain>, likely <low> to <high> pts.`, then the same for `held out` once known. `–` without one. |
| Cost per run | What it spent per scored searched run, or "Unpriced". |
| Pull request | `–` until it is picked, else its [state](#config-pull-request-states): "Opening…", "Opened", "Closing…", "Merged" or "Closed", linked to the pull request on GitHub once it is there, with an ⓘ whose hover says why a closed pull request closed; or "Not opened" with a warning icon, "Why", whose hover reads `<reason>. <message>`: the [reason](#config-pull-request-reasons) in words, then Spotlight's message. |

The first row, "Started from", shows the live config. Then each iteration has
a row `Iteration <n>`, followed by its candidates. An iteration's row reads
`· Looked for why it stalled` for a [reflection](#reflections), its
[state](#iteration-states) unless it ended, and "Agent run", linked to the
agent run's Run page, titled `Iteration <n> of Search <m>`. Hovering over `Iteration <n>` shows
`<state>. The search took <n> of <m> proposals. The search agent spent
<spent>.`: rejected proposals count among the second, a reflection has no
count of proposals, and what its agent spent shows once known.

An iteration with no candidates reads `Nothing proposed yet.` while its agent
run waits or runs, and `The search agent proposed nothing replayable.` after.
A reflection reads `This iteration proposes nothing. The search agent is
looking into why the remaining tasks fail.` until it ends, then `This
iteration proposed nothing. The search agent looked into <n> tasks that the
best config still failed. Causes recorded: <n>`. Both are followed by "See
why it stalled", which scrolls to its [card](#why-it-stalled).

With no iteration yet, the card reads "No candidates yet" and `The live config
replays first. The search agent proposes candidates after that replay
finishes.` while the search is `seeding`, `Spotlight couldn't replay the live
config. The search agent never ran.` once it ended `seed-failed`, or else `The
search agent proposed no candidates.`, with "Watch the live config's replay".

The page opened with `#candidate-<candidateId>` scrolls to that candidate's
row. A searched candidate's "Changes" link on the Insights
[Candidates](/docs/reference/app/insights#candidate-rows) section opens it so,
unless picking it opened a pull request.

### Candidate details

Selecting a candidate opens a side pane, which can be resized and closed. Its
heading is the candidate's name, then its icons: the blue lightning icon for a
[frontier](#frontier) point, its [overfit status](#overfit) when it has
one, and a warning icon when it is
[over the regression limit](#regressions-against-the-live-config). Its
replay's [state](/docs/reference/app/replays#replay-states) shows until that
replay has finished. Under it are these sections:

| Section | Shows |
| --- | --- |
| Changes | For a candidate, one change per line, as [Config](/docs/reference/app/tasks-runs-and-the-inbox#config) words them, or `Same as the live config.` For the live config, `The station as configured when the search started.` |
| Hypothesis | Its agent's hypothesis: what the candidate should improve, and why. Only when it has one. |
| Results | A table of the candidate beside the live config. See below. |

The "Results" heading has "Replay", linked to its replay on the searched
tasks ("Replay of the set" for the live config), and "Held-out replay" when it
has one.

The "Results" table has the columns "This config", "Live config" and "Gain".
For the live config, it has only the "Live config" column.

| Row | Shows |
| --- | --- |
| Held out | The held-out score as a percentage, or as in the [Candidates](#candidates) table. Hovering over a score shows `Likely range: <range>`. |
| Searched | The [search score](#scores) as a percentage, or `–`, with its range on hover. |
| Cost per run | What it spent per scored searched run, or "Unpriced". |
| Regressions | How many tasks it [regressed](#regressions-against-the-live-config) on, as in the [frontier table](#success-against-cost). Not for the live config. |

Each "Gain" cell is its [gain](#gains) over the live config there, as in
`+12 pts`, or `–`. An up or down triangle, or a dash for no change, is green
when the verdict is `better`, red when `worse`, and grey when `within-noise`.
Hovering over it shows the verdict, "Better", "Worse" or "Within noise", and
`Likely range: <low> to <high> pts`.

Under "Results", the candidate Spotlight picked shows its pull request. See
[Spotlight's pick](#spotlights-pick).

### Success against cost

The card's note says what the frontier joins for the search's [aim](#aims):
`Success on the searched tasks and cost per run of each candidate. Frontier:
candidates that no other candidate beats for less. The live config is always
on the frontier.` For the same success for less, the second sentence reads
`Frontier: candidates that match the live config's success, within noise, and
that no other candidate matches for less.` Its header has a "Chart" and
"Table" switch, on "Chart" at first.

The chart draws each candidate with a search score whose searched replay has
finished, and the live config once it has a search score: its
[search score](#scores) up the side, its cost per run along the bottom. Points
on the [frontier](#frontier) are joined by a dashed line, and the live config
is drawn as a diamond. The legend reads "On the frontier", "Other candidates"
and "Live config". Hovering over a point shows its name,
`<share> succeeded · <cost> a run`, and `on the frontier` for a frontier
point. The live config is always on the frontier, so its point reads
`where it started · on the frontier`.

With no priced point, the chart reads
`No candidate has a priced score yet. Show the table to see the rest.` Points
not priced are listed under the chart after `Hidden, not priced:`, each as its
name with its search score and range.

"Table" lists every candidate instead:

| Column | Shows |
| --- | --- |
| Candidate | Its name, or "Live config", the blue lightning icon for a frontier point, its [overfit status](#overfit) when it has one, and a warning icon when it is [over the regression limit](#regressions-against-the-live-config). |
| Iteration | The iteration that proposed it, or `–` for the live config. |
| Searched | Its search score with its range, `of <n> runs scored`, counting replay runs, repeats included, or "Not scored yet". |
| Gain on searched | Its [gain](#gains) over the live config on the searched tasks with its range and significance, then its [side-by-side](#side-by-side-with-the-live-config) wins, losses and ties there, or `–`. |
| Held out | Its held-out score with its range, "Replaying" while its held-out replay is queued or running, "Not held out" for a candidate that was not replayed there, or `–`. |
| Gain on held out | Its gain over the live config on the held-out tasks, once its held-out replay has finished, then its side-by-side wins, losses and ties there, else `–`. |
| Regressions | How many tasks it [regressed](#regressions-against-the-live-config) on against the live config, searched and held out together. Hovering over a count above 0 shows `Searched: <n>` and `Held out: <n>`, without a count that is not made yet. `–` until either count is made, and for the live config. |
| Cost per run | What it spent per scored searched run, or "Unpriced". |

## Search states

| State | Shown | Final |
| --- | --- | --- |
| `seeding` | Replaying the live config | no |
| `searching` | Searching | no |
| `holding-out` | Checking on held-out tasks | no |
| `finished` | Finished | yes |
| `stopped` | Stopped | yes |

A search starts `seeding`: the station's live config is replayed on every run
of the set, as many times as its repeats, and this replay becomes the set's
[baseline](/docs/reference/glossary#baseline). Once it finishes, the search is
`searching`, and wants its first iteration. Each iteration runs its agent once;
the agent proposes up to its candidates per iteration, each replayed on
the searched runs. An iteration closes once its agent run has ended, its spend
is known, and its candidates' replays have ended. Then the next iteration
starts, unless the search has run its iterations, [stalled](#stalls), or
cannot afford one more. It then holds out: `holding-out` while the best candidates are
replayed on the held-out runs, then `finished`. A search with no candidate
whose replay finished goes straight to `finished`.

## Stop reasons

| `stopReason` | Shown | Pill | State |
| --- | --- | --- | --- |
| `iterations-spent` | Ran every iteration it was given | None | `finished` |
| `ceiling-reached` | Reached its ceiling | Hit its ceiling | `finished` |
| `stalled` | Found nothing better twice in a row | Stalled | `finished` |
| `stopped` | Stopped by a person | Stopped | `stopped` |
| `station-gone` | Station is gone from the line | Station gone | `stopped` |
| `seed-failed` | Live config couldn't be replayed | Couldn't start | `stopped` |

The pill shows in the [search page](#search-page)'s header. Hovering over it,
or over the search's state on the [Searches card](#searches-card), shows the
stop reason in words.

`ceiling-reached` also ends a search whose replay of the live config ran over
its ceiling. `stalled` ends a search that [stalled](#stalls) with no room to
look into why, or whose reflection found nothing the config can fix. A stopped
search cancels or stops its agent's run
and stops its replays.

## Iteration states

| State | Shown | Meaning |
| --- | --- | --- |
| `wanted` | Waiting for a runner | Its agent run is not yet queued, or no runner has claimed it. |
| `running` | Running | Its agent run is queued or running, and may propose candidates. |
| `ended` | Ended | Its agent run ended. |
| `failed` | Failed | Its agent run failed, asked a person, or could not start. |

Each iteration is of one kind: `propose`, whose agent proposes candidates, or
`reflect`, a [reflection](#reflections), whose agent proposes nothing and
records causes. A reflection counts in "Iterations" like any other.

An agent run no runner claims within 60 minutes is cancelled, and its iteration
fails. An agent run whose spend is not known 15 minutes after it ended is
counted as [unpriced](#spend-and-ceiling).

## The search's agent run

Each iteration's agent run is a run of its own kind:

| | Search agent run |
| --- | --- |
| Task | Has no task. |
| Placement | Where the station's runs go: the station's `runners`, else the line's. Its priority is below every task run and chat run. |
| Workspace | No repository is checked out, and no skills, settings files or team memories are laid out. |
| Briefing | The station's live config as the search started, the budget left, how many candidates it may propose, how many tasks are held out, what counts as better for the search's [aim](#aims), what a candidate may change, and how to propose one. After a reflection that continued, also each `config` cause it recorded, with its task, evidence and suggestion. A reflection's briefing instead names the config whose failures it looks into, lists each failing task with its original run and the replay run that failed it, describes the five [causes](#causes), and says how to record one. |
| `spotlight history` | Only the searched station. The held-out tasks' runs are left out; the searched runs are always written. A `candidates/` folder contains each candidate so far. Each replay run's `result.json` gives its verdict, a code for each reason it failed and the judge's [`guidance` field](/docs/reference/app/replays#guidance), and never the judge's reasons. See [`spotlight history`](/docs/reference/cli/agent-commands#spotlight-history). |
| `spotlight candidate` | Proposes a candidate. Not allowed in a reflection. See [`spotlight candidate`](/docs/reference/cli/agent-commands#spotlight-candidate). |
| `spotlight cause` | Records a task's cause, in a reflection only. See [`spotlight cause`](/docs/reference/cli/agent-commands#spotlight-cause). |
| Not allowed | Messages from people, git, tools, `spotlight reply`, `spotlight recall` and `spotlight remember`. `spotlight trace` finds no held-out task. |
| Asking a person | Ends the run, and its iteration fails. |

## Stalls

A propose iteration found something better when one of its candidates'
replays on the searched tasks finished with a gain, paired task by task on
the searched runs against the best config of the iterations before it, that
the search's [aim](#aims) counts:

| Aim | Better than the best before |
| --- | --- |
| More success | Its gain reads "Better". |
| The same success for less | Its gain does not read "Worse", and it costs less per run, both costs known. |

The best before is the first in the order of the aim among the live config
and the candidates of earlier iterations whose replays finished. An iteration
whose agent run failed, or none of whose candidates' replays finished, found
nothing better.

When an iteration closes, the search ends `iterations-spent` once it has run
every iteration. Otherwise, if its last two iterations were both propose
iterations that found nothing better, it has stalled:

- With at least 2 iterations left, and room under the ceiling for what it has
  spent, what the held-out replays need, one more iteration and one more agent
  run, its next iteration is a [reflection](#reflections).
- Otherwise it ends `stalled`, and its starter gets a [notice](#notices).

A reflection is not a propose iteration, so after one that continued, two more
propose iterations must find nothing better before the search stalls again.

### Reflections

A reflection looks into the failures of the best config so far: the first in
the order of the search's aim among the live config and every candidate whose
searched replay finished. It looks into each searched run of the set on which
that config's success, the share of its scored repeats that succeeded, is below
one half and at least one repeat failed. A held-out task is never among them. The
first failed repeat is the replay run it links to.

With no such task, the reflection ends at once, without an agent run, and the
search ends `stalled`. Otherwise its agent records one [cause](#causes) per
task with [`spotlight cause`](/docs/reference/cli/agent-commands#spotlight-cause).
Recording a task's cause again replaces the one before. Once its agent run
ends, or fails:

| Recorded | The search |
| --- | --- |
| At least one `config` cause | Wants a propose iteration, whose briefing lists the `config` causes, if it can afford one; else ends `ceiling-reached`, or `iterations-spent` with none left. |
| No `config` cause | Ends `stalled`. |

### Causes

| `cause` | Title | Means | Shown to do |
| --- | --- | --- | --- |
| `task` | The task itself | `The task is unclear, out of date, or can't be done as written. No config would get it right.` | `Fix the task, or take it out of the replay set.` |
| `judge` | The judge | `The work can be fine, but the judge scored it wrong. The judge's rubric requires the wrong thing.` | `Fix the judge's rubric.` |
| `check` | The check | `The check failed for a reason that the change didn't cause, such as a broken or flaky test.` | `Fix the check.` |
| `infra` | Around the work | `Something around the work failed the run, such as the runner, the network or a missing tool.` | `Replay it again. If it keeps failing, fix what the run needs.` |
| `config` | The station's config | `A change to the station's config, such as prompt, model or skills, could still fix it.` | `You don't need to do anything. The search keeps trying configs for these tasks.` |

Only `config` lets the search go on.

### Reflection results

| `result` | When | Shown |
| --- | --- | --- |
| `continued` | A `config` cause, and the search wanted a propose iteration. | `The search continued. A config change can still fix some of these tasks.` |
| `ceiling-reached` | A `config` cause, but the search could not afford a propose iteration or had none left. | `The search ended at its ceiling. A config change can still fix some of these tasks.` |
| `no-config-cause` | No `config` cause. | `The search ended. No config change can fix the tasks that are left. The rest of the budget stays unspent.` |
| `no-failures` | No searched task failed. | `The search ended. No searched task failed.` |
| `did-not-run` | Its agent run failed before it recorded any cause. | `The search ended. The search agent's run failed before it recorded a cause.` |

### Notices

Searches send [inbox notices](/docs/reference/app/tasks-runs-and-the-inbox#notices)
to the team: one notice, which every person on the team sees in their inbox,
while they are on the team. A notice about a search links to it with "Open the
search"; a notice about a skipped search links to the station with "Open the
station".

| When | Form | Headline | Points |
| --- | --- | --- | --- |
| Spotlight opened a pull request for the picked candidate | `ended` | `Spotlight opened a config pull request for the <station> station` | The candidate line, `Pull request: <url>`, `Please review the pull request. The station changes when you merge it.` |
| The pull request could not be opened | `ended` | `Sorry, the config pull request for the <station> station could not be opened` | The candidate line, `Reason: <message>` |
| Spotlight picked no candidate | `ended` | `The search of the <station> station ended with no pull request` | The [decline](#spotlights-pick) in words. |
| A search was [skipped](#skip-reasons) for `no-scoring`, `set-too-small`, `no-headroom`, `ceiling-too-low` or `no-agent` | `advice` | `Spotlight cannot search the <station> station` | Advice by reason, below. |

`the <station> station` reads `a station` when the station has no name to
give. The candidate line is `Candidate <name> did better than the live config
on the held-out tasks.`, or, for a search that aims for the same success for
less, `Candidate <name> cost less per run than the live config and did as well
on the held-out tasks.` In a notice, `pull-request-open` reads `A config pull
request for the station is open. Spotlight keeps one open config pull request
for each station.`, and `rejected-before` reads `A config pull request for each
passing candidate was closed on GitHub before. Spotlight does not propose this
config again while the station's live config stays the same.` Each finished
search sends one `ended` notice. A config pull request that merges, or that
Spotlight closes as stale, sends no notice. When the search ended [stalled](#stalls), the notice's points go on
with what its last reflection found, as below, or with `Two iterations in a
row found nothing better. No budget was left to find out why.` when it had no
budget to reflect.

A reflection's points start with what happened, by its result:

| `result` | First point |
| --- | --- |
| `continued` | `Two iterations in a row found nothing better. A config change could still fix some of the <n> tasks still failing.` |
| `no-config-cause` | `No config change can fix the <n> tasks still failing. The rest of the budget stays unspent.` |
| `no-failures` | `Two iterations in a row found nothing better. The best config already passes every searched task.` |
| `did-not-run` | `The reflection run failed before recording any cause. The search page links to that run.` |
| `ceiling-reached` | `A config change could fix some of the <n> tasks still failing. No budget was left to try one.` |

After it, one point per cause other than `config`, as
`<what to do>, for "<task title>": <suggestion>`, or the evidence without a
suggestion: "Take the task out of the replay set, or reword it", "Fix the
judge's rubric", "Fix the station's check" or "Fix what the run needed around
the work". A task with no title reads "one of the searched tasks". A point is
cut at 1,000 characters; past 20 points, the last reads `The search page shows
<n> more.` A reflection's points join the notice only when the search ended
stalled.

| Skip `reason` | Points |
| --- | --- |
| `no-scoring` | `The station has no judge and no check. Spotlight cannot score a config without one of them.`, `Please add a judge or a check to the station in the Terraform of the line.` |
| `set-too-small` | `The replay set of the station has too few tasks. Spotlight adds tasks from new runs of the station.`, `Minimum tasks required: 5` |
| `no-headroom` | `The live config does not do better on the replay set when it gets the answer. A search has no room to improve it.`, `Please add harder tasks to the station, or change its judge or check.` |
| `ceiling-too-low` | `The search ceiling is too low to replay each task of the set for each candidate.`, `Please raise the search ceiling in the search policy of the line.` |
| `no-agent` | `No runner can start the harness of the search agent.`, `Please set a harness for the station, or an agent in its search policy.` |

A skip sends its notice when the reason differs from the station's last
recorded skip, so a skip repeated for the same reason sends no new notice.

## Scores

| Score | Meaning |
| --- | --- |
| Search score | Its [success](/docs/reference/app/replays#success) on the searched tasks: per task, the share of its scored repeats that succeeded, averaged over the tasks scored, with its 95% range. For the live config, from its replay's searched runs only. |
| Held-out score | Its success on the held-out tasks, worked out the same way, once its held-out replay has finished. For the live config, from its replay's held-out runs. |
| Cost per run | What its replay on the searched tasks spent per scored run, in the ceiling's currency. Unknown, "Unpriced", while any of that spend was not priced or was in another currency. |

Results and their reasons are a replay's: see
[Results](/docs/reference/app/replays#results).

### Gains

Each candidate other than the live config reads its gain over the live
config's replay twice: on the searched tasks, and on the held-out tasks once
both its held-out replay and the live config's replay have finished. Each is
paired task by task, with its range and a significance of "Better", "Worse" or "within
noise", as a [replay's gain](/docs/reference/app/replays#gains) is, against the
line's `min_gain`. The frontier and the best candidate do not depend on it.

### Side by side with the live config

Each candidate's replays, on the searched and on the held-out tasks, are
[set side by side](/docs/reference/app/replays#side-by-side) with the search's
replay of the live config once they finish, when the candidate has a judge.
Each reads `Side by side with the search's starting config: <n> wins, <n>
losses, <n> ties`, counting the tasks of that replay, once any was compared. They never change its score, its
gain, the frontier or the best candidate.

### Overfit

Once a candidate's held-out gain is known, a candidate whose searched gain reads
"Better" gets an `overfit` status from it:

| Held-out gain | Shown | Note |
| --- | --- | --- |
| `better` | Nothing | |
| `within-noise` or `worse`, over at least 5 tasks scored on both sides | "Likely overfit": `likely` | "Likely overfit" and `It gained on searched tasks, not on held-out tasks.` |
| Over fewer than 5 tasks scored on both sides | "Overfit unknown": `too-few-held-out` | "Overfit unknown" and `Too few held-out tasks have a score.` |

On the [Searches card](#searches-card), in the "Best" tile, the
candidates table, the candidate's details and the frontier table, the overfit
status is a warning icon named by the status: amber for "Likely overfit", grey
for "Overfit unknown". Hovering over or focusing the icon opens its note. A
candidate whose searched gain does not read "Better" has no overfit status, nor
does one before its held-out gain is known, nor the live config. A likely
overfit candidate stays on the frontier and can still be the
[best candidate](#best-candidate). Spotlight never
[picks](#spotlights-pick) a candidate with an overfit status.

### Regressions against the live config

Each candidate other than the live config counts the tasks it
[regressed](/docs/reference/app/replays#regressions) on against the live
config's replay. The rule is the same as for a replay against its
counterpart. The count on the searched tasks is made when the candidate's
searched replay has finished. The count on the held-out tasks is made when
both its held-out replay and the live config's replay have finished. The
"Regressions" column of the [frontier table](#success-against-cost) shows the
two counts together.

When the line has a `replay_check` block, its
[`max_regressions`](/docs/reference/terraform/line#replay-check-fields) is the
regression limit. Spotlight reads it from the line as it is now. A candidate is
over the regression limit when its searched and held-out regressions together
are more than `max_regressions`. Then an amber warning icon, named "Over the
regression limit", shows beside its name: on the
[Searches card](#searches-card) when it is the best candidate, in the "Best"
[tile](#tiles), in the [Candidates](#candidates) table and the
[candidate's details](#candidate-details), and in the frontier table. Hovering
over or focusing the icon opens "Over the regression limit", with
`Regressed: <n> tasks` ("task" for 1) and `Line allows: <max_regressions>`. A candidate over the limit stays on the
frontier and can still be the [best candidate](#best-candidate). Spotlight
never [picks](#spotlights-pick) a candidate over the limit. A line without a `replay_check` block has no
limit: the counts show, and no candidate is marked.

### Aims

A search aims for one of two things, chosen when it starts and kept for its
life:

| Aim | `objective` | Ranks |
| --- | --- | --- |
| More success | `success` | Every scored candidate, by score, then the cheaper. |
| The same success for less | `cost` | The live config, and the candidates whose gain over the live config reads "Better" or "within noise", by cost per run, then by score. A candidate whose gain reads "Worse", or is not known yet, is left out. |

The station's `objective` in its [`search`](/docs/reference/terraform/line)
block sets the aim. Left out, a search aims for the same success for less when
the newest finished replay of the live config, as it is now, over every run of
the set, other than a search's, succeeded on more than 95% of it, and for more
success otherwise.

### Frontier

The frontier is every candidate with a finished searched replay and a search
score that no other candidate beats on both counts: succeeding at least as
often for no more cost per run, and better on one. An unpriced cost counts as
the highest. The live config is always on the frontier. When the search aims
for the same success for less, only candidates whose gain on the searched
tasks reads "Better" or "within noise" can be on it.

When a search stops searching, the frontier's candidates, the live config
aside, are replayed on the held-out runs, as many as its candidates per
iteration, in the order of its [aim](#aims). When it aims for the same success
for less, only candidates that cost less per run than the live config are.

### Best candidate

The candidate first in the order of the search's [aim](#aims): by held-out
score and held-out gain once any candidate has a held-out score, else by
search score and searched gain. When it aims for more success, that is the one
that succeeds most, then the cheaper; when it aims for the same success for
less, the cheapest that keeps its success, read "Cheapest". When the live
config comes first, the best reads "Live config".

## Spend and ceiling

A search's spend is what its replays and its agent's runs spent, in the
ceiling's currency. A tenth of the ceiling is for the agent's runs; the rest
gives each replay its own ceiling. A replay run whose cost was not reported or
is in another currency counts as the full share a replay run is given, and an
agent run whose spend is unpriced as the full share an agent run is given. A
new iteration starts only while what was spent, what the held-out replays need
and one more iteration fit under the ceiling. An agent run may go over its
share, so a search can end a little over its ceiling.

A search's replays run up to 4 at a time, apart from the team's own
limit of 2 replay runs. See
[Limits and timeouts](/docs/reference/limits-and-timeouts#searches).

## Spotlight's pick

When a search finishes, Spotlight ranks its candidates that have a held-out
score in the order of the search's [aim](#aims), and picks the first that
passes every rule below and that Spotlight may propose. It then opens a
[pull request](#the-pull-request) for it. When none passes, it picks none, and
the search gets no pull request. A stopped search gets no pick. Nobody picks a
candidate by hand.

| Rule | A candidate passes when |
| --- | --- |
| Held-out gain, aiming for more success | Its [gain](#gains) over the live config on the held-out tasks reads "Better": its likely range stays above zero and reaches the line's `min_gain`. |
| Held-out cost, aiming for the same success for less | Its gain over the live config on the held-out tasks reads "Better" or "within noise", and it cost less per run than the live config. |
| Regression limit | It is not [over the regression limit](#regressions-against-the-live-config). |
| Overfit | It has no [overfit status](#overfit). |

Spotlight does not propose a candidate whose config a person closed a config
pull request for on GitHub, while the station's live config stays what it was
then. See [Config pull request states](#config-pull-request-states).

The search page's header then reads "Picked by Spotlight" or "No pull
request", with what Spotlight decided on hover:

| `pick` | `reason` | Shown |
| --- | --- | --- |
| `picked` | | By the pull request's [state](#config-pull-request-states): `Spotlight picked <candidate>. Its config pull request is opening.`, `Spotlight opened a config pull request for <candidate>.`, `Spotlight is closing the config pull request for <candidate>.`, `The config pull request for <candidate> merged.`, `The config pull request for <candidate> is closed.` or `Spotlight picked <candidate>. Its config pull request could not be opened.`, then, for a closed pull request, why it closed, as below. |
| `declined` | `no-candidate` | `No candidate finished its replay on the held-out tasks.` |
| `declined` | `no-held-out-gain` | `No candidate did better than the live config on the held-out tasks.` |
| `declined` | `not-cheaper` | `No candidate cost less per run than the live config and did as well on the held-out tasks.` |
| `declined` | `over-regression-limit` | `The best candidate is over the regression limit of the line.` |
| `declined` | `likely-overfit` | `The best candidate is likely overfit. It did better only on the searched tasks.` |
| `declined` | `station-gone` | `The station is gone from its line. Spotlight cannot change its config.` |
| `declined` | `pull-request-open` | `A config pull request for the station is open.` |
| `declined` | `rejected-before` | `A config pull request for each passing candidate was closed on GitHub before. Spotlight does not propose these configs again while the station's live config stays the same.` |

A declined search's `reason` is `station-gone` when the station has left its
line, `pull-request-open` when a candidate passes but a config pull request of
the station is open, `rejected-before` when every candidate that passes was
closed on GitHub before, and otherwise the first rule the top-ranked candidate
fails. The finished search also sends the team a [notice](#notices).

The picked candidate's [details](#candidate-details) show its pull request
under "Results":

| State | Shown |
| --- | --- |
| `opening` | `Opening a pull request…` |
| `opened` | "View pull request", linked to it. |
| `closing` | `Spotlight is closing the pull request…`, then "View pull request". |
| `merged` | `Pull request merged`, then "View pull request". |
| `closed` | `Pull request closed`, with an ⓘ whose hover says why, then "View pull request". |
| `failed` | "No pull request opened", the [reason](#config-pull-request-reasons) in words, Spotlight's message, and, for an attribute, `At <attribute>, computed by <expression>. Please set it by hand to <value>`, each part only when known. |

While a config pull request of the station is open, Spotlight starts no search
of the station. See [Skip reasons](#skip-reasons).

### The pull request

Spotlight reads the file named by the line's
[`source`](/docs/reference/terraform/line#source-fields) on the repository's
default branch, edits the station's block, commits to its own branch and opens
the pull request against the default branch.

| | Value |
| --- | --- |
| Branch | `spotlight/search-<first 8 characters of the search id>-<candidate name>` |
| Title | `<station key>: <candidate name>` |
| Commit message | The title, then `Picked from a Spotlight search of the <station key> station.` |
| Body | `Spotlight searched for a better config of the <station key> station on the <line key> line and found <candidate name>. Spotlight picked it because it did better than the live config on the held-out tasks. This changes the station as the candidate has it: <attributes>.`, then the agent's hypothesis, a table of its and the live config's success on the searched and held-out tasks, each with its range, and cost per run, a sentence on how many tasks it regressed on against the live config, as in `Against the live config it regressed on 2 searched tasks; on the held-out tasks, 1 held-out task. The search never showed its agent the held-out tasks.`, a sentence for each gain, as in `On the held-out tasks it gained +12 points (+3 to +21) on the live config, more than the 5-point gain the line counts as real.`, a sentence for its side-by-side wins, losses and ties on the searched and on the held-out tasks once any was compared, as in `Set side by side with the live config's change on the searched tasks, without the judge knowing which was which, its change was better on 4 tasks, worse on 1 task and as good on 2 tasks.`, any attribute Spotlight could not check, and a link to the search. |

In the regressions sentence, `it could not be compared on the searched tasks`
replaces `it regressed on <n> searched tasks` when the searched tasks have no
count.

The edit finds exactly one `resource "spotlight_line"` whose `key` is the
line's, written as a plain string, preferring the one whose `team_id` refers to
the team's `spotlight_team`, and in it exactly one `station` block whose `key`
is the station's. It changes only the attributes the candidate changes:

| Attribute written as | Edit |
| --- | --- |
| A plain value or heredoc | Replaced in place. |
| `file("${path.module}/<path>")`, for `prompt`, `description`, `harness`, `model`, `effort` or `profile` | The new value is written to the station's own file beside the `.tf` file: `prompts/<team>/<line>/<station>.md` for `prompt`, the file the export writes, and `prompts/<team>/<line>/<station>.<attribute>.md` for the others. If the attribute was already read from that file, and nothing else reads it, the file is changed in place. Otherwise a new file is written, with `-2`, `-3` and on added to its name when one is taken, and `file()` is pointed at it. |
| A reference to a resource in the same file, as for `profile`, `skills` and `tools` | Followed to its value. A new value is written as a reference when a resource in the file contains it. |
| Not written | Added after the block's last attribute. |
| Anything else, such as a variable or a local | Fails with `computed-attribute`. |

Before it writes, the edit checks that every attribute the candidate may change,
the station's `check` and `passes_to`, and its `judge` block still have the values the
search started from, and fails with `base-changed` otherwise. An attribute it
cannot read and the candidate does not change is listed in the pull request
as not checked. An attribute read through `file()` with a path not built on
`${path.module}` cannot be followed, so changing it fails with
`computed-attribute`. A `file()` path outside the repository fails with
`file-missing`. The edited
file is read back, and the edit fails with `edit-failed` if it does not parse or does
not contain the candidate's values.

When GitHub answers a request with a `4xx` status, other than for a rate limit,
the pull request fails at once with `github-error`. An attempt that fails
for another reason, such as GitHub not answering or a rate limit, is tried
again after 30 seconds, 2 minutes, 8 minutes and 32 minutes, and then fails
with `github-error`.

### Config pull request states [#config-pull-request-states]

Once a pull request is on GitHub, Spotlight follows it until it merges or
closes. A station has at most one open config pull request: one that is
`opening`, `opened` or `closing`.

| `state` | Shown | Means |
| --- | --- | --- |
| `opening` | `Opening a pull request…`, "Opening…" | Spotlight is opening it on GitHub, and tries again after a failure, as above. |
| `opened` | `Pull request opened`, "Opened" | It is open on GitHub. |
| `closing` | `Spotlight is closing the pull request…`, "Closing…" | The station's live config changed, and Spotlight is closing it on GitHub. |
| `merged` | `Pull request merged`, "Merged" | It merged on GitHub. |
| `closed` | `Pull request closed`, "Closed" | It closed on GitHub without merging, by Spotlight or by a person. |
| `failed` | `No pull request opened`, "Not opened" | Spotlight could not open it. See [Config pull request reasons](#config-pull-request-reasons). |

When a change to the line is applied, Spotlight compares the station's live
config with each of its `opened` pull requests. When the live config matches
neither the config the pull request started from nor the one it proposes, the
pull request is stale: it moves to `closing`, Spotlight closes it on GitHub and
comments `Spotlight closed this pull request. The station's live config changed
after this pull request opened.` A pull request that already merged or closed
on GitHub settles as `merged` or `closed` instead. When GitHub answers with an
error that trying again cannot fix, or 5 tries to close it fail, the pull request settles as
`closed` with the failure recorded. A merged pull request is never closed as
stale.

Spotlight also reads each `opened` pull request's state from GitHub every 6
hours, in case it missed GitHub's event, and records a merge or a close it
finds.

| `closedBecause` | Shown on hover |
| --- | --- |
| `stale` | `The live config of the station changed after the pull request opened.` |
| `by-person` | `The pull request was closed on GitHub. Spotlight does not propose this config again while the station's live config stays the same.` |

When Spotlight could not close a stale pull request, the hover ends with
`Sorry, Spotlight could not close it on GitHub. <message>`.

When a person closes a config pull request on GitHub without merging it, the
station's [cooldown](#skip-reasons) starts again from that moment, and
Spotlight does not propose the same config for the station while its live
config stays the same. Reopening the pull request on GitHub, while the station
has no other open config pull request, moves it back to `opened` and lifts
that. When a pull request merges, the station's
[improvement status](#improvement-status) reads "Improved" until its next
search starts. A merged or stale-closed pull request sends no notice.

### Config pull request reasons

| Code | Shown |
| --- | --- |
| `no-source` | Line names no repository for its Terraform |
| `repository-unreachable` | Spotlight's GitHub App can't access the line's repository |
| `file-missing` | Line's Terraform file isn't in its repository |
| `file-unparsable` | Line's Terraform file couldn't be read |
| `block-not-found` | Station's block isn't in the file |
| `blocks-ambiguous` | Station's block appears more than once |
| `computed-attribute` | Attribute is computed in Terraform. Please set it by hand. |
| `base-changed` | File changed since the search began |
| `edit-failed` | Edited file wouldn't parse as Terraform. Please make the change by hand. |
| `branch-taken` | Pull request branch already exists |
| `file-unwritable` | File couldn't be written to its repository |
| `github-error` | GitHub answered with an error |

Each comes with Spotlight's message, such as
``Terraform computes `prompt` from `local.build_prompt`. Please change it by hand.``.
`block-not-found` also covers a station no longer on its line, and
`file-missing` a file a `file()` reads that the repository does not contain.
`file-unwritable` is a file that is a symbolic link in the repository.
`branch-taken` means the branch has commits Spotlight did not write.

## Search replays

A search's replays are replays of its set, and each replay page and replay run
reads as any other replay. A candidate's replay covers only the searched runs,
and a held-out replay only the held-out runs. The replay page's header, and
the Run page of each of its replay runs, read `candidate <name> in its search`,
or `the live config it started from in its search`, linked to the search.

While a search is in progress, Spotlight does not refresh its set, and no run
can be taken out of it. The set's page disables the X beside each run, with
`A search of this set is running. Take out runs after the search ends or a
person stops it.` on hover.
