A [search](/docs/reference/glossary#search) has an agent propose changed
configs for a work station, called candidates, and
[replays](/docs/reference/app/replays) each on the searched tasks of the
station's replay set. The best are then replayed on the set's
[held-out tasks](/docs/reference/glossary#held-out-task). Spotlight starts
searches itself, from the line's [`search`](/docs/reference/terraform/line#search-fields)
policy, and when a search finishes, it picks a candidate and opens a
[config pull request](#the-pull-request) in the line's Terraform repository.
See [How Spotlight improves a station](/docs/improvement/how-spotlight-improves-a-station).

The app has no page for a search. A search's result shows in its config pull
request on GitHub, and in an [inbox notice](#notices) when a person must act.
Its candidates show under
[Candidates](/docs/reference/app/insights#candidates) on the Insights Stations
tab.

## Automatic improvement card

Under "Config", a work station's page shows its search policy as "Automatic
improvement", after "Line": "On", with `Up to <ceiling> a search · every
<period>`, as in `Up to $10 a search · every 7 days`, or "Off", with `No
automatic searches`. Hovering over "On" shows `Spotlight searches for a better
config of this station and opens a pull request for it.`, then:

| Row | Shows |
| --- | --- |
| Line ceiling a month | The line's `monthly_ceiling`. |
| After an alert | "Starts a search" or "Doesn't start a search", from `on_alert`. |
| Cooldown | The `cooldown`, in words, as in `3 days`. |
| Agent | The search agent's harness, model and effort, or "Spotlight picks". |
| Iterations | The station's `iterations`, or "Spotlight picks". |
| Repeats | The station's `repeats`, or "Spotlight picks". |
| Objective | "More success" or "The same success for less", or "Station health picks". |

The card only shows the policy. The policy is changed in the line's
Terraform. See [`search`](/docs/reference/terraform/line#search-fields) on the
line.

## Automatic searches

Spotlight looks at each work station that has a replay set and a search
policy that is on, and starts a search when one is due:

| `trigger` | When |
| --- | --- |
| `schedule` | The policy's `period` has passed since the station's last search started, or the station has had no search. |
| `alert` | One of the station's [alerts](/docs/reference/terraform/line#alert-fields) fired since its last search, and `on_alert` is `true`. The period need not have passed. |
| `request` | A chat that improves the station called [`test-station-change`](/docs/reference/built-ins/built-in-tools-and-skills#test-station-change). The period and the cooldown need not have passed. |

While the station's search policy is off, Spotlight starts no search and looks
again a day later. A search is not started while another search of the
station is in progress, or while the last finished search's pick, or the pull
request for it, is not done; Spotlight looks again an hour later. Before a
search starts, Spotlight
[refreshes the set](/docs/reference/app/replays#how-spotlight-keeps-the-set).
While a search is in progress, Spotlight does not refresh its set. A search
that starts takes:

| Part | Value |
| --- | --- |
| Iterations | The station's `iterations`, else 3. |
| Candidates per iteration | 2. |
| At once | 4 replay runs. |
| Repeats | The station's `repeats`, else 1. |
| Ceiling | The station's or the line's `ceiling`, in the line's `currency`. |
| Aim | The station's `objective`, else [chosen](#aims) from the set's health. |
| Agent | The station's `agent`, else the station's own harness, model and effort. |
| Held-out tasks | Drawn from the set's tasks that no earlier search of the station searched on. |

A `request` search starts at once or not at all. In mode `test` it has 1
iteration, whose only candidate is the requested change, and it runs no search
agent; in mode `search` its first candidate is the requested change, and the
rest of the table applies. It keeps to the same rules as the others, apart
from `cooldown`: the station's search policy is on, the station has a replay
set, its last search has given its result, and the [skip reasons](#skip-reasons)
other than `cooldown` do not apply, `no-agent` not in mode `test`. A station
takes at most 3 requested starts or joins in one UTC day. Otherwise the tool
answers with a [refusal](/docs/reference/errors-and-messages#test-refusals).
When a search of the station is in progress, in state `seeding` or
`searching`, and has an iteration left, a requested change joins it as one
candidate of that iteration instead, and gets no search or refinement of its
own. A search takes at most as many requested changes as it has candidates
per iteration.

A `request` search does not change when the station's next automatic search is
due: its period, cooldown and any alert that waits stay as they were. Its
searched tasks count as used, so no later search of the station holds them
out.

The first search on a new set, on a set a refresh changed, or after a change
to the station's config, [calibrates the set](/docs/reference/app/replays#calibration)
in its replay of the live config, which then replays each run 3 times. The
set's health checks apply to the searches after it.

### Skip reasons

When a due search cannot start, Spotlight records why and looks again later:
a day later for most reasons, an hour later for `pull-request-open`, at the
end of the cooldown for `cooldown`, and on the first day of the next month,
in UTC, for `monthly-ceiling`. The first row that applies decides:

| `reason` | When | Notice |
| --- | --- | --- |
| `no-scoring` | The station has no `judge`, and no `check` with `diffs`. | Yes |
| `cooldown` | The `cooldown` has not passed since the last search started, or since a person last closed a config pull request of the station on GitHub. | No |
| `pull-request-open` | A [config pull request](#config-pull-request-states) of the station is `opening`, `opened` or `closing`. | No |
| `monthly-ceiling` | What the line's searches started this month spent, plus one more `ceiling`, is over `monthly_ceiling`. | No |
| `set-too-small` | The set cannot give at least 2 held-out tasks and 3 searched tasks, so it covers fewer than 5 tasks. | No |
| `noisy` | At the search's repeats, the set's [noise](/docs/reference/app/replays#noise) is more than the line's `min_gain` allows. | Yes |
| `judge-unstable` | The set's newest [calibration](/docs/reference/app/replays#calibration) found the judge agreeing with itself less than 80% of the time. | Yes |
| `flaky-checks` | The set's newest calibration found a flaky check. | Yes |
| `no-headroom` | The newest [replay with the answer](/docs/reference/app/replays#replay-with-the-answer) found no [room to improve](/docs/reference/app/replays#room-to-improve). | No |
| `no-fresh-held-out` | Fewer of the set's tasks than a search holds out are ones no earlier search of the station searched on. | No |
| `ceiling-too-low` | The `ceiling` cannot give each replay run at least 0.01 of its currency. | Yes |
| `no-agent` | The search agent's harness is not one a runner can start, its model or effort is not valid, or neither the station's `search` nor the station names a harness. | Yes |

A reason marked "Yes" needs a person to act, and sends the team a
[notice](#notices) with advice. The others pass with time or with the
station's new runs, and send nothing. A skip sends its notice when the reason
differs from the station's last recorded skip, so a skip repeated for the same
reason sends no new notice.

## Search states

| State | Final |
| --- | --- |
| `seeding` | no |
| `searching` | no |
| `holding-out` | no |
| `finished` | yes |
| `stopped` | yes |

A search starts `seeding`: the station's live config is replayed on every run
of the set, as many times as its repeats, or 3 times when it
[calibrates the set](/docs/reference/app/replays#calibration), and this replay
becomes the set's [baseline](/docs/reference/glossary#baseline). Once it
finishes, the search is `searching`, and wants its first iteration. Each
iteration runs its agent once; the agent proposes up to its candidates per
iteration, each replayed on the searched runs. An iteration closes once its
agent run has ended, its spend is known, and its candidates' replays have
ended. Then the next iteration starts, unless the search has run its
iterations, [stalled](#stalls), or cannot afford one more. It then holds out:
`holding-out` while the best candidates are replayed on the held-out runs,
then `finished`. A search with no candidate whose replay finished goes
straight to `finished`.

## Stop reasons

| `stopReason` | State | When |
| --- | --- | --- |
| `iterations-spent` | `finished` | It ran every iteration it was given. |
| `ceiling-reached` | `finished` | It reached its ceiling, or its replay of the live config ran over its ceiling. |
| `stalled` | `finished` | It [stalled](#stalls) with no room to look into why, or its reflection found nothing the config can fix. |
| `turned-off` | `stopped` | A change to the line in Terraform turned the search policy off for the station, with `enabled = false` on the line or the station. |
| `station-gone` | `stopped` | The station left its line. |
| `seed-failed` | `stopped` | The live config could not be replayed. |

A stopped search cancels or stops its agent's run and stops its replays.
Spotlight picks a candidate only of a `finished` search. Nobody stops a search
by hand.

## Iteration states

| State | Meaning |
| --- | --- |
| `wanted` | Its agent run is not yet queued, or no runner has claimed it. |
| `running` | Its agent run is queued or running, and may propose candidates. |
| `ended` | Its agent run ended. |
| `failed` | Its agent run failed, asked a person, or could not start. |

Each iteration is of one kind: `propose`, whose agent proposes candidates, or
`reflect`, a [reflection](#reflections), whose agent proposes nothing and
records causes. A reflection counts as an iteration like any other.

An agent run no runner claims within 60 minutes is cancelled, and its iteration
fails. An agent run whose spend is not known 15 minutes after it ended is
counted as [unpriced](#spend-and-ceiling).

## The search's agent run

Each iteration's agent run is a run of its own kind:

| | Search agent run |
| --- | --- |
| Task | Has no task. |
| Placement | Where the station's runs go: the station's `runners`, else the line's. Its priority is below every task run and chat run. |
| Workspace | No repository is checked out, and no skills, settings files or team memories are laid out. |
| Briefing | The station's live config as the search started, the budget left, how many candidates it may propose, how many tasks are held out, what counts as better for the search's [aim](#aims), what a candidate may change, and how to propose one. After a reflection that continued, also each `config` cause it recorded, with its task, evidence and suggestion. A reflection's briefing instead names the config whose failures it looks into, lists each failing task with its original run and the replay run that failed it, describes the five [causes](#causes), and says how to record one. |
| `spotlight history` | Only the searched station. The held-out tasks' runs are left out; the searched runs are always written. A `candidates/` folder contains each candidate so far. Each replay run's `result.json` gives its verdict, a code for each reason it failed and the judge's [`guidance` field](/docs/reference/app/replays#guidance), and never the judge's reasons. See [`spotlight history`](/docs/reference/cli/agent-commands#spotlight-history). |
| `spotlight candidate` | Proposes a candidate. Not allowed in a reflection. See [`spotlight candidate`](/docs/reference/cli/agent-commands#spotlight-candidate). |
| `spotlight cause` | Records a task's cause, in a reflection only. See [`spotlight cause`](/docs/reference/cli/agent-commands#spotlight-cause). |
| Not allowed | Messages from people, git, tools, `spotlight reply`, `spotlight recall` and `spotlight remember`. `spotlight trace` finds no held-out task. |
| Asking a person | Ends the run, and its iteration fails. |

## Stalls

A propose iteration found something better when one of its candidates'
replays on the searched tasks finished with a gain, paired task by task on
the searched runs against the best config of the iterations before it, that
the search's [aim](#aims) counts:

| Aim | Better than the best before |
| --- | --- |
| More success | Its gain reads `better`. |
| The same success for less | Its gain does not read `worse`, and it costs less per run, both costs known. |

The best before is the first in the order of the aim among the live config
and the candidates of earlier iterations whose replays finished. An iteration
whose agent run failed, or none of whose candidates' replays finished, found
nothing better.

When an iteration closes, the search ends `iterations-spent` once it has run
every iteration. Otherwise, if its last two iterations were both propose
iterations that found nothing better, it has stalled:

- With at least 2 iterations left, and room under the ceiling for what it has
  spent, what the held-out replays need, one more iteration and one more agent
  run, its next iteration is a [reflection](#reflections).
- Otherwise it ends `stalled`.

A reflection is not a propose iteration, so after one that continued, two more
propose iterations must find nothing better before the search stalls again.

### Reflections

A reflection looks into the failures of the best config so far: the first in
the order of the search's aim among the live config and every candidate whose
searched replay finished. It looks into each searched run of the set on which
that config's success, the share of its scored repeats that succeeded, is below
one half and at least one repeat failed. A held-out task is never among them. The
first failed repeat is the replay run it links to.

With no such task, the reflection ends at once, without an agent run, and the
search ends `stalled`. Otherwise its agent records one [cause](#causes) per
task with [`spotlight cause`](/docs/reference/cli/agent-commands#spotlight-cause).
Recording a task's cause again replaces the one before. Once its agent run
ends, or fails:

| Recorded | The search |
| --- | --- |
| At least one `config` cause | Wants a propose iteration, whose briefing lists the `config` causes, if it can afford one; else ends `ceiling-reached`, or `iterations-spent` with none left. |
| No `config` cause | Ends `stalled`. |

### Causes

| `cause` | Means | In a notice |
| --- | --- | --- |
| `task` | The task is unclear, out of date, or can't be done as written. No config would get it right. | `the task itself`, then `Spotlight takes the task out of the replay set.` The next refresh takes the task out of the set; see [How Spotlight keeps the set](/docs/reference/app/replays#how-spotlight-keeps-the-set). |
| `judge` | The work can be fine, but the judge scored it wrong. | `the judge`, then `Please fix the rubric of the judge.` |
| `check` | The check failed for a reason that the change didn't cause, such as a broken or flaky test. | `the check`, then `Please fix the check of the station.` |
| `infra` | Something around the work failed the run, such as the runner, the network or a missing tool. | `what the run needed around the work`, then `Please fix the setup that the run needs.` |
| `config` | A change to the station's config, such as prompt, model or skills, could still fix it. | Not shown. |

Only `config` lets the search go on.

### Reflection results

| `result` | When | What else Spotlight found |
| --- | --- | --- |
| `continued` | A `config` cause, and the search wanted a propose iteration. | `Two iterations in a row found nothing better. A config change could still fix some of the <n> tasks still failing.` |
| `ceiling-reached` | A `config` cause, but the search could not afford a propose iteration or had none left. | `A config change could fix some of the <n> tasks still failing. No budget was left to try one.` |
| `no-config-cause` | No `config` cause. | `No config change can fix the <n> tasks still failing. The rest of the budget stays unspent.` |
| `no-failures` | No searched task failed. | `Two iterations in a row found nothing better. The best config already passes every searched task.` |
| `did-not-run` | Its agent run failed before it recorded any cause. | `The reflection run failed before it recorded a cause.` |

The last column is the first point of "What else Spotlight found" in the
[pull request](#the-pull-request), from the search's newest reflection. One
point per cause other than `config` follows, as
`"<task title>": the cause is <cause>. <suggestion> <fix>`, with the evidence
when the agent gave no suggestion, the cause and the fix as under
[Causes](#causes). A task with no title reads `Untitled task`. A point is cut
at 1,000 characters, and the title at 120; past 20 points, the last reads
`<n> more causes are not shown.` A search that stalled with no budget to
reflect gives `Two iterations in a row found nothing better. No budget was
left to find out why.`

## Scores

| Score | Meaning |
| --- | --- |
| Search score | Its [success](/docs/reference/app/replays#success) on the searched tasks: per task, the share of its scored repeats that succeeded, averaged over the tasks scored, with its 95% range. For the live config, from its replay's searched runs only. |
| Held-out score | Its success on the held-out tasks, worked out the same way, once its held-out replay has finished. For the live config, from its replay's held-out runs. |
| Cost per run | What its replay on the searched tasks spent per scored run, in the ceiling's currency. Unknown while any of that spend was not priced or was in another currency. |

Results and their reasons are a replay's: see
[Results](/docs/reference/app/replays#results).

### Gains

Each candidate other than the live config reads its gain over the live
config's replay twice: on the searched tasks, and on the held-out tasks once
both its held-out replay and the live config's replay have finished. Each is
paired task by task, with its range and a significance of `better`, `worse` or
`within-noise`, as a [replay's gain](/docs/reference/app/replays#gains) is, against the
line's `min_gain`. The frontier and the best candidate do not depend on it.

### Side by side with the live config

Each candidate's replays, on the searched and on the held-out tasks, are
[set side by side](/docs/reference/app/replays#side-by-side) with the search's
replay of the live config once they finish, when the candidate has a judge.
The [pull request](#the-pull-request) gives the picked candidate's wins,
losses and ties on each. They never change its score, its gain, the frontier
or the best candidate.

### Overfit

Once a candidate's held-out gain is known, a candidate whose searched gain reads
`better` gets an `overfit` status from it:

| Held-out gain | `overfit` |
| --- | --- |
| `better` | None |
| `within-noise` or `worse`, over at least 5 tasks scored on both sides | `likely`: it gained on the searched tasks, not on the held-out tasks. |
| Over fewer than 5 tasks scored on both sides | `too-few-held-out`: too few held-out tasks have a score to tell. |

A candidate whose searched gain does not read `better` has no overfit status,
nor does one before its held-out gain is known, nor the live config. A
candidate with an overfit status stays on the frontier and can still be the
[best candidate](#best-candidate). Spotlight never [picks](#spotlights-pick) a
candidate with an overfit status.

### Regressions against the live config

Each candidate other than the live config counts the tasks it
[regressed](/docs/reference/app/replays#regressions) on against the live
config's replay. The count on the searched tasks is made when the candidate's
searched replay has finished. The count on the held-out tasks is made when
both its held-out replay and the live config's replay have finished.

When the line has a `replay_check` block, its
[`max_regressions`](/docs/reference/terraform/line#replay-check-fields) is the
regression limit. Spotlight reads it from the line as it is now. A candidate is
over the regression limit when its searched and held-out regressions together
are more than `max_regressions`. A candidate over the limit stays on the
frontier and can still be the [best candidate](#best-candidate). Spotlight
never [picks](#spotlights-pick) a candidate over the limit. A line without a
`replay_check` block has no limit.

### Aims

A search aims for one of two things, chosen when it starts and kept for its
life:

| Aim | `objective` | Ranks |
| --- | --- | --- |
| More success | `success` | Every scored candidate, by score, then the cheaper. |
| The same success for less | `cost` | The live config, and the candidates whose gain over the live config reads `better` or `within-noise`, by cost per run, then by score. A candidate whose gain reads `worse`, or is not known yet, is left out. |

The station's `objective` in its [`search`](/docs/reference/terraform/line)
block sets the aim. Left out, a search aims for the same success for less when
the newest finished replay of the live config, as it is now, over every run of
the set succeeded on more than 95% of it, and for more success otherwise. See
[Health](/docs/reference/app/replays#health).

### Frontier

The frontier is every candidate with a finished searched replay and a search
score that no other candidate beats on both counts: succeeding at least as
often for no more cost per run, and better on one. An unpriced cost counts as
the highest. The live config is always on the frontier. When the search aims
for the same success for less, only candidates whose gain on the searched
tasks reads `better` or `within-noise` can be on it.

When a search stops searching, the frontier's candidates, the live config
aside, are replayed on the held-out runs, as many as its candidates per
iteration, in the order of its [aim](#aims). When it aims for the same success
for less, only candidates that cost less per run than the live config are.

### Best candidate

The candidate first in the order of the search's [aim](#aims): by held-out
score and held-out gain once any candidate has a held-out score, else by
search score and searched gain. When it aims for more success, that is the one
that succeeds most, then the cheaper; when it aims for the same success for
less, the cheapest that keeps its success. The live config can come first.

## Spend and ceiling

A search's spend is what its replays and its agent's runs spent, in the
ceiling's currency. A tenth of the ceiling is for the agent's runs; the rest
gives each replay its own ceiling. A search that
[calibrates the set](/docs/reference/app/replays#calibration) also keeps room
for the calibration's extra repeats and for the
[replay with the answer](/docs/reference/app/replays#replay-with-the-answer)
that follows it. A replay run whose cost was not reported or
is in another currency counts as the full share a replay run is given, and an
agent run whose spend is unpriced as the full share an agent run is given. A
new iteration starts only while what was spent, what the held-out replays need
and one more iteration fit under the ceiling. An agent run may go over its
share, so a search can end a little over its ceiling.

A search's replays run up to 4 at a time, apart from the team's own
limit of 2 replay runs. See
[Limits and timeouts](/docs/reference/limits-and-timeouts#searches).

## Spotlight's pick

When a search finishes, Spotlight ranks its candidates that have a held-out
score in the order of the search's [aim](#aims), and picks the first that
passes every rule below and that Spotlight may propose. It then opens a
[pull request](#the-pull-request) for it. When none passes, it picks none, the
search gets no pull request, and only the people who
[requested](#automatic-searches) a candidate of it are told. A stopped search gets no pick.
Nobody picks a candidate by hand.

| Rule | A candidate passes when |
| --- | --- |
| Held-out gain, aiming for more success | Its [gain](#gains) over the live config on the held-out tasks reads `better`: its likely range stays above zero and reaches the line's `min_gain`. |
| Held-out cost, aiming for the same success for less | Its gain over the live config on the held-out tasks reads `better` or `within-noise`, and it cost less per run than the live config. |
| Regression limit | It is not [over the regression limit](#regressions-against-the-live-config). |
| Overfit | It has no [overfit status](#overfit). |

Spotlight does not propose a candidate whose config a person closed a config
pull request for on GitHub, while the station's live config stays what it was
then. See [Config pull request states](#config-pull-request-states).

A search that picks none records why, as its `pick` `reason`:

| `reason` | When |
| --- | --- |
| `no-candidate` | No candidate finished its replay on the held-out tasks. |
| `no-held-out-gain` | No candidate did better than the live config on the held-out tasks. |
| `not-cheaper` | No candidate cost less per run than the live config and did as well on the held-out tasks. |
| `over-regression-limit` | The best candidate is over the regression limit of the line. |
| `likely-overfit` | The best candidate is likely overfit: it did better only on the searched tasks. |
| `station-gone` | The station left its line. |
| `pull-request-open` | A candidate passes, but a config pull request of the station is open. |
| `rejected-before` | Every candidate that passes was closed on GitHub before, while the station's live config was the same. |

Past `station-gone`, `pull-request-open` and `rejected-before`, the `reason` is
the first rule the top-ranked candidate fails. A search that picks none sends
the team no notice, unless it [stalled](#stalls) on causes a person must fix.
It sends each person who requested a candidate of it a notice of their own. See
[Notices](#notices).

### The pull request

Spotlight reads the file named by the line's
[`source`](/docs/reference/terraform/line#source-fields) on the repository's
default branch, edits the station's block, commits to its own branch and opens
the pull request against the default branch.

| | Value |
| --- | --- |
| Branch | `spotlight/search-<first 8 characters of the search id>-<candidate name>` |
| Title | `<station key>: <candidate name>` |
| Commit message | The title, then `Picked from a Spotlight search of the <station key> station.` |

The description holds everything a reviewer needs, with no link into
Spotlight. It opens with `Spotlight searched for a better config of the
<station key> station on the <line key> line and found <candidate name>.
Spotlight picked it because it did better than the live config on the held-out
tasks. This changes the station as the candidate has it: <attributes>.` Then,
when they apply, a paragraph for an [overfit](#overfit) candidate, or for a
candidate whose held-out replay had not finished, and a paragraph for a
candidate [over the regression limit](#regressions-against-the-live-config).
The sections follow:

| Section | Holds |
| --- | --- |
| What changes | One line per changed attribute, as `` `<attribute>`: `<was>` → `<now>` ``, with `not set` for a value that was or is not set, and the name of a skill or tool after the attribute. A value longer than 80 characters or of more than one line is folded under "Was and now", cut at 1,000 characters with `… Spotlight cut this value at 1000 characters.` At most 30 changes show, then `<n> more changes are not shown.`; past 8 folded values, a long change reads `<kind>. The value is too long to show here.` |
| Why it should be better | `The search's agent wrote:`, then the agent's hypothesis, cut at 1,000 characters. Only when the agent wrote one. |
| How it scored | A table of the candidate's and the live config's success on the searched and on the held-out tasks, each with its range as `72% (50–89%)`, and their cost per run, `—` where not known. Then how many tasks it regressed on against the live config, as in `Against the live config it regressed on 2 searched tasks; on the held-out tasks, 1 held-out task. The search never showed its agent the held-out tasks.`; a sentence for each [gain](#gains), as in `On the held-out tasks it gained +12 points (+3 to +21) on the live config, more than the 5-point gain the line counts as real.`; and a sentence for its [side-by-side](#side-by-side-with-the-live-config) wins, losses and ties on the searched and on the held-out tasks, once any was compared. |
| Not checked | The attributes the file computes in Terraform, which Spotlight could not check against the config the search started from. Only when there are any. |
| Task by task | A table for the held-out tasks, then one for the searched tasks: "Task", "Live config", "Candidate" and "Regressed" (`Yes` or `No`), regressed tasks first, then tasks the candidate lost. Each side reads `<result>: <reason>`, as for a [replay's results](/docs/reference/app/replays#results). A title is cut at 120 characters, `Untitled task` without one. At most 20 rows show, then `+<n> more tasks.` |
| About this search | `Started by:` `the schedule of the search policy`, `a station alert` or `a person, from a chat that improves the station`; `Iterations: <n> of <max>, with up to <n> candidates in each`; `Reflections:` how many iterations looked into why tasks failed, when any did; `Spent: <spent> of the <ceiling> ceiling`; `Search agent:` its harness, model and effort; `Tasks: <n> searched, <n> held out`; `Replay set: <n> runs,` and when it was refreshed; and `Noise:` how far success moves between repeats, or that Spotlight has not measured it yet, then the line's `min_gain`. |
| What else Spotlight found | What the search's newest [reflection](#reflection-results) found, one point per cause outside the config. Only when there is any. |

When the description would pass 60,000 characters, Spotlight leaves out the
last sections and ends it with `Spotlight left out the last <n> sections to
keep this description under the limit of GitHub, 65536 characters.` In the
description, `@` is never a mention, and text from tasks and the agent cannot
add links or tables.

The edit finds exactly one `resource "spotlight_line"` whose `key` is the
line's, written as a plain string, preferring the one whose `team_id` refers to
the team's `spotlight_team`, and in it exactly one `station` block whose `key`
is the station's. It changes only the attributes the candidate changes:

| Attribute written as | Edit |
| --- | --- |
| A plain value or heredoc | Replaced in place. |
| `file("${path.module}/<path>")`, for `prompt`, `description`, `harness`, `model`, `effort` or `profile` | The new value is written to the station's own file beside the `.tf` file: `prompts/<team>/<line>/<station>.md` for `prompt`, the file the export writes, and `prompts/<team>/<line>/<station>.<attribute>.md` for the others. If the attribute was already read from that file, and nothing else reads it, the file is changed in place. Otherwise a new file is written, with `-2`, `-3` and on added to its name when one is taken, and `file()` is pointed at it. |
| A reference to a resource in the same file, as for `profile`, `skills` and `tools` | Followed to its value. A new value is written as a reference when a resource in the file contains it. |
| Not written | Added after the block's last attribute. |
| Anything else, such as a variable or a local | Fails with `computed-attribute`. |

Before it writes, the edit checks that every attribute the candidate may change,
the station's `check` and `passes_to`, and its `judge` block still have the values the
search started from, and fails with `base-changed` otherwise. An attribute it
cannot read and the candidate does not change is listed in the pull request
as not checked. An attribute read through `file()` with a path not built on
`${path.module}` cannot be followed, so changing it fails with
`computed-attribute`. A `file()` path outside the repository fails with
`file-missing`. The edited
file is read back, and the edit fails with `edit-failed` if it does not parse or does
not contain the candidate's values.

When GitHub answers a request with a `4xx` status, other than for a rate limit,
the pull request fails at once with `github-error`. An attempt that fails
for another reason, such as GitHub not answering or a rate limit, is tried
again after 30 seconds, 2 minutes, 8 minutes and 32 minutes, and then fails
with `github-error`.

### Config pull request states [#config-pull-request-states]

Once a pull request is on GitHub, Spotlight follows it until it merges or
closes. A station has at most one open config pull request: one that is
`opening`, `opened` or `closing`.

| `state` | Means |
| --- | --- |
| `opening` | Spotlight is opening it on GitHub, and tries again after a failure, as above. |
| `opened` | It is open on GitHub. |
| `closing` | The station's live config changed, and Spotlight is closing it on GitHub. |
| `merged` | It merged on GitHub. |
| `closed` | It closed on GitHub without merging, by Spotlight or by a person. |
| `failed` | Spotlight could not open it. See [Config pull request reasons](#config-pull-request-reasons). |

When a change to the line is applied, Spotlight compares the station's live
config with each of its `opened` pull requests. When the live config matches
neither the config the pull request started from nor the one it proposes, the
pull request is stale: it moves to `closing`, Spotlight closes it on GitHub and
comments `Spotlight closed this pull request. The station's live config changed
after this pull request opened.` A pull request that already merged or closed
on GitHub settles as `merged` or `closed` instead. When GitHub answers with an
error that trying again cannot fix, or 5 tries to close it fail, the pull request settles as
`closed` with the failure recorded. A merged pull request is never closed as
stale.

Spotlight also reads each `opened` pull request's state from GitHub every 6
hours, in case it missed GitHub's event, and records a merge or a close it
finds.

A closed pull request records why, as `closedBecause`: `stale`, when the
station's live config changed after it opened, or `by-person`, when it was
closed on GitHub. When Spotlight could not close a stale pull request, the
failure is recorded with it.

When a person closes a config pull request on GitHub without merging it, the
station's [cooldown](#skip-reasons) starts again from that moment, and
Spotlight does not propose the same config for the station while its live
config stays the same. Reopening the pull request on GitHub, while the station
has no other open config pull request, moves it back to `opened` and lifts
that. A merged or stale-closed pull request sends no notice.

### Config pull request reasons

| Code | Means |
| --- | --- |
| `no-source` | The line names no repository for its Terraform. |
| `repository-unreachable` | Spotlight's GitHub App can't access the line's repository. |
| `file-missing` | The line's Terraform file isn't in its repository, or a file a `file()` reads is not. |
| `file-unparsable` | The line's Terraform file couldn't be read. |
| `block-not-found` | The station's block isn't in the file, or the station is no longer on its line. |
| `blocks-ambiguous` | The station's block appears more than once. |
| `computed-attribute` | An attribute is computed in Terraform, and must be set by hand. |
| `base-changed` | The file changed since the search began. |
| `edit-failed` | The edited file wouldn't parse as Terraform, and the change must be made by hand. |
| `branch-taken` | The pull request branch has commits Spotlight did not write. |
| `file-unwritable` | The file couldn't be written to its repository, as for a symbolic link. |
| `github-error` | GitHub answered with an error. |

Each comes with Spotlight's message, such as
``Terraform computes `prompt` from `local.build_prompt`. Please change it by hand.``,
which the [notice](#notices) gives as `Reason: <message>`.

## Notices

A search sends the team an [inbox notice](/docs/reference/app/tasks-runs-and-the-inbox#notices)
only when a person must act. Every person on the team sees it in their inbox,
while they are on the team. Each links to the station with "Open the station".
These notices go to the team, whatever started the search. A person who
requested a candidate gets a notice of their own only when their change did
not become the pull request; see below.

| When | Form | Headline | Points |
| --- | --- | --- | --- |
| Spotlight opened a pull request for the picked candidate | `ended` | `Spotlight opened a config pull request for the <station> station` | `Candidate <name> changes <attributes>.`, then `Held-out gain: <gain> points`, or for a search that aims for the same success for less, `Cost per run: <cost> <currency>, against <cost> <currency> for the live config`. Also links to the pull request on GitHub with "Review the pull request". |
| The pull request could not be opened | `ended` | `Sorry, the config pull request for the <station> station could not be opened` | `Candidate <name> changes <attributes>.`, `Reason: <message>`. |
| A search ended with no pull request after it [stalled](#stalls) on causes outside the config | `advice` | `The search of the <station> station stalled on causes outside the config` | One point per task, as under [Reflection results](#reflection-results). |
| A search was [skipped](#skip-reasons) for a reason a person must fix | `advice` | `Spotlight cannot search the <station> station` | Advice by reason, below. |

`the <station> station` reads `a station` when the station has no name to
give. `<attributes>` lists the changed attributes, as in `prompt, model`; with
none known, the point reads `Candidate <name> changes the station config.` The
gain reads as in `+12 points`, or `Held-out gain: not measured`; a cost
without a measure reads `Cost per run: not measured`. A notice
links to a pull request only at `https://github.com/`.

| Skip `reason` | Points |
| --- | --- |
| `no-scoring` | `The station has no judge and no check. Spotlight cannot score a config without one of them.`, `Please add a judge or a check to the station in the Terraform of the line.` |
| `ceiling-too-low` | `The search ceiling is too low to replay each task of the set for each candidate.`, `Please raise the search ceiling in the search policy of the line.` |
| `no-agent` | `No runner can start the harness of the search agent.`, `Please set a harness for the station, or an agent in its search policy.` |
| `noisy` | `Success moves too much between repeats of the same runs. Spotlight cannot tell configs apart on the replay set.`, `Please make the judge or the check of the station give the same result for the same work.` |
| `judge-unstable` | `The judge of the station does not give the same verdict twice for the same run.`, `Please make the rubric of the judge more exact.` |
| `flaky-checks` | `The check of the station gives a different result when it runs twice on the same change.`, `Please fix the check of the station.` |

A person who requested a candidate of a search gets one of these, addressed
to them alone, when none of their candidates became the pull request. Each
ends with one point for each candidate the person requested, below.

| When | Form | Headline | Points |
| --- | --- | --- | --- |
| The search picked no candidate | `ended` | `Spotlight did not open a config pull request for the <station> station` | Why, by `reason`, below. |
| The search picked another candidate | `ended` | `Spotlight opened a config pull request for another candidate of the <station> station` | `Candidate <name> became the config pull request.` |
| The search stopped before a result, because search was turned off, the station left its line or the live config's replay failed | `ended` | `The search of the <station> station stopped before a result` | `A person turned off search for the station.`, `The station is no longer on the line.` or `The replay of the live config failed.` |

| `reason` | Point |
| --- | --- |
| `no-candidate` | `No candidate did better than the live config on the searched tasks.` |
| `no-held-out-gain` | `No candidate did better than the live config on the held-out tasks.` |
| `not-cheaper` | `No candidate cost less per run than the live config.` |
| `over-regression-limit` | `The best candidate failed more tasks than the regression limit of the line allows.` |
| `likely-overfit` | `The best candidate did better on the searched tasks only, not on the held-out tasks.` |
| `station-gone` | `The station is no longer on the line.` |
| `pull-request-open` | `A config pull request for the station is open.` |
| `rejected-before` | `A person closed a config pull request with the same config before.` |

A requested candidate's point reads:

| Its replay | Point |
| --- | --- |
| Not started before the search ended | `Spotlight did not replay <name>: the search ended first.` |
| Not finished before the search ended | `Spotlight did not finish the replay of <name>: the search ended first.` |
| Stopped at the search's ceiling | `The replay of <name> stopped at the search ceiling.` |
| Stopped or deleted | `The replay of <name> failed.` |
| Finished, with a held-out score | `Candidate <name>, held-out gain: <gain> points`, or for a search that aims for the same success for less, `Candidate <name>, cost per run: <cost> <currency>, compared with <cost> <currency> for the live config` |
| Finished, with no held-out score | `Candidate <name> did not beat the live config on the searched tasks. Searched gain: <gain> points`, or `Searched gain: not measured` |

A search that nobody requested a candidate of, and that ends with no pull
request and no causes to fix, a merged pull request and a pull request
Spotlight closes as stale send no notice.
