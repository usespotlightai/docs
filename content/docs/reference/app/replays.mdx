A [replay](/docs/reference/glossary#replay) runs a work station's past task
runs again under a [candidate](/docs/reference/glossary#candidate) config,
and scores each one. Spotlight keeps one replay set for each work station and
[refreshes it](#how-spotlight-keeps-the-set) from the station's runs.
Spotlight starts every replay itself: for a
[search](/docs/reference/app/searches), for a
[replay check](/docs/reference/api/replay-checks) of a planned change, and for
the set's [replay with the answer](#replay-with-the-answer). See
[How Spotlight improves a station](/docs/improvement/how-spotlight-improves-a-station#the-replay-set-spotlight-keeps).

The app has no page for a replay set, a replay or a replay run. The results
show task by task in the [config pull request](/docs/reference/app/searches#the-pull-request)
that a search opens and in the output of
[`spotlight replay check`](/docs/reference/cli/replay-command#spotlight-replay-check).
The replayed candidates show under
[Candidates](/docs/reference/app/insights#candidates) on the Insights
Stations tab.

## What a set is made of

A set holds past task runs of its station, one run of each task. How each
original run turned out decides which runs a
[refresh](#how-spotlight-keeps-the-set) adds.

### Outcomes

How an original run turned out comes from the first thing a person did on its
task after it, other than answering an approval, and from how it ended. The
first row that applies decides.

| Outcome | The run |
| --- | --- |
| Accepted | A person then closed the task. |
| Sent back | A person then sent the task back. |
| Failed | The run ended `failed`. A superseded run, or one that ended another way, goes on to the next rows. |
| Asked a person | A person then answered it, it ended asking a person, or a person approved or dismissed a tool call it asked approval for. |
| Other | None of the above, such as a run no person has acted on since. |

When people did two things on the task at the same moment, the first of
sending back, closing, answering, parking and starting counts.

## How Spotlight keeps the set

Spotlight creates a work station's replay set, empty, when a run of the
station first ends, and keeps that one set for the station's life. Nobody
creates, renames or deletes a set, or adds or removes its runs.

A refresh reads the station's 100 newest ended task runs and changes the set:

| Change | Which runs |
| --- | --- |
| Takes out | Runs in the set that ended more than 90 days ago, and runs of a task that a search's [reflection](/docs/reference/app/searches#reflections) blamed on the task itself, unless a later reflection gave the task another cause. |
| Adds | Up to 30 runs in the set in all: the newest run of each task that has no run in the set, among the runs that can be replayed and ended within 90 days. A task that a reflection blamed on the task itself is not added. |

Runs are added one at a time: the outcome among "Accepted", "Sent back",
"Asked a person" and "Failed" that the set, with the runs added so far, has
fewest of, that some run left has, and that occurs fewer times than the most
common outcome, "Other" included. Ties go to "Accepted", then "Sent back",
"Asked a person" and "Failed". The newest run left of that outcome is added.
With no such outcome, the newest run left is added. See [Outcomes](#outcomes).

| A refresh runs | When |
| --- | --- |
| On a schedule | 7 days after the last refresh for a set of 30 runs, and 1 day after it for a set of fewer. A set never refreshed is refreshed at once. |
| Before a search | Each time Spotlight starts a search of the set. |

A refresh does not run while the set is in use: while a replay of it is
queued or running, while a search of it is in progress, or while a
[replay check](/docs/reference/api/replay-checks) waits for its baseline. A
replay check does not refresh the set. A set whose station has left its line
is not refreshed.

## Results

Each task of a replay has a result on each side, the live config and the
candidate, with a one-line reason. The config pull request and
`spotlight replay check` show them as `<result>: <reason>`:

| Result | Shown | Meaning |
| --- | --- | --- |
| `succeeded` | `Succeeded` | Every repeat of the task was scored and succeeded. |
| `failed` | `Failed` | Every repeat was scored and failed. |
| `mixed` | `Succeeded <n>%` | Some scored repeats succeeded and some failed; `<n>` is the share that succeeded. |
| `unscored` | `Not scored` | No repeat could be scored. |
| `pending` | `Running` | A repeat has not ended, or its checks or judging have not finished. |
| `absent` | `Not replayed` | The task was not replayed on that side. |

A repeat fails when the run failed with `exited`, `refused`, `timed-out` or no
failure code, asked a person, or failed a check or the judge. A repeat is
unscored when nothing could score it: it could not be replayed or started, its
replay stopped or reached its ceiling first, its checks or judging could not
give an answer, nothing scores the station, or it failed before the agent
began or for another reason outside the candidate. Unscored and pending
repeats never count against the candidate.

A run is scored by the candidate's own station block:

| Scored by | When | Passes |
| --- | --- | --- |
| Its checks | The block sets `diffs: true` and a `check`. | The check passes on every layer of the run's change stack. |
| Its judge | The block has a `judge`. Every replay run is judged, whatever the judge's `sample`. | `Yes`, 4 or more on a 1 to 5 rubric, or at least the judge's `passThreshold` of its claims met. |

With both, a run must pass both. When a person closed the original run's task
as the first thing they did on it after the run, the judge is also given the
original's change, and scores the replay against it. A replay's judge score is
not a run's
[judge score](/docs/reference/app/tasks-runs-and-the-inbox#judge-score): it
counts in no agreement, alert or Insights figure of the team's runs.

The reason is the first reason of a repeat that shows the result: a repeat
that succeeded for `succeeded`, one that failed for `failed` and `mixed`, and
one that went unscored for `unscored`. It reads `<reason>.`, or
`<reason>: <detail>.` where there is a detail, cut at 200 characters:

| Code | Reason | Detail |
| --- | --- | --- |
| `unreplayable` | `Spotlight could not replay or start the run` | [Why](#why-a-run-cannot-be-replayed) |
| `not-run` | `The run did not start` | [Why](#why-a-run-cannot-be-replayed) |
| `run-failed` | `The run failed` | Its [failure](#run-failures) |
| `run-stopped` | `The replay stopped before the run finished` | |
| `asked-a-person` | `The run asked a person, and a replay cannot answer` | |
| `check-failed` | `Checks failed` | The layer that failed |
| `check-skipped` | `Checks could not run` | [The skip](#check-skips) |
| `change-not-generated` | `Spotlight could not make the change` | [The skip](#check-skips) |
| `no-change` | `The run changed no files for the checks` | |
| `no-change-stack` | `The change did not get to Spotlight` | |
| `judged` | `Judge passed it` | The judge's reason |
| `judge-failed` | `Judge failed it` | The judge's reason |
| `unjudged` | `Judge could not judge it` | [Why](#judging-failures) |
| `nothing-judges` | `No check or judge scores this station` | |

Without a reason to show, the side reads `Checks passed.`, `The run failed.`,
`The repeats did not agree.`, `Nothing scored the run.`, `The replay has not
finished.` or `Not replayed.`, by result.

When a replay stops, or reaches its ceiling, before a run that finished could
be judged, that run is unscored with `Judge could not judge it: the replay
stopped before judging.` In a replay that [calibrates the set](#calibration),
changes are judged and checked a second time; the second answer never changes
a result.

### Run failures

| Failure | Detail | Result |
| --- | --- | --- |
| `exited` | `the agent stopped with an error` | Failed |
| `refused` | `the config is not allowed in a replay` | Failed |
| none | | Failed |
| `unprepared` | `the workspace setup failed before the agent started` | Unscored |
| `unprovisioned` | `no runner was available` | Unscored |
| `hooks-unanswered` | `hooks did not answer` | Unscored |
| `runner-lost` | `Spotlight lost the runner` | Unscored |
| `timed-out` | `the run went over the time limit of the host` | Failed |
| `cancelled` | `the run was cancelled before a runner claimed it` | Unscored |
| `superseded` | `a newer run replaced it` | Unscored |

A config is `refused` when it has no harness profile, or uses tools, MCP
servers or secrets that replays don't get. An exhausted run with no failure
code is unscored. A failure code Spotlight does not know shows as the detail
as it is. When an attempt is queued again, as after `timed-out`, its cost is
not part of the run's cost: only the run's last attempt, and attempts
suspended on the way, add to the replay's spend.

### Check skips

| Code | Detail |
| --- | --- |
| `no-base` | `the starting commit is missing` |
| `no-checkout` | `the checkout is missing` |
| `checkout-failed` | `the checkout failed` |
| `setup-failed` | `the repository setup failed` |
| `workspace-failed` | `the runner could not open a workspace` |
| `out-of-time` | `the checks ran out of time` |
| `no-image` | `the check image is missing` |
| `provision-failed` | `no runner was available for the check` |
| `queue-timeout` | `no runner claimed the check in time` |
| `skipped` | `the checks were skipped` |
| `not-generated` | `the change was not made` |
| `no-check-asked` | `the candidate has no check command`. When the candidate has a check but no change stack ended passed, failed, skipped or not generated. |

A replay's checks run as a station's checks do. See
[Checks](/docs/reference/app/change-stacks-and-decisions#checks).

### Judging failures

| Code | Detail |
| --- | --- |
| `unavailable` | `no judge model was available` |
| `unreadable-rubric` | `the rubric could not be read`. Also when the replay's candidate is gone or has no judge. |
| `no-evidence` | `there was nothing to judge` |
| `request-failed` | `the judge request failed` |
| `unreadable` | `the answer of the judge could not be read` |
| `ungrounded` | `the judge cited nothing that the run did` |
| `errored` | `judging failed` |
| `interrupted` | `judging was interrupted` |
| `stopped-before-judging` | `the replay stopped before judging` |

### Guidance

The first time the judge judges a replay run, it also gives the `guidance`
field: one sentence of at most 280 characters that says what the run should do
differently to do the task well, in terms of the task. Spotlight keeps the
`guidance` field only when the judge failed the run. Only a search's agent
reads it, in the replay run's `result.json` from
[`spotlight history`](/docs/reference/cli/agent-commands#in-a-searchs-run).
That file never includes the judge's reasons.

Spotlight drops the `guidance` field when it:

- is more than 280 characters, or contains a line break;
- names a claim by its number or place, as in `claim 2`, `#3` or `the first
  claim`;
- repeats 5 or more words in a row from the rubric or from a claim, ignoring
  case and punctuation;
- contains a whole sentence of 3 or more words from the rubric or from a
  claim, ignoring case and punctuation. The text between two line breaks
  counts as a sentence too.

These judgings give no `guidance` field: the second judging of a change when a
replay [calibrates the set](#calibration), a run's own
[judging](/docs/reference/app/tasks-runs-and-the-inbox#judge-score), and
[side-by-side](#side-by-side) judging.

### Success

A replay's success is worked out task by task, a task being one run of the
set. A task's success is the share of its scored repeats that succeeded: `1` or
`0` with one repeat, and `2/3` when 2 of 3 repeats succeeded. The replay's
success is the average over the tasks with a scored repeat.

Beside it is its range: the 95% interval of the average, from 2,000 resamples
of the scored tasks. Reading the same results again gives the same range.

### Gains

A replay compared with another, its [reference replay](#reference-replays),
has a gain over it: on each task both scored, its success less the reference
replay's, averaged, in points, with the 95% interval of that average from the
same resampling of those tasks.

| Significance | When |
| --- | --- |
| `better` | The whole interval is above 0, and the gain is at least `min_gain`. |
| `worse` | The whole interval is below 0, and the loss is at least `min_gain`. |
| `within-noise` | Anything else, and always when fewer than 5 tasks were scored on both sides. |

`min_gain` is the line's [`replay_check.min_gain`](/docs/reference/terraform/line#replay-check-fields),
or 0.05 when the line has no `replay_check`. A replay reads it from the line
as it is now; a [replay check](/docs/reference/api/replay-checks) keeps the
one it started under.

## Side by side

A replay whose candidate has a judge, and that keeps a
[reference replay](#reference-replays) to set its changes beside, is set beside
it, task by task, once the replay has finished. Baselines and replays with the
answer are never set side by side, nor is a replay that was stopped or reached
its ceiling. Each repeat of a task is set beside the reference replay's repeat
with the same number, or else its first repeat, when all of these are true:

- Both runs completed with a change of at least one line, and have their
  result.
- People accepted the original run's change: the first thing a person did on
  its task after it was closing the task.
- Both replays are judged under the same rubric version.
- The ceiling has room. Each pair is tried at most twice, and before each
  request, Spotlight sets aside four times what judging the repeat's own
  change cost, two passes for each of two attempts, on top of what the replay
  has spent and what its pairs still being judged have set aside. When that
  first judging cost nothing, nothing is set aside. A repeat that would pass
  the ceiling is not requested.

The judge is given the rubric, the claims or both of the replay's own
candidate, the task's title and description, the two changes as hunks labelled
A and B, and the accepted change, which is neither. The changes are cut at
60,000 characters, and each hunk at 200 lines. It is not told which change is
the replay's. It answers `A`, `B` or a tie, with 1 to 5 reasons, each citing 1
to 10 hunks of A or B and never of the accepted change. It judges the pair in
two passes: once in an order drawn from the two runs, and once the other way
round. When the two passes name the same change, or both a tie, that is the
outcome; otherwise the outcome is a tie. Reasons that cite no hunk, or cite
the accepted change, are dropped, and a pass is `ungrounded` when half its
reasons or fewer remain. The replay's change winning is a win, the reference
replay's a loss. At most 4 pairs are judged at once, and a pair whose judging
fails is tried once more at most; one that failed `no-evidence`,
`interrupted` or `unavailable` is not tried again.

A task with repeats is a win when more of its compared repeats won than lost, a
loss when more lost, and a tie otherwise. The replay's wins, losses and ties
count tasks with at least one compared repeat. They never change a run's
result, the replay's success, its gain or its regressions. The config pull
request gives them for the searched and the held-out tasks.

What side-by-side judging spends counts against the replay's ceiling, but does
not add to its spend totals or its cost per run.

## Health

A set's health says whether the set can tell a better config from a worse one.
Spotlight reads it for the station's live config as it is now: only replays of
the live config at the station's current
[config fingerprint](/docs/reference/glossary#config-fingerprint) count, other
than a search's, unless that search's replay of the live config
[calibrated the set](#calibration). Before Spotlight starts a search, it reads
the health, and [skips the search](/docs/reference/app/searches#skip-reasons)
when a check found a problem. A check not yet measured stops no search.

| Check | Read from | Problem | Skip reason |
| --- | --- | --- | --- |
| [Noise](#noise) | The newest finished replay of the live config that replayed each run 2 or more times. | The spread is more than `min_gain` allows at the search's repeats. | `noisy` |
| [Room to improve](#room-to-improve) | The newest finished [replay with the answer](#replay-with-the-answer) of the live config, against the live replay that started it. | The answer does not do clearly better. | `no-headroom` |
| Judge agreeing with itself | The newest finished replay of the live config over every run of the set that [calibrated the set](#calibration). | The judge passed or failed the same change alike less than 80% of the time. | `judge-unstable` |
| Flaky checks | The same replay. | The check passed once and failed once on at least one change. | `flaky-checks` |

The live config's success over the whole set also decides a search's
[aim](/docs/reference/app/searches#aims): above 95%, a search aims for the
same success for less, unless the station's `objective` says otherwise.

### Noise

The spread is the highest repeat's success rate less the lowest's, a repeat's
rate being the share of its scored runs that succeeded. The repeats a search
needs are the spread divided by `min_gain`, squared and rounded up. A search
with fewer repeats than that is skipped as `noisy`. The config pull request
gives the spread under "About this search", or says Spotlight has not measured
the noise yet.

### Room to improve

Spotlight measures room to improve with the [replay with the
answer](#replay-with-the-answer). When its gain over the live replay that
started it reads `better`, the set has room. When it reads `within-noise` or
`worse`, the set has none, and a search is skipped as `no-headroom`. With
fewer than 5 tasks scored on both sides, or before the replay with the answer
has finished, room to improve is not measured.

### Replay with the answer

After a replay of the live config over every run of the set finishes, other
than a search's that does not [calibrate the set](#calibration), Spotlight
starts a replay of the same live config with each run's answer, when:

- the station still runs that config, at the same
  [config fingerprint](/docs/reference/glossary#config-fingerprint);
- the station has not left its line;
- at least one of the set's original runs was "Accepted" or "Sent back" (see
  [Outcomes](#outcomes));
- the set has no replay with the answer of that config that is queued,
  running or finished.

Nobody starts it. Its candidate is named `With the answer, <date>`. It replays
only the set's runs whose original was "Accepted" or "Sent back", among the
runs that live replay replayed and that are still in the set, with the repeats
and a ceiling of its own equal to those of the live replay whose finishing
started it. Its [reference replay](#reference-replays) is that live replay.

Each replay run's briefing ends with a section headed `## The answer`:

| Original | The answer |
| --- | --- |
| Accepted | `People accepted this change for the task. Make the same change.`, then the original run's change as a diff. |
| Sent back | `A person sent an earlier attempt at this task back and said:`, then what people wrote on the task after the run, up to the task's next run, each quoted, then `Do the task so that it meets what they requested.` |

Which kind of answer each run gets is fixed when the replay starts; a run
whose original change has no hunks, or whose sending back came with no words,
is left out. The hunks and people's words are read again when each run is
queued, and the answer is cut at 60,000 characters. If a run's answer is gone
by then, the run is not replayed (`answer-gone`). If the station's config
changes while it is queued or running, Spotlight stops it.

### Calibration

A calibration is a replay of the live config over the whole set that also
measures the set's noise, the judge's agreement with itself and flaky checks.
The first search on a set calibrates it in its replay of the live config, when
both are true:

- the set contains 5 runs or more;
- no replay of the live config at its current
  [config fingerprint](/docs/reference/glossary#config-fingerprint) has
  calibrated the set as it is now, every run of it, or is calibrating it,
  while queued, running or finished.

So the first search on a new set, on a set a refresh changed, and after a
change to the station's config, calibrates the set. The baseline of a
[replay check](/docs/reference/api/replay-checks) never calibrates the set.

The calibration replays each run 3 times, or the search's repeats when more.
Its ceiling comes out of the search's ceiling, which also keeps room for the
[replay with the answer](#replay-with-the-answer) that follows it. Once it
finishes, every change whose check passed or failed is checked a second time,
and every change the judge gave a verdict on is judged a second time. Each
change is weighed on its own, in order: it is judged again when what its first
judging cost still fits under the ceiling, on top of what is spent and set
aside so far. A second judging or check never changes a run's result. Its
finishing then starts the replay with the answer.

A search that calibrates the set starts before the set's health is measured,
so the health checks apply from the next search.

## Reference replays

A replay's reference replay is the replay of the set it is compared with. Its
task-by-task results and its gain are measured against it.

| Replay | Reference replay |
| --- | --- |
| A search's replay of a candidate, on the searched or the held-out tasks | The search's replay of the live config it started from. |
| A [replay check](/docs/reference/api/replay-checks) of a planned change | The baseline that starts beside it, else the set's current baseline that covers its runs with at least as many repeats. |
| A [replay with the answer](#replay-with-the-answer) | The replay of the live config whose finishing started it. |

The first two also set their changes [side by side](#side-by-side) with it. A
replay whose reference replay is gone is compared with nothing. A baseline has
no reference replay. A baseline that was stopped or reached its ceiling is not
compared with, and the next replay check of the set starts a new one.

## Regressions

A task regressed when the reference replay's [success](#success) on it is higher
than this replay's by more than 50 points (0.5), or when this replay's judge
score, averaged over its repeats, is more than 0.01 below the reference
replay's. With one repeat each, that is the reference replay succeeding and
this replay failing. Either is enough: a task whose repeats all succeeded still
regresses when its judge score is lower. A task can regress only once every
repeat of it, on both sides, has ended and has its result. A repeat that has
neither a scored result nor a judge's verdict cannot make a task regress.

Judge scores are compared only when both runs were judged, under the same
rubric version, either both or neither against the original's accepted change,
and on the same scale.

## Why a run cannot be replayed

A refresh adds only runs that can be replayed. A run that cannot be replayed
when its replay comes to start it is unscored, with the reason `Spotlight could
not replay or start the run: <why>.`, or `The run did not start: <why>.` when
it never started:

| Code | Why |
| --- | --- |
| `unknown-run` | `the run does not exist` |
| `not-a-task-run` | `the run has no task` |
| `task-gone` | `the task was deleted` |
| `still-running` | `the run has not ended` |
| `no-starting-point` | `the run recorded no starting point` |
| `no-briefing` | `the task briefing was not kept` |
| `archive-gone` | `the starting workspace is gone` |
| `attachments-gone` | `the briefing files are gone` |
| `answer-gone` | `the answer is gone` |
| `repository-gone` | `the repository is not on the line` |
| `not-at-the-station` | `the run was not at this station` |
| `candidate-unfit` | `the candidate cannot run it` |
| `cannot-start` | `the run could not start` |
| `unchecked` | `Spotlight could not check it` |
| `cancelled` | `the run did not start` |
| `dispatch-failed` | `the run did not start after several tries` |

`candidate-unfit` means the candidate was removed, or its block no longer fits
the line as it is now. `cannot-start` means the candidate's station runs no
harness a runner can start. `dispatch-failed` follows 10 failed attempts to
queue the run.

A workspace archive is kept for at least 30 days after the latest run that
started from it, and while a run that started from it is in a replay set. Once
the run's task is deleted, the replay set no longer keeps it. See
[Workspace archives](/docs/reference/limits-and-timeouts#workspace-archives).

## Spend and ceiling

A replay's spend is the cost of its runs, every repeat included, of generating
their change stacks and of judging them, counted in the ceiling's currency. A
generation or judging attempt that failed counts what it was billed. A cost in
another currency is summed apart and does not count against the ceiling. A run
whose cost was never reported counts at a fixed amount per run against the
ceiling. Side-by-side judging counts against the ceiling, but does not add to
the spend; see [Side by side](#side-by-side). Each replay has its own
ceiling: a search divides its ceiling among its replays (see
[Spend and ceiling](/docs/reference/app/searches#spend-and-ceiling)), and a
replay check takes the line's `replay_check.ceiling`. The second judgings of a
[calibration](#calibration) count against its ceiling, but not in its success
or in what its runs cost.

Once a replay's spend reaches its ceiling, it ends as `ceiling-reached`: nothing
more of it starts, its runs not yet started are cancelled, and its runs already
running finish. What they spend still counts, so a replay can end above its
ceiling.

## Replay runs

Replay runs and a search's agent runs do not show in the app: a Run page at
their id reads `This team has no such run.` A replay run differs from a task
run:

| | Replay run |
| --- | --- |
| Task | Has no task. The task's state, notes, board and inbox do not change. |
| Workspace | The exact archive the original run restored, or none if it restored none. A replay that cannot restore it fails. |
| Checkouts | Each repository at the commit the original run started from. |
| Briefing | The task as briefed to the original run, with its notes, attachments and decisions then. The memories it was briefed with are looked up again when the replay run is queued: a memory deleted since is left out, and each one reads as it is now. `spotlight history` and `spotlight recall` read as of the original run's start. A [replay with the answer](#replay-with-the-answer) adds the answer. |
| Agent commands | `spotlight trace`, `spotlight remember` and replies to a pull request's review comments are not allowed. |
| Git | Fetch only. A push fails with `this run may only fetch`. |
| Tools, MCP servers, secrets | None. |
| Hooks | None run for it. |
| Asking a person | Ends the run, counted as asked. Handing the task to a person, or to nowhere, does the same. |
| Change stack | Generated when the candidate sets `diffs: true`, checked, and never sent to GitHub. |
| Archive | None is archived for a later run. |
| Outcomes | Not recorded among the station's outcomes or in the Insights figures of the team's runs. No memories are drafted. |
| Priority | Below every task run and chat run. At most 2 of a team's replay runs, other than a search's, are queued or running at once. A search's replay runs keep to its own limit; see [Spend and ceiling](/docs/reference/app/searches#spend-and-ceiling). |
