A [replay](/docs/reference/glossary#replay) runs some of a work station's past
task runs again under a [candidate](/docs/reference/glossary#candidate) config,
and scores each one. The same data is read and written through the
[Replays API](/docs/reference/api/replays), candidates through the
[`replay-candidate`](/docs/reference/api/replay-candidate) resource, and both
from the [`spotlight replay`](/docs/reference/cli/replay-command) command.

Only people on the team, the workspace's owners and admins, and workspace
tokens with the `read` scope can read a team's replay sets, replays,
candidates and replay runs. Anyone else is answered `404`. Opening a set,
renaming or deleting it, adding or removing runs, starting or stopping a
replay, and proposing or deleting a candidate also need `plan`. See
[Team outcomes](/docs/reference/roles-and-permissions#team-outcomes).

## Station page

A work station's page has a "Replays" section, after "How its runs turned
out". It holds three parts.

| Part | Shows |
| --- | --- |
| Replay sets | One row per set of the station: its name, linked to the set's page, `<n> runs`, "Station gone" when its station has left the line, and its latest replay, as `Latest: <candidate>`, the replay's state, its [success](#success) against the baseline and its [side-by-side](#side-by-side) wins, losses and ties. A set never replayed reads "Not replayed yet". "Open a replay set" asks for a name, then opens the new set's page. With no sets, the part reads "No replay sets yet". |
| Candidates | One row per proposed candidate of the station, newest first: its name, its short [config fingerprint](/docs/reference/glossary#config-fingerprint), when it was proposed, and `Changed from live <fingerprint>:` with one phrase per change, as the Run page's [Config](/docs/reference/app/tasks-runs-and-the-inbox#config) words them. A candidate that changes nothing reads "The same as the live config when it was proposed." With none, the part reads "No candidates yet". The live snapshots Spotlight takes for baselines are not listed; they show as "Live config" on the replays that ran them. |
| Propose a candidate | The command that proposes one, with the station's address filled in, and "Copy command". |

To a person who may not read the team's replays, "Replay sets" reads "Only
the team's members can see its replays".

After "Replays" comes "Searches", the station's searches for a better config.
See [Searches](/docs/reference/app/searches#station-page).

## Replay set page

`/w/<slug>/team/<teamId>/lines/<lineId>/stations/<stationId>/replay-sets/<setId>`

The top bar holds the breadcrumbs, `<team> › <line> › <station> › Replay sets
› <set>`, where "Replay sets" opens the station's replay sets, and "Rename" and
"Delete" at its right. Under it, the heading shows the station's mark, the
set's name and `<n> runs · opened <when>`, with these pills:

| Pill | When | On hover |
| --- | --- | --- |
| Station gone | Its station has left its line. | `Station is gone from its line. The set starts no replays, takes no runs and keeps no workspaces.` |
| Frozen by a search | A search of the set is under way. | `A search of this set is underway. Its runs are frozen until the search ends or is stopped.` |

Then come four panels. Each is titled with an ⓘ that explains it on hover, and
holds its actions at its bottom left. A button that cannot be used is disabled
and gives the reason on hover.

| Panel | Shows | Can change |
| --- | --- | --- |
| Replays | One row per replay of the set, newest first, as Config, State, Success, Gain, Spent and Started. Config is the candidate's name, or "Live config", linked to the replay, with `Each run <n> times` when it replays each run more than once. State is its [state](#replay-states), with its note on hover. Success is its [success](#success), with `Likely range: <low>–<high>%` on hover, and a warning sign when some of its runs have no score yet. Gain is "Baseline" on the set's baseline, else its [gain](#gains) over the baseline in points, coloured by verdict, with the verdict and range, the baseline's success and its [side-by-side](#side-by-side) wins, losses and ties on hover. Spent is `<spent> of <ceiling>`. With none, it reads "Not replayed yet" and `Replay the live config first. It becomes the baseline.` | "Start a replay": see below. |
| Health | One row per reading of the set's [health](#health), as Reading and Result. | Nothing. |
| Runs | A bar of how the set's runs [turned out](#outcomes), then one row per run, as Run, State and Ended. Run is its task's title, linked to the run; a task since deleted reads "A deleted task". A run that [cannot be replayed](#why-a-run-cannot-be-replayed) carries a red warning sign, with the reason on hover. See [What a set is made of](#what-a-set-is-made-of). With none, it reads "No runs in this set". | "Add runs" opens the station's latest 50 ended task runs, each with "Add", "In the set" or "Can't be replayed" and the reason, after any runs [suggested to even the mix](#suggested-runs). The X that shows on a row's hover takes the run out of the set. "Add runs" is not offered once the station is gone. While a search of the set is under way, runs can be neither added nor taken out, and "Add runs" reads `Set is frozen while a search of it runs.` on hover. |
| Checks | The [checks](/docs/reference/app/searches#guarding-a-stations-changes) replayed on the set, as Change, Verdict, Regressions and When. A row opens its replay, and reads `attempt <n>` when the check was tried again. Its ⓘ explains `spotlight replay check` and gives the line's `replay_check` threshold. With none, it reads "No checks yet". | The "Guards config changes" switch, disabled once the station is gone. |

"Rename" asks for a new name; the set's runs and replays stay as they are.
"Delete", then "Delete set", deletes the set and its replays and their
results, and its runs' workspaces are no longer kept for it. Delete is
disabled while a replay of the set is queued or running, and while a search
of the set is under way, with `A replay or search
of this set is running. Delete it once that ends or is stopped.` on hover.

"Start a replay" is disabled with `Add runs to the set first.` on an empty set,
and with `Station is gone from its line.` once the station has left the line.
It opens a dialog:

| Field | Values |
| --- | --- |
| Replay under | "Live config", the station as it is configured now (the default), or one of the station's proposed candidates. |
| Repeats | How many times to replay each run, 1 to 5. `1` at first. |
| Ceiling | The most the replay may spend, every copy of each run included, above 0 and at most 1,000, and a three-letter currency, `USD` unless changed. |

With "Live config", the replay becomes the set's baseline when the set has
none yet, or becomes the new baseline when the set's runs changed since the
last one, or when the last one replayed each run fewer times than this one;
otherwise it replays beside the set's baseline. With a proposed candidate, a
baseline of the live config starts beside it when the set has none covering
all its runs with at least as many copies, with a ceiling of its own equal to
this one and the same repeats, so the two may spend up to twice the ceiling.
Either baseline may [check the set](#checking-the-set), with more repeats and
a larger ceiling. The dialog says which applies, adding `First baseline checks
the set: each run 3 times, ceiling ×3. Each change judged and checked twice.`
when the baseline will check the set.

"Start replay" opens the new replay's page. The dialog refuses a ceiling of 0
or less with `Please enter a ceiling above 0.`, more than 1,000 with `Maximum
ceiling: 1,000`, a currency that is not three letters with `Please enter a
three-letter currency code, like USD.`, and repeats out of bounds with `Please
enter a whole number from 1 to 5.`

## What a set is made of

The "Runs" panel reads the set's original runs as they stand when the page
loads.

| Part | Shows |
| --- | --- |
| Bar | How its runs turned out: the bar split by [outcome](#outcomes), then each outcome that occurs with its count. |
| ⓘ beside "Runs" | `Past runs of the station. Each replay reruns all of them.`, then when they ended, as `Ended between <when> and <when> · Median: <when>`, or `Ended <when>` when they all ended at the same moment, left out while no run's end can be read; then `Where their tasks came from:` with each [origin](#origins) and its count, the largest first, ties in alphabetical order. |
| Warning sign in the panel's header | With 6 runs or more, when one outcome other than "Other" covers more than two thirds of them. On hover: `<n> of <n> runs <outcome>. Add runs that turned out other ways to balance the set.`, the outcome read as "were accepted", "were sent back", "asked a person" or "failed". |

### Outcomes

How an original run turned out comes from the first thing a person did on its
task after it, and from how it ended. The first row that applies decides.

| Outcome | The run |
| --- | --- |
| Asked a person | A person granted or refused a tool call it asked approval for. |
| Accepted | A person then closed the task or approved it. |
| Sent back | A person then sent the task back or refused it. |
| Failed | The run failed. |
| Asked a person | A person then answered it, or it ended asking a person. |
| Other | None of the above, such as a run no person has acted on since. |

### Origins

Where a run's task came from is recorded when the task is opened.

| Origin | The task |
| --- | --- |
| A person | A person opened it at this station. |
| Another station | It was opened at another station and reached this one later, whoever opened it. |
| GitHub, Slack, Linear, or the integration's name | An integration opened it on something it heard. Tasks opened from `git` count as GitHub. |
| Unknown | Its run or task can no longer be read, as for a deleted task. |

### Suggested runs

Once the set holds runs, the "Add runs" dialog lists up to 5 runs first,
under "Suggested to even the mix", with `Recent runs with outcomes the set has
few of. Nothing is added until you add it.` Each shows its
[outcome](#outcomes) and "Add". None is ever added without it.

The suggestions come from the station's latest 50 ended task runs that can be
replayed, taking the newest run of each task and leaving out tasks with a run
in the set already. They are picked one at a time: the outcome among Accepted,
Sent back, Asked a person and Failed that the set, with the runs picked so
far, holds fewest of, and fewer of than its most common outcome. Ties go to
Accepted, then Sent back, Asked a person and Failed. The newest run of that
outcome is picked. Picking stops at 5, at the room left in the set below 50,
or when no outcome is short. "Other" is never suggested.

An empty set, a set whose station has left its line, and a set already even
get no suggestions, and the part is not shown. Suggested runs are not listed
again below it.

## Replay page

`/w/<slug>/team/<teamId>/lines/<lineId>/stations/<stationId>/replays/<replayId>`

To someone who may read the team's replays, an unknown replay, or one of
another station, reads "Replay not found". To anyone else, the page reads
"Only the team's members can see its replays".

The header shows the candidate's name, or "Live config", then
`Replays <set> · started <when> · config <fingerprint>` and, for a queued,
stopped or over-budget replay, its [state's note](#replay-states). The set's
baseline also reads `This is the set's baseline: the live config, which every
other replay of the set is compared against.` While the replay is queued or
running, "Stop", then "Stop replay", stops it. A replay with a
[counterpart](#counterparts) reads `Each task compared with <counterpart>.`,
linked to that replay.

| Label | Shows |
| --- | --- |
| Success | `<share> (<low>–<high>%) succeeded`, the [success](#success) with its range, or "No score yet". Beside it, the [gain](#gains) over its [counterpart](#counterparts), as in `+25 pts (+5 to +40) vs baseline 50% (35–65%) · Better`, or `· the baseline` on the baseline itself. Then, once any task was [set side by side](#side-by-side), `Side by side with <counterpart>: <n> wins, <n> losses, <n> ties`, the counterpart linked to its replay. The success's range, the verdict and the wins, losses and ties each carry a note on what they mean, which opens on hover or focus. |
| Scored | `<n> scored · <n> unscored`, then what scores the station: `by its checks and its judge`, `by its checks`, `by its judge`, or `nothing scores this station`. |
| Copies | `Each run <n> times`. Shown only when the replay replays each run more than once. |
| Spent | `<spent> of <ceiling>`, with a bar that fills as the ceiling is spent, and `Over the ceiling by <amount>` when runs already running took the replay past it, then "Runs", "Drafting" and "Judging" in the ceiling's currency, and "Side by side" once [side-by-side judging](#side-by-side) spent anything, with the note "Judging changes side by side counts against the ceiling, but not toward cost per run." "Also spent" sums what was spent in other currencies, one sum per currency. "Not priced" counts the runs whose cost was never reported and the drafting and judging model calls that came back with no price, as in `2 runs · 1 model call`. |

Under "Task by task", one row per task, regressions first, then in the set's
order. With a [counterpart](#counterparts) to compare with, named in the
column headers as it is shown, such as "The baseline":

| Column | Shows |
| --- | --- |
| Task | The task's title, linked to the original run, and "Regressed" when the task [regressed](#regressions). |
| This replay | The [result](#results), its first reason with a count of the rest, and "Run", linked to the replay run. With more than one copy, `<n> of <m> copies succeeded`, where `<m>` counts the scored copies, or "No copy scored yet", then each copy as `Copy <n>` and its result in the same form. |
| `<Counterpart>` | The counterpart's result on the task, in the same form. |
| Judge | The judge's score for this replay, `vs` the counterpart's, then the difference to two decimals, or why the two are [not compared](#score-comparisons). A score reads `Yes`, `No`, `<n>/5` or `<n> of <m> claims met`; with copies, each copy's score, joined by `·`, and the difference between the two sides' averages. |
| Closer to the accepted change | Which change the judge found better [side by side](#side-by-side): "This one", the counterpart, as in "The baseline", or "Neither", and `–` for a task not compared. Shown only once any task was compared. |
| `Cost vs <counterpart>` | This replay's run cost less the counterpart's, each averaged over its copies, once every copy of both has settled. |
| `Time vs <counterpart>` | This replay's run time less the counterpart's, averaged the same way. |

Without a counterpart, the columns are "Task", "Result", "Judge", "Closer to
the accepted change" once any task was compared, "Cost" and "Time", for this
replay alone, cost and time averaged over the copies. A value
not known reads `–`.

## Replay states

| State | Label | Note | Final |
| --- | --- | --- | --- |
| `queued` | Queued | Waiting for a runner | no |
| `running` | Running | | no |
| `finished` | Finished | | yes |
| `stopped` | Stopped | Stopped by a person; nothing more starts | yes |
| `over-budget` | Over budget | It spent its ceiling, so nothing more starts | yes |

A replay is `running` once its first run is queued, and `finished` once every
run has a result. A stopped replay starts no more runs, and its running runs
are stopped. An over-budget replay starts no more runs, and its runs already
running finish. A run that never started reads "It never
ran".

## Results

| Result | Meaning |
| --- | --- |
| Pending | The run has not ended, or its checks or judging have not finished. |
| Succeeded | The run ended and passed everything that scores the station. |
| Failed | The run failed with `exited`, `refused`, `timed-out` or no failure code, asked a person, or failed a check or the judge. Only a failed result can be a regression. |
| Unscored | Nothing could score the run: it could not be replayed or started, its replay stopped it or reached its ceiling first, its checks or judging could not give an answer, it failed before the agent began or for another reason outside the candidate, or Spotlight abandoned it (see [Run failures](#run-failures)). |

A run is scored by the candidate's own station block:

| Scored by | When | Passes |
| --- | --- | --- |
| Its checks | The block sets `diffs: true` and a `check`. | The check passes on every layer of the run's change stack. |
| Its judge | The block has a `judge`. Every replay run is judged, whatever the judge's `sample`. | `Yes`, 4 or more on a 1 to 5 rubric, or at least the judge's `passShare` of its claims met. |

With both, a run must pass both. When the original run's next person act was
Closed or Approved, the judge is also given the original's change, and scores
the replay against it. A replay's judge score is not a run's
[judge score](/docs/reference/app/tasks-runs-and-the-inbox#judge-score): it
counts toward no agreement, standing, alert or Insights figure of the team's
runs. It counts only toward the replay's [success](#success), which the
Insights [Candidates](/docs/reference/app/insights#candidates) tab shows.

Each result carries reasons, shown as `<reason>: <detail>` where there is a
detail:

| Code | Reason shown | Result |
| --- | --- | --- |
| `unreplayable` | It could not be replayed or started, with [the refusal](#why-a-run-cannot-be-replayed) | Unscored |
| `not-run` | It never ran | Unscored |
| `run-failed` | The run failed, with its [failure](#run-failures) | Failed or Unscored, by failure |
| `run-stopped` | Its replay was stopped, or reached its ceiling, before the run finished | Unscored |
| `asked-a-person` | It asked a person, which a replay cannot | Failed |
| `check-failed` | Its checks failed, with the layer that failed | Failed |
| `check-skipped` | Its checks could not run, with [the skip](#check-skips) | Unscored |
| `change-undrafted` | Its change could not be drafted | Unscored |
| `no-change` | It changed nothing for the checks to run on | Unscored |
| `no-change-stack` | It changed files, but its change never reached Spotlight | Unscored |
| `judged` | The judge passed it, with the judge's reason | Succeeded |
| `judge-failed` | The judge failed it, with the judge's reason | Failed |
| `unjudged` | The judge could not judge it, with [why](#judging-failures) | Unscored |
| `nothing-judges` | Neither checks nor a judge score this station | Unscored |

The judge's reasons cite the replay run's steps and the hunks of its change,
as a run's judge reasons do. On claims, each claim's mark and reasons are kept
with the claims as worded when it was judged.

### Run failures

A failed replay run is classified by its [failure code](/docs/reference/app/tasks-runs-and-the-inbox#failure-codes):

| Failure | Detail shown | Result |
| --- | --- | --- |
| `exited` | the agent exited with an error | Failed |
| `refused` | Spotlight would not start it as configured, as for a harness profile that is missing or tools, MCP servers or secrets a replay is not given | Failed |
| none | | Failed |
| `unprepared` | its workspace could not be made ready before the agent began, so it goes unscored | Unscored |
| `unprovisioned` | no runner could be provisioned, so it goes unscored | Unscored |
| `hooks-unanswered` | its hooks never answered, so it goes unscored | Unscored |
| `runner-lost` | the runner was lost, so it goes unscored | Unscored |
| `timed-out` | it kept running past its host's time limit | Failed |
| `superseded` | it was superseded, so it goes unscored | Unscored |

A run Spotlight gave up on as abandoned with no code is unscored. A `timed-out` attempt that is tried again still spends against the ceiling.
Only a failed result can be a regression.

### Check skips

| Code | Detail shown |
| --- | --- |
| `no-base` | its starting commit was missing |
| `no-checkout` | its checkout was missing |
| `checkout-failed` | its checkout failed |
| `setup-failed` | the repository's setup failed |
| `no-room` | there was no runner to check on |
| `out-of-time` | the checks ran out of time |
| `no-image` | the image to check in was missing |
| `unprovisioned` | no runner could be provisioned to check on |

| `skipped` | the checks were skipped |
| `undrafted` | its change was never drafted |
| `no-check-asked` | the candidate runs no check command |

### Judging failures

| Code | Detail shown |
| --- | --- |
| `unavailable` | no judge model was available |
| `unreadable-rubric` | the rubric could not be read |
| `no-evidence` | there was nothing to judge |
| `refused` | the judge declined |
| `unreadable` | the judge's answer could not be read |

| `interrupted` | judging was interrupted |

### Success

A replay's success is worked out task by task, a task being one run of the
set. A task's success is the share of its scored copies that succeeded: `1` or
`0` with one copy, and `2/3` when 2 of 3 copies succeeded. The replay's success
is the average over the tasks with a scored copy. Unscored and pending runs are
left out, so a run that could not be replayed or started, or that its replay
stopped, never counts against the candidate.

Beside it is its range: the 95% interval of the average, from 2,000 resamples
of the scored tasks, shown as `(<low>–<high>%)`. Reading the same results
again gives the same range.

### Gains

A replay with a [counterpart](#counterparts) reads its gain over it: on each
task both scored, its success less the counterpart's, averaged, in points, with
the 95% interval of that average from the same resampling of those tasks.

| Verdict | Shown | When |
| --- | --- | --- |
| `better` | Better | The whole interval is above 0, and the gain is at least `min_gain`. |
| `worse` | Worse | The whole interval is below 0, and the loss is at least `min_gain`. |
| `within-noise` | Within noise | Anything else, and always when fewer than 5 tasks were scored on both sides. |

`min_gain` is the line's [`replay_check.min_gain`](/docs/reference/terraform/line#replay-check-fields),
or 0.05 when the line has no `replay_check`. The app shows it as `+5 pts`. A
replay reads it from the line as it is now; a
[replay check](/docs/reference/api/replay-checks) keeps the one it started
under.

## Side by side

A replay whose candidate has a judge is set beside its
[counterpart](#counterparts), task by task, once the replay has finished. A
stopped or over-budget replay never finishes, so it is never set side by side.
Each copy of a task is set beside the counterpart's copy with the same number,
or else its first copy, when all of these hold:

- Both runs completed with a change of at least one line, and have their
  result.
- People accepted the original run's change: its next person act was Closed or
  Approved.
- Both replays are judged under the same rubric version. Otherwise the copy
  reads `other-rubric`.
- The ceiling has room. Each pair is tried at most twice, and before asking,
  Spotlight sets aside four times what judging the copy's own change cost, two
  readings for each of two attempts, on top of what the replay has spent and
  what its pairs still being judged have set aside. A copy that would pass the
  ceiling is not asked; once no pair is still being judged, it reads `budget`.

The judge is given the station's rubric, its claims or both, the task's title
and description, the two changes as hunks labelled A and B, and the accepted
change, which is neither. It is not told which change is the replay's. It
answers `A`, `B` or a tie, with 1 to 5 reasons, each citing 1 to 10 hunks of A
or B and never of the accepted change. It reads the pair twice: once in an
order drawn from the two runs, and once the other way round. When the two
readings name the same change, or both a tie, that is the outcome; otherwise
the outcome is a tie. The replay's change winning is a win, the counterpart's a
loss. At most 4 pairs are judged at once, and a pair whose judging fails is
tried once more at most.

A task with copies is a win when more of its compared copies won than lost, a
loss when more lost, and a tie otherwise. The replay's wins, losses and ties
count tasks with at least one compared copy. They never change a run's result,
the replay's success, its gain or its regressions.

Until it is judged, a copy reads "Not judged side by side yet: that happens
once the replay finishes." A copy not compared reads `Not judged side by side:
<reason>.`:

| Code | Reason shown |
| --- | --- |
| `unavailable` | no judge model was available |
| `unreadable-rubric` | the rubric could not be read |
| `no-evidence` | there was nothing to compare: either change, or the accepted change, has no hunks |
| `refused` | the judge declined |
| `unreadable` | the judge's answer could not be read |
| `ungrounded` | the judge cited nothing either change did |
| `errored` | judging went wrong |
| `interrupted` | judging was interrupted |
| `other-rubric` | its counterpart was judged by another version of the judge |
| `budget` | no room was left under the ceiling |

What side-by-side judging spends counts against the replay's ceiling, but not
toward its spend totals or its cost per run. The replay page shows it apart, as
"Side by side" under "Spent".

## Health

The "Health" panel of the set's page says whether the set can tell a better
config from a worse one. Its ⓘ reads `Whether this set can tell a better config
from a worse one. Measured by Spotlight: the first baseline of the live config
replays each run 3 times, then the live config is replayed handed each run's
answer. Sets of fewer than 5 runs are not checked.` It is read for the
station's live config as it is now: only replays of the live config at the
station's current [config fingerprint](/docs/reference/glossary#config-fingerprint)
count.

Each reading is a row: its label with an ⓘ that gives its advice on hover,
then what it found, and "View replay", which opens the replay it was read
from. A reading that found a problem is marked with a warning sign.

| Reading | Read from | Until then |
| --- | --- | --- |
| Noise | The newest finished replay of the live config that replayed each run 2 or more times. | "Not measured" |
| Room to improve | The newest [replay with the answer](#replay-with-the-answer) of the live config as it is now, once it has finished beside its live replay. Before that, the newest finished replay of the live config over every run of the set, other than a search's. | "Not measured" |
| Judge agreeing with itself | The newest finished replay of the live config over every run of the set that [checked the set](#checking-the-set). | "Not checked" |
| Flaky checks | The same replay. | "Not checked" |

### Noise

| Shows | Meaning |
| --- | --- |
| `Success moved <n> pts between <m> copies` | The spread: the highest copy's success rate less the lowest's. A copy's rate is the share of its scored runs that succeeded. Marked when the spread is more than `min_gain`, with the advice `One copy can't tell a real gain from chance. Search with more repeats per run, or raise the line's min_gain.` Otherwise the advice is `Noise is within the line's minimum real gain. A gain that size is unlikely to be chance.` Both end with `Minimum real gain: <min_gain>`. |
| `Each copy: <rate>, <rate>, …` | Each copy's success rate, in order. |
| `<n> tasks went both ways` | Tasks whose copies both succeeded and failed, or "No task went both ways". The tasks are listed under it. |
| `measured on config <fingerprint> <when>` | The fingerprint and when the replay ended. |

### Room to improve

Before any [replay with the answer](#replay-with-the-answer), or when one
finished but could not be compared, the reading comes from the live config's
success over the whole set:

| Shows | When |
| --- | --- |
| `The live config succeeds on <share>` | Its success over the whole set is 95% or less. |
| `Almost none: the live config succeeds on <share>`, marked, with the advice `No room for more success. Search for the same success at less cost, or add tasks the live config fails.` | Its success is above 95%. A [search](/docs/reference/app/searches#start-a-search) of the set then aims for the same success for less unless told otherwise. |

Once there is a replay with the answer, the reading comes from it, and "View
replay" opens it:

| Shows | When |
| --- | --- |
| "Measuring with the answer" | It is queued or running. |
| "Couldn't measure with the answer" | It, or the live replay it is compared with, was stopped or ran over its ceiling, or that live replay is gone. The next replay of the live config over the whole set starts another. |
| `Up to <gain> with the answer` | Its [gain](#gains) over its live replay reads Better. |
| `Little: <gain> with the answer`, marked | Its gain reads Within noise or Worse. The advice adds `Even the answer barely helps. Add tasks the live config fails, or search for the same success at less cost.` |

Once compared, the advice starts with `Live config: <share> on <n> runs. With
the answer: <share>.`, both read on the runs it replayed.

### Replay with the answer

After a replay of the live config over every run of the set finishes, other
than a search's, Spotlight starts a replay of the same live config handed each
run's answer, when:

- the station still runs that config, at the same
  [config fingerprint](/docs/reference/glossary#config-fingerprint);
- the station has not left its line;
- at least one of the set's original runs was Accepted or Sent back (see
  [Outcomes](#outcomes));
- the set has no replay with the answer of that config that is queued,
  running or finished.

Nobody starts it, and it cannot be started from the app or the API. Its
candidate is named `With the answer, <date>`, and it shows under "Replays"
like any other replay. It replays only the set's runs whose original was
Accepted or Sent back, with the repeats and a ceiling of its own equal to
those of the live replay whose finishing started it. That live replay is its
[counterpart](#counterparts), and both are read on the runs it replayed.

Each replay run's briefing ends with a section headed `## The answer`:

| Original | The answer |
| --- | --- |
| Accepted | `People accepted this change for the task. Make the same change.`, then the original run's change as a diff. |
| Sent back | `A person sent an earlier attempt at this task back and said:`, then what people wrote on the task after the run, up to the task's next run, each quoted, then `Do the task so that it meets what they asked for.` |

Each run's answer is fixed when the replay starts. A run whose original change
has no hunks, or whose sending back came with no words, is left out. If a
run's answer is gone by the time it would start, the run is not replayed and
reads `answer-gone` (see [Why a run cannot be replayed](#why-a-run-cannot-be-replayed)).
If the station's config changes while it is queued or running, Spotlight stops
it.

### Checking the set

Nobody starts a check, and it cannot be started from the app or the API. A
baseline of the live config checks the set when both hold:

- the set holds 5 runs or more;
- no replay of the live config at its current
  [config fingerprint](/docs/reference/glossary#config-fingerprint) over the
  whole set has checked it, or is checking it, while queued, running or
  finished.

This applies to a "Live config" replay that becomes the baseline, and to a
baseline that starts beside a proposed candidate. A search's replay of the
live config and the baseline of a
[replay check](/docs/reference/api/replay-checks) never check the set.

The checking baseline replays each run 3 times, or the repeats asked for when
more. Its ceiling grows in step: the ceiling asked for, times its repeats,
divided by the repeats asked for, and at most `1,000`. One repeat at `5.00`
becomes 3 repeats at `15.00`. Its 3 copies measure the set's [noise](#noise).

Once it finishes, every change whose check passed or failed is checked a
second time, and every change the judge gave a verdict on is judged a second
time. Changes are judged again in order while the ceiling still has
room for one more at what its first judging cost; the rest are not judged
again. A second judging or check never changes a run's result. Its finishing
then starts the [replay with the answer](#replay-with-the-answer), as any
replay of the live config over the whole set does.

Until a set is checked, its noise, judge and checks readings say `Measured by
the first baseline of the live config:`, then what it does, in their advice.

## Counterparts

A replay other than a baseline is
compared with one other replay of the set, its counterpart, chosen when it
starts and kept. Its task-by-task rows, its gain and its
[side-by-side](#side-by-side) comparisons all use the same counterpart.

| Replay | Counterpart |
| --- | --- |
| Under a proposed candidate or the live config | The baseline that starts beside it, else the set's baseline standing when it starts that covers its runs with at least as many copies, a finished one first. |
| A [replay with the answer](#replay-with-the-answer) | The replay of the live config whose finishing started it. |
| A search's replay of a candidate, on the searched or the held-out tasks | The search's replay of the live config it started from. |
| A [replay check](/docs/reference/api/replay-checks) of a planned change | The baseline that starts beside it, else the set's standing baseline, as for a proposed candidate. |

A replay with none is compared with the set's baseline: the newest replay of
the live config the set started as a baseline, while it is queued, running or
finished. A stopped or over-budget baseline is not compared with, and the next
replay of the set starts a new one.

The counterpart is shown as `the baseline` when it is the set's baseline now,
else as `the search's starting config` for a search's replay, `the live
config` for a [replay with the answer](#replay-with-the-answer), and `an
earlier baseline` for the others.

## Regressions

A task regressed when the counterpart's [success](#success) on it is more than
0.5 above this replay's, or when this replay's judge score, averaged over its
copies, is more than 0.01 below the counterpart's. With one copy each, that is
the counterpart succeeding and this replay failing. A task can regress only once
every copy of it, on both sides, has settled and has its result. An unscored
result is never a regression.

### Score comparisons

Judge scores are compared only when both runs were judged, under the same
rubric version, and either both or neither against the original's accepted
change. Otherwise the "Judge" column says why:

| Code | Shown |
| --- | --- |
| `unjudged` | One side was not judged |
| `other-rubric` | Judged by different rubrics |
| `other-reference` | Only one was judged against the accepted change |

## Why a run cannot be replayed

A run that cannot be replayed is refused when it is added to a set, with
`409`, and a run in a set that can no longer be replayed reads its refusal
on the set's page. A run refused when its replay comes to start it is
unscored, with `It could not be replayed or started: <refusal>`.

| Code | Shown |
| --- | --- |
| `unknown-run` | There is no such run |
| `not-a-task-run` | It worked no task of its own |
| `task-gone` | Its task was deleted |
| `still-running` | It has not ended yet |
| `no-starting-point` | It never recorded where it started |
| `no-briefing` | The task as it was briefed was never kept |
| `archive-gone` | The workspace it started from is no longer kept |
| `attachments-gone` | Files it was briefed with are gone |
| `answer-gone` | Its answer is gone |
| `repository-gone` | A repository it worked in has left the line |
| `not-at-the-station` | It did not run at this station |
| `candidate-unfit` | The candidate cannot run it |
| `cannot-start` | It could not be started |
| `unchecked` | It could not be checked just now |
| `forgone` | It was never started |
| `dispatch-failed` | It failed to start after several tries |

`not-at-the-station`, `repository-gone`, `candidate-unfit`, `cannot-start`,
`forgone` and `dispatch-failed` arise only when a replay comes to start the
run. `candidate-unfit` means the candidate was removed, or its block no longer
fits the line as it is now. `cannot-start` means the candidate's station runs
no harness a runner can start. `dispatch-failed` follows 10 failed attempts to
queue the run. `unchecked` means Spotlight could not read the run's facts at
that moment; it may clear on its own.

A run keeps the workspace archive it started from for 30 days after it
started, and for as long as it is in a replay set. See
[Workspace archives](/docs/reference/limits-and-timeouts#workspace-archives).

## Spend and ceiling

A replay's spend is the cost of its runs, every copy included, of drafting their change stacks and of
judging them, counted in the ceiling's currency. A drafting or judging attempt
that failed counts what it was billed. A cost in another currency is summed
apart and does not count toward the ceiling, nor does a cost that was never
reported. Side-by-side judging counts against the ceiling, but not toward
the spend; see [Side by side](#side-by-side). Each replay has its own ceiling. A baseline started beside a replay has a ceiling of its own, equal to
the replay's. The second judgings of a baseline that [checks the set](#checking-the-set)
count against its ceiling, but not toward its success or what its runs cost.

Once a replay's spend reaches its ceiling, it ends as `over-budget`: nothing
more of it starts, its runs not yet started are withdrawn, and its runs already
running finish. What they spend still counts, so a replay can end above its
ceiling. The replay page then reads `Over the ceiling by <amount>`, and
`spotlight replay status` adds `over the ceiling by <amount>`.

## Replay runs

A replay run's Run page opens at `/w/<slug>/team/<teamId>/runs/<runId>`, like
any run, from "Run" on the replay page. Its breadcrumb ends with the original
run's task title and `Replay at <station>`. It shows:

- `A replay of <task title>`, linked to the original run;
- `Under <candidate> in a replay of <set>`, with `(the baseline)` for a
  baseline, linked to the replay page, and the run's result in it; for a
  search's replay, also `candidate <name> in its search`, or `the live config
  it started from in its search`, linked to the search;
- on claims, each claim with "Met" or "Not met" and its reasons, then the
  pass share, as on the Station page;
- once the run was asked to be [set side by side](#side-by-side), `Closer to
  the accepted change:` with "This one", "The other change" or "Neither", and
  "The other run", linked to the counterpart's run. Before it is judged: "Not
  judged side by side yet: that happens once the replay finishes." When the two readings disagreed: "The judge read the
  two changes both ways round and picked a different one depending on which it
  saw first, so this counts as a tie." Under "Both readings", `With this change
  shown first:` and `With the other change shown first:`, each with its
  outcome and reasons, as in `Cites 2 hunks of this change and 1 hunk of the
  other`;
- the run's [config](/docs/reference/app/tasks-runs-and-the-inbox#config) and
  [spend](/docs/reference/app/tasks-runs-and-the-inbox#spend), and its steps.

In place of the message box: `A replay runs on its own. Nobody can talk to it,
and nothing it does reaches the task.` A replay run can be read, with its
config and its event stream, only by those who may read the team it replayed
for, recorded when it was queued, even after its station is removed. Anyone
else is answered `404`, and the page reads `There is no such run for this team.`

A replay run differs from a task run:

| | Replay run |
| --- | --- |
| Task | Holds no task. The task's state, notes, board and inbox do not change. |
| Workspace | The exact archive the original run restored, or none if it restored none. A replay that cannot restore it fails. |
| Checkouts | Each repository at the commit the original run started from. |
| Briefing | The task as briefed to the original run, with its notes, attachments and decisions then, and the memories it was briefed with. `spotlight history` and `spotlight recall` read as of the original run's start. A [replay with the answer](#replay-with-the-answer) adds the answer. |
| Git | Fetch only. A push is refused with `this run may only fetch`. |
| Tools, MCP servers, secrets | None. |
| Hooks | None run for it. |
| Asking a person | Ends the run, counted as asked. Handing the task to a person, or to nowhere, does the same. |
| Change stack | Drafted when the candidate sets `diffs: true`, checked, and never sent to GitHub. |
| Archive | None is kept for a later run. |
| Outcomes | Not recorded among the station's outcomes or in the Insights figures of the team's runs; its replay shows on the Insights [Candidates](/docs/reference/app/insights#candidates) tab. No memories are drafted. |
| Priority | Below every task run and chat run. At most 2 of a team's replay runs, other than a search's, are queued or running at once. A search's replay runs are held to its own limit; see [Spend and ceiling](/docs/reference/app/searches#spend-and-ceiling). |

See [Inside a sandbox](/docs/reference/hosts/sandbox) for the phases every
run goes through.
