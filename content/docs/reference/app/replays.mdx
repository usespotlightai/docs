A [replay](/docs/reference/glossary#replay) runs some of a work station's past
task runs again under a [candidate](/docs/reference/glossary#candidate) config,
and scores each one. The same data is read and written through the
[Replays API](/docs/reference/api/replays), candidates through the
[`replay-candidate`](/docs/reference/api/replay-candidate) resource, and both
from the [`spotlight replay`](/docs/reference/cli/replay-command) command.

Only people on the team, the workspace's owners and admins, and workspace
tokens with the `read` scope can read a team's replay sets, replays,
candidates and replay runs. Anyone else is answered `404`. Opening a set,
renaming or deleting it, adding or removing runs, starting or stopping a
replay, and proposing or deleting a candidate also need `plan`. See
[Team outcomes](/docs/reference/roles-and-permissions#team-outcomes).

## Station page

A work station's "Improve" tab, `…/stations/<stationId>/improve`, has a
"Replay sets" card under "Try a change", at `#replays`. It lists the station's
replay sets, one row each:

| Column | Shows |
| --- | --- |
| Set | The set's name, linked to the set's page, and "Station gone" when its station has left the line. |
| Runs | How many runs the set holds. |
| Latest replay | The latest replay's [success](#success) as `<share> succeeded`, or `No score yet`, and its [state](#replay-states). Hovering over the success shows the replay's candidate, or "Live config", and its [success line](#success-line). A set never replayed reads "Not replayed yet". |

"Create a replay set" asks for a name, then opens the new set's page. With no
sets, the card reads "No replay sets yet" and
`A replay set holds past runs to replay under a candidate. Create one to start comparing.`,
with "Create a replay set". To a person who may not read the team's replays,
the card reads `Only team members can see its replays`.

### Success line

The success line reads the replay's success with its range, as in
`40% (20–60%) succeeded`, or `No score yet`, then:

| Replay | Then |
| --- | --- |
| The set's baseline | `· the baseline` |
| With a [gain](#gains) over its [counterpart](#counterparts) | The gain and its range, then `vs <counterpart> <share>`, then the verdict, as in `+10 pts (+2 to +18) vs live config 25% (10–40%) · Better`. |
| With a counterpart but no gain | `· <counterpart> <share>`, as in `· live config 25%`. |
| Compared with nothing | Nothing. |

`<counterpart>` is the counterpart's label in lower case: `baseline`,
`live config`, `search's starting config` or `earlier baseline`. `<share>` is
the counterpart's success on the tasks both replays scored, with its range
when known. Without that success, the label shows alone. Once any task was
[set side by side](#side-by-side), the line ends with
`· Side by side with <replay>: <n> wins, <n> losses, <n> ties`, `<replay>`
being the counterpart as [shown](#counterparts), as in `the baseline`.

deletes the set's replays and results. Spotlight stops keeping its runs'
starting workspaces. You can't undo this.`, with "Keep it" and "Delete set".
Delete is disabled while a replay of the set is queued or running, and while
a search of the set is running, with `A replay or search of this set is
running. Please delete the set after it ends.` on hover.

"Add runs" opens `Add runs to <set>`, `The station's latest ended runs.
Spotlight keeps a run's starting workspace while it's in the set.` It lists the
station's ended task runs, the 50 created most recently, newest first,
after any runs [suggested to even the mix](#suggested-runs). Runs that are no
longer in the workspace are left out after those 50 are read, so the list can
hold fewer. Each shows its title, its state, when it ended and, when it cannot
be replayed, the refusal, then "Add", "In the set" or "Can't be replayed".
"Add" reads "Adding…" while the run is added; when the server refuses it, the
dialog shows nothing, and the server's message shows in an error notice. With
no ended run, it reads `No ended runs to replay yet. Runs appear here once they
end.` While the suggestions load, the dialog shows a placeholder, and when they
cannot be read, `Suggested runs could not be loaded.` with "Try again". "Done"
closes it. A set holds at most 50 runs.

"Start a replay" is disabled with `Please add runs to the set first.` on an
empty set, and with `The station is gone from its line.` once the station has
left the line. It opens `Replay <set>`, `Each of the set's <n> runs restarts
from its starting point under the chosen config. Nothing reaches the task,
GitHub or any inbox.`:

| Field | Values |
| --- | --- |
| Replay under | "Live config", with the detail "Station as configured now", chosen at first; or one of the station's proposed candidates, newest first, each with its fingerprint. |
| Repeats | How many times to replay each run, 1 to 5. `1` at first. Its hint: `Spotlight replays each run this many times, from 1 to 5. More copies measure noise and narrow the ranges. They also add runs and spend.` |
| Ceiling | The most the replay may spend, every copy of each run included, above 0 and at most 1,000, and a three-letter currency, `USD` unless changed. |

A new baseline is needed when the set has no standing baseline (queued,
running or finished) that holds every run now in the set, replays each run at
least as many times as asked, and was scored the way the live config scores
now. So a baseline is needed when the set has none, when a run was added since
the last one (taking a run out does not count), when the last one replayed each
run fewer times, when the last one was stopped or went over budget, and when the
live config's scoring changed: its fingerprint, the options and ends it has on
the line, its `check`, its `diffs` or its judge's rubric. With "Live config",
the replay itself then becomes the new baseline; otherwise it replays beside
the set's baseline. With a proposed candidate, a baseline of the live config
starts beside it, with a ceiling of its own equal to this one and the same
repeats, so the two may spend up to twice the ceiling. Either baseline may
[check the set](#checking-the-set). At 1 or 2 repeats, a checking baseline
replays each run 3 times under a larger ceiling; at 3 to 5 repeats, it keeps
the repeats and the ceiling asked for. When the baseline beside a candidate
checks the set, the two may spend up to the ceiling plus the baseline's: 4
times the ceiling at 1 repeat, 2.5 times at 2 repeats and twice at 3 to 5
repeats, with the baseline's ceiling at most 1,000. The dialog gives what the
two may spend only in the two notes below for a candidate with no baseline or
more repeats than the baseline, and these say twice the ceiling at any
repeats.

Under the ceiling, the dialog reads `The most that this replay can spend. Its
runs count, and so do the drafting and judging of their changes. Nothing more
starts after the replay spends it.`, then one of these notes:

| When | Note |
| --- | --- |
| No baseline, "Live config" | `The set has no baseline yet. This replay of the live config becomes the baseline.` |
| No baseline, a candidate | `The set has no baseline yet. A baseline of the live config also starts, with its own ceiling of the same size. Together, both replays can spend up to twice this ceiling.` |
| More repeats than the baseline, "Live config" | `The set's baseline replays each run <once or n times>. This replay repeats each run more often. This replay of the live config becomes the new baseline.` |
| More repeats than the baseline, a candidate | `The set's baseline replays each run <once or n times>. This replay repeats each run more often. A new baseline that replays each run <n times> also starts, with its own ceiling of the same size. Together, both replays can spend up to twice this ceiling.` |
| Otherwise, "Live config" | `If the set's runs changed since its baseline, this replay becomes the new baseline. Otherwise, Spotlight compares it with the current baseline.` |
| Otherwise, a candidate | `If the set's runs changed since its baseline, a new baseline also starts. It gets its own ceiling of the same size.` |

When the set holds 5 runs or more and its noise is not measured, the first
four notes end with `The first baseline checks the set. It replays each run 3
times with 3 times the ceiling. It judges and checks each change twice.` The
note reads the same at any repeats. It holds at 1 repeat. The baseline that
checks the set replays each run 3 times, or the repeats asked for when more,
under the ceiling times those repeats divided by the repeats asked for: at 2
repeats, 3 times under 1.5 times the ceiling; at 3 to 5 repeats, as asked,
under the same ceiling.

"Start replay" opens the new replay's page. The dialog refuses a ceiling of 0
or less with `Please enter a ceiling above 0.`, more than 1,000 with `Maximum
ceiling: 1,000`, a currency that is not three letters with `Please enter a
three-letter currency code, like USD.`, and repeats out of bounds with `Please
enter a whole number from 1 to 5.` When the candidates cannot be read, it reads
`Sorry, the station's candidates couldn't be loaded. You can still replay the
live config.`

## What a set is made of

The "Runs" panel reads the set's original runs as they stand when the page
loads.

| Part | Shows |
| --- | --- |
| Bar | How its runs turned out: the bar split by [outcome](#outcomes), then each outcome that occurs with its count, in the order "Accepted", "Sent back", "Asked a person", "Failed", "Other". |
| ⓘ beside "Runs" | `Past runs of the station. Each replay reruns all of them.`, then, once the set holds runs, when they ended, as `Ended between <when> and <when> · Median: <when>`, or `Ended <when>` when they all ended at the same moment, left out while no run's end can be read; then `Where their tasks came from: <origin> <count> · <origin> <count>`, with each [origin](#origins), the largest count first, ties in the alphabetical order of the origin's key (such as `github`, `person`, `station`), not of the label shown. |
| "Unbalanced set" warning sign in the panel's header | With 6 runs or more, when one outcome other than "Other" covers more than two thirds of them. On hover: `<n> of <n> runs <outcome>. Add runs that turned out other ways to balance the set.`, the outcome read as "were accepted", "were sent back", "asked a person" or "failed". |

### Outcomes

How an original run turned out comes from the first thing a person did on its
task after it, other than answering an approval, and from how it ended. The
first row that applies decides.

| Outcome | The run |
| --- | --- |
| Accepted | A person then closed the task. |
| Sent back | A person then sent the task back. |
| Failed | The run ended `failed`. A superseded run, or one that ended another way, goes on to the next rows. |
| Asked a person | A person then answered it, it ended asking a person, or a person granted or refused a tool call it asked approval for. |
| Other | None of the above, such as a run no person has acted on since. |

When people did two things on the task at the same moment, the first of
sending back, closing, answering, parking and starting counts.

### Origins

Where a run's task came from is recorded when the task is opened.

| Origin | The task |
| --- | --- |
| A person | A person opened it at this station. |
| Another station | It was opened at another station and reached this one later, whoever opened it. |
| GitHub, Slack, Linear, or the integration's name | An integration opened it on something it heard. Tasks opened from `git` count as GitHub. |
| Unknown | Its run or task can no longer be read, as for a deleted task. |

### Suggested runs

Once the set holds runs, the "Add runs" dialog lists up to 5 runs first,
under "Suggested to even the mix", with `Recent runs with outcomes that the
set has few of. These runs join the set only when you add them.` Each shows
its [outcome](#outcomes) and "Add". None is ever added without it.

The suggestions come from the same 50 ended task runs the dialog lists.
From those, Spotlight keeps the runs that can be replayed and are not in the
set, then takes the newest run of each task, leaving out tasks with a run in
the set already. Runs are then picked one at a time: the outcome among
"Accepted", "Sent back", "Asked a person" and "Failed" that the set, with the runs
picked so far, holds fewest of, that some run left has, and that is held fewer
times than the most common outcome, "Other" included. Ties go to "Accepted", then
"Sent back", "Asked a person" and "Failed". The newest run left of that outcome is
picked. Picking stops at 5, at the room left in the set below 50, or when no
outcome is short. "Other" is never suggested.

An empty set, a full set, a set whose station has left its line, and a set
already even get no suggestions, and the part is not shown. Suggested runs are not listed
again below it.

### Tasks

The "Tasks" card has one row per task, regressions first, then in the set's
order. Its ⓘ reads `Each task of the set, replayed and compared with
<counterpart>. Regressions come first. Pick a task to see its runs and
judging.`, or `Each task of the set, replayed. Pick a task to see its runs and
judging.` with nothing to compare with. `<counterpart>` is the
[counterpart](#counterparts) as shown, such as `the live config`. With a
counterpart to compare with, the columns are:

| Column | Shows |
| --- | --- |
| Task | The task's title, which opens the [task's details](#task-details), and a red warning sign when the task [regressed](#regressions), with `Regressed: fewer copies succeeded than in <counterpart>, or the judge scored it lower.` on hover. |
| This replay | The [result](#results), with its reasons on hover, joined by `·`. With more than one copy, `<n> of <m> succeeded`, where `<m>` counts the scored copies, or "Not scored yet", with each copy as `Copy <n>: <result> (<reasons>)` on hover. |
| `<Counterpart label>` | Headed by the counterpart's label: "Baseline", "Live config", "Search's starting config" or "Earlier baseline". The counterpart's result on the task, in the same form, or "Not replayed". |
| Judge | This replay's judge score less the counterpart's, to two decimals, or why the two are [not compared](#score-comparisons). On hover: `This replay <scores> · <Counterpart> <scores>`, `<Counterpart>` being the counterpart as shown with a capital, as in `The live config`. A score reads `Yes`, `No`, `<n>/5` or `<n> of <m> claims met`; with copies, each copy's score, joined by `·`, and the difference is between the two sides' averages. Shown once any copy was judged. |
| Closer | Which change the judge found closer to the accepted change [side by side](#side-by-side): "This one", the counterpart, as in "The baseline", or "Neither", and `–` for a task not compared. Its ⓘ reads `Closer to the accepted change, as a blind judge saw it`. Shown once any task was compared. |
| Cost change | This replay's run cost less the counterpart's, each averaged over its copies, once every copy of both has settled. Only costs in the ceiling's currency count. |
| Time change | This replay's run time less the counterpart's, averaged the same way. |

Without a counterpart, the columns are "Task", "Result", "Judge" once any copy
was judged, "Closer" once any task was compared, "Cost" and "Time", for this
replay alone, the judge cell listing each copy's score, and cost and time
averaged over the copies. A value not known reads `–`.

With no tasks, the card reads "No tasks in this replay" and `The set had no
runs when this replay started. Please add runs to the set, then replay it
again.`, with "Open the set".

### Task details

Selecting a task opens a pane beside the card. Its top holds the task's title,
"Original run", linked to the original run, and an X that closes it. Then
come this replay's copies, under "This replay", or "Result" with nothing to
compare with, then the counterpart's, under its [label](#counterparts):
"Baseline", "Live config", "Search's starting config" or "Earlier baseline".
With more than one copy, each is titled with its copy, as in
`This replay, copy 2` or `Live config, copy 2`. Each copy
shows:

- its [result](#results), with "Open the run", linked to the replay run;
- on claims, each claim with "Met" or "Not met" and its reasons, then the pass
  share, as on the Station page;
- once the copy was asked to be [set side by side](#side-by-side), `Closer to
  the accepted change:` with "This one", "The other change" or "Neither", and
  "The other run", linked to the counterpart's run, then
  [what the side-by-side judging found](#reading-a-side-by-side-judging);
- under "Why it succeeded", "Why it failed" or "Why it went unscored", each of
  its [reasons](#results), with chips for the steps and hunks the reason cites,
  as `Step <n>` and `<file>, line <n>` or `<file>, lines <a>–<b>`;
- under "Checks", each check of its change stack: the command, then "Still
  checking.", `Skipped: <reason>`, or each step, "The whole change" or a
  layer, as `<step> · passed in <time>` or `<step> · failed in <time>`, with
  the output of a failed step;
- under "What it changed", the files it changed.

A chip opens the step, or the file's diff at the hunk, in place of the copy's
reasons, checks and changes, with "Back" to return.

## Replay states

| State | Label | Note | Final |
| --- | --- | --- | --- |
| `queued` | Queued | `The replay waits for a runner.` | no |
| `running` | Running | | no |
| `finished` | Finished | | yes |
| `stopped` | Stopped | `A person stopped the replay. No more runs start.` | yes |
| `over-budget` | Over budget | `The replay reached its ceiling. No more runs start.` | yes |

A replay is `running` once its first run is queued, and `finished` once every
run has a result. A stopped replay starts no more runs, and its running runs
are stopped. An over-budget replay starts no more runs, and its runs already
running finish. A run that never started reads `Never ran`, as does a run a
stopped replay left waiting, or `Couldn't be replayed or started: <refusal>`
when it was refused as it came to start, as for `dispatch-failed`, `forgone`
or `candidate-unfit`. Through the API, a person can also stop an over-budget
replay whose runs are still running: those runs stop, and its state stays
`over-budget`.

## Results

| Result | Meaning |
| --- | --- |
| Pending | The run has not ended, its checks or judging have not finished, or, for a run with no change stack, its measures have not come in. |
| Succeeded | The run ended and passed everything that scores the station. |
| Failed | The run failed with `exited`, `refused`, `timed-out` or no failure code, asked a person, or failed a check or the judge. |
| Unscored | Nothing could score the run: it could not be replayed or started, its replay stopped it or reached its ceiling first, its checks or judging could not give an answer, nothing scores the station (`nothing-judges`), it failed before the agent began or for another reason outside the candidate, or Spotlight abandoned it (see [Run failures](#run-failures)). |

A result does not decide alone whether a task [regressed](#regressions): a
copy that succeeded, or one that is unscored but has a judge's verdict, can
regress through a lower judge score.

A run is scored by the candidate's own station block:

| Scored by | When | Passes |
| --- | --- | --- |
| Its checks | The block sets `diffs: true` and a `check`. | The check passes on every layer of the run's change stack. |
| Its judge | The block has a `judge`. Every replay run is judged, whatever the judge's `sample`. | `Yes`, 4 or more on a 1 to 5 rubric, or at least the judge's `passShare` of its claims met. |

With both, a run must pass both. When a person closed the original run's task
as the first thing they did on it after the run, the judge is also given the
original's change, and scores the replay against it. A replay's judge score is
not a run's
[judge score](/docs/reference/app/tasks-runs-and-the-inbox#judge-score): it
counts toward no agreement, standing, alert or Insights figure of the team's
runs. It counts only toward the replay's [success](#success), which the
[Candidates](/docs/reference/app/insights#candidates) section of the Insights Stations tab shows.

Each result carries reasons, shown as `<reason>: <detail>` where there is a
detail:

| Code | Reason shown | Detail | Result |
| --- | --- | --- | --- |
| `unreplayable` | `Couldn't be replayed or started` | [The refusal](#why-a-run-cannot-be-replayed), in lower case | Unscored |
| `not-run` | `Never ran` | | Unscored |
| `run-failed` | `Run failed` | Its [failure](#run-failures) | Failed or Unscored, by failure |
| `run-stopped` | `Replay stopped or hit its ceiling before the run finished` | | Unscored |
| `asked-a-person` | `Asked a person (replays can't)` | | Failed |
| `check-failed` | `Checks failed` | The layer that failed | Failed |
| `check-skipped` | `Checks couldn't run` | [The skip](#check-skips) | Unscored |
| `change-undrafted` | `Change couldn't be drafted` | | Unscored |
| `no-change` | `No change for the checks to run on` | | Unscored |
| `no-change-stack` | `Files changed, but the change never reached Spotlight` | | Unscored |
| `judged` | `Judge passed it` | The judge's reason | Succeeded |
| `judge-failed` | `Judge failed it` | The judge's reason | Failed |
| `unjudged` | `Judge couldn't judge it` | [Why](#judging-failures) | Unscored |
| `nothing-judges` | `No checks or judge score this station` | | Unscored |

When the replay stops, or goes over budget, before a run that finished could
be judged, that run is unscored with `Judge couldn't judge it: replay stopped
before judging`. In a replay that [checks the set](#checking-the-set), changes
are judged and checked a second time; the second answer never changes a
result.

The judge's reasons cite the replay run's steps and the hunks of its change,
as a run's judge reasons do. On claims, each claim's mark and reasons are kept
with the claims as worded when it was judged.

### Success

A replay's success is worked out task by task, a task being one run of the
set. A task's success is the share of its scored copies that succeeded: `1` or
`0` with one copy, and `2/3` when 2 of 3 copies succeeded. The replay's success
is the average over the tasks with a scored copy. Unscored and pending runs are
left out, so a run that could not be replayed or started, or that its replay
stopped, never counts against the candidate.

Beside it is its range: the 95% interval of the average, from 2,000 resamples
of the scored tasks, shown as `<low>–<high>%`. Reading the same results
again gives the same range.

### Gains

A replay compared with another, its [counterpart](#counterparts), reads its
gain over it: on each task both scored, its success less the counterpart's,
averaged, in points, with
the 95% interval of that average from the same resampling of those tasks.

| Verdict | Shown | When |
| --- | --- | --- |
| `better` | Better | The whole interval is above 0, and the gain is at least `min_gain`. |
| `worse` | Worse | The whole interval is below 0, and the loss is at least `min_gain`. |
| `within-noise` | Within noise | Anything else, and always when fewer than 5 tasks were scored on both sides. |

Only the replay page's "Gain" tile writes "Within noise" with a capital.
Elsewhere, as in the "Gain" hover on the set's page, it reads `within noise`.

`min_gain` is the line's [`replay_check.min_gain`](/docs/reference/terraform/line#replay-check-fields),
or 0.05 when the line has no `replay_check`. The app shows it as `+5 pts`. A
replay reads it from the line as it is now; a
[replay check](/docs/reference/api/replay-checks) keeps the one it started
under.

## Side by side

A replay whose candidate has a judge, and that keeps a
[counterpart](#counterparts) in `pairedWith`, is set beside it, task by task,
once the replay has finished. Baselines keep no counterpart, and a replay with
the answer keeps none in `pairedWith`, so neither is ever set side by side. A
stopped or over-budget replay never finishes, so it is never set side by side.
Each copy of a task is set beside the counterpart's copy with the same number,
or else its first copy, as the counterpart's copies conclude, when all of these
hold:

- Both runs completed with a change of at least one line, and have their
  result.
- People accepted the original run's change: the first thing a person did on
  its task after it was closing the task.
- Both replays are judged under the same rubric version. Otherwise, and when
  the counterpart has no judge, the copy reads `other-rubric`.
- The ceiling has room. Each pair is tried at most twice, and before asking,
  Spotlight sets aside four times what judging the copy's own change cost, two
  readings for each of two attempts, on top of what the replay has spent and
  what its pairs still being judged have set aside. When that first judging
  cost nothing, nothing is set aside. A copy that would pass the
  ceiling is not asked; once no pair is still being judged, it reads `budget`.

The judge is given the rubric, the claims or both of the replay's own
candidate, the task's title and description, the two changes as hunks labelled
A and B, and the accepted change, which is neither. With no candidate or no
judge, the copy reads `unreadable-rubric`. The changes are cut at 60,000
characters, and each hunk at 200 lines. It is not told which change is the replay's. It
answers `A`, `B` or a tie, with 1 to 5 reasons, each citing 1 to 10 hunks of A
or B and never of the accepted change. It reads the pair twice: once in an
order drawn from the two runs, and once the other way round. When the two
readings name the same change, or both a tie, that is the outcome; otherwise
the outcome is a tie. Reasons that cite no hunk, or cite the accepted change,
are dropped, and a reading is `ungrounded` when half its reasons or fewer
stand. The replay's change winning is a win, the counterpart's a loss. At most
4 pairs are judged at once, and a pair whose judging fails is tried once more
at most; one that failed `no-evidence`, `interrupted` or `unavailable` is not
tried again.

A task with copies is a win when more of its compared copies won than lost, a
loss when more lost, and a tie otherwise. The replay's wins, losses and ties
count tasks with at least one compared copy. They never change a run's result,
the replay's success, its gain or its regressions.

### Reading a side-by-side judging

In a copy's [details](#task-details), until it is judged, a copy reads `The
judge hasn't compared the changes side by side yet. It compares them when the
replay finishes.` When the two readings disagreed, it reads `The judge picked
a different change depending on which change it saw first. This counts as a
tie.` Under "Both readings", `With this change shown first:` and `With the
other change shown first:` each give their outcome and reasons, each reason
with the hunks it cites, as in `Cites 2 hunks of this change and 1 hunk of the
other`.

A copy not compared reads `Not judged side by side: <reason>.`:

| Code | Reason shown |
| --- | --- |
| `unavailable` | `no judge model available` |
| `unreadable-rubric` | `rubric couldn't be read` |
| `no-evidence` | `nothing to compare` |
| `refused` | `judge declined` |
| `unreadable` | `judge's answer couldn't be read` |
| `ungrounded` | `judge cited nothing either change did` |
| `errored` | `judging failed` |
| `interrupted` | `judging was interrupted` |
| `other-rubric` | `another judge version judged the counterpart` |
| `budget` | `no room left under the ceiling` |
| none | `nothing to compare it with` |

`no-evidence` means either change, or the accepted change, has no hunks, or
the evidence of one of the three runs could not be read.

What side-by-side judging spends counts against the replay's ceiling, but not
toward its spend totals or its cost per run. The replay page shows it apart, as
"Side by side" in the ⓘ of "Spent".

## Health

The "Health" panel of the set's page says whether the set can tell a better
config from a worse one. Its ⓘ reads `Shows whether this set can tell a
better config from a worse one. The first baseline of the live config replays
each run 3 times. Then Spotlight replays the live config with each run's
answer. Spotlight doesn't check sets of fewer than 5 runs.` It is read for the
station's live config as it is now: only replays of the live config at the
station's current [config fingerprint](/docs/reference/glossary#config-fingerprint)
count.

Each reading is a row: its label with an ⓘ that gives its advice on hover,
then what it found, marked with a tick when it found no problem, a warning
sign when it found one, an hourglass while it is being measured, and a dashed
circle while it cannot be read, and "View replay", which opens the replay it
was read from.

| Reading | Read from | Until then |
| --- | --- | --- |
| Noise | The newest finished replay of the live config that replayed each run 2 or more times. | "Not measured" |
| Room to improve | The newest [replay with the answer](#replay-with-the-answer) of the live config as it is now, once it has finished beside its live replay. Before that, the newest finished replay of the live config over every run of the set, other than a search's. | "Not measured" |
| Judge agreeing with itself | The newest finished replay of the live config over every run of the set that [checked the set](#checking-the-set). | "Not checked" |
| Flaky checks | The same replay. | "Not checked" |

### Noise

| Shows | Meaning |
| --- | --- |
| `Success moved <n> pts between <m> copies` | The spread: the highest copy's success rate less the lowest's. A copy's rate is the share of its scored runs that succeeded. Marked when the spread is more than `min_gain`, with the advice `One copy can't tell a real gain from chance. Search with more repeats per run, or raise the line's min_gain.` Otherwise the advice is `Noise is within the line's minimum real gain. A gain of that size is unlikely to be chance.` Both end with `Minimum real gain: +<n> pts`. |
| `Each copy: <rate>, <rate>, …` | Each copy's success rate, in order. |
| `<n> tasks went both ways` | Tasks whose copies both succeeded and failed, or "No task went both ways". The tasks are listed under it. |
| `measured on config <fingerprint> <when>` | The fingerprint and when the replay ended. |

Until it is measured, the advice reads `The first baseline of the live config
replays each run 3 times to measure noise. Noise shows how much success moves
by chance.`

### Room to improve

Before any [replay with the answer](#replay-with-the-answer), or when one
finished but could not be compared, the reading comes from the live config's
success over the whole set:

| Shows | When | Advice |
| --- | --- | --- |
| "Not measured" | No replay of the live config over the whole set has finished. | `Replay the live config over the whole set to see how much of it succeeds already.` |
| `The live config succeeds on <share>` | Its success over the whole set is 95% or less. | `The set has room for a search to find more success.` |
| `Almost none: the live config succeeds on <share>`, marked | Its success is above 95%. A [search](/docs/reference/app/searches#start-a-search) of the set then aims for the same success for less unless told otherwise. | `The set has no room for more success. Search for the same success at less cost, or add tasks that the live config fails.` |

The last two end with `If the set's runs were accepted or sent back, Spotlight
measures this with the answer after a replay of the whole set.`

Once there is a replay with the answer, the reading comes from it, and "View
replay" opens it:

| Shows | When | Advice |
| --- | --- | --- |
| "Measuring with the answer" | It is queued or running. | `Spotlight replays the live config with each run's answer.` |
| "Couldn't measure with the answer" | It, or the live replay it is compared with, was stopped or ran over its ceiling, or that live replay is gone. When it was itself stopped or ran over its ceiling, the next replay of the live config over the whole set starts another. When it finished and its live replay is gone, no other starts for that config. | `The replay with the answer or its live replay didn't finish. If the set's runs were accepted or sent back, Spotlight measures this with the answer after a replay of the whole set.` |
| `Too few runs to tell: <n> runs with an answer` | Both finished, but fewer than 5 tasks were scored on both sides. | `Spotlight needs 5 runs that were accepted or sent back to measure room. Please add some to the set.` |
| `Up to <gain> with the answer` | Its [gain](#gains) over its live replay is `better`. | `<rates> A better config can gain up to this much.` |
| `Little: <gain> with the answer`, marked | Its gain is `within-noise` or `worse`. | `<rates> Even the answer barely helps. Add tasks that the live config fails, or search for the same success at less cost.` |

`<rates>` is `Live config: <share> on <n> runs. With the answer: <share>.`,
both read on the runs it replayed. Every advice in this table but "Couldn't
measure with the answer" ends with `Answer: the change people accepted, or
what they said when they sent the run back.`

### Judge agreeing with itself

| Shows | When | Advice |
| --- | --- | --- |
| "Not checked" | No check of the set asked for a second judging. | `The first baseline of the live config judges each change twice to measure this. It shows whether the verdicts match.` |
| "Judging again" | No change has been judged twice yet. | `The judge is judging each change a second time.` |
| `Same verdict on <share> of <n> changes`, marked | The judge passed or failed the same change alike less than 80% of the time. | `The verdicts are partly chance. Please make the rubric more specific before you search.` |
| `Same verdict on <share> of <n> changes` | 80% of the time or more. | `The verdicts stay the same when the judge judges again.` |

`<n>` counts the changes judged twice, both times with a verdict. While second
judgings are still to come, the advice ends with `<n> second judgings are
still to come.`

| Shows | When | Advice |
| --- | --- | --- |
| "Not checked" | No check of the set asked for a second check. | `The first baseline of the live config runs the station's check twice on each change to measure this. It shows whether the check gives the same answer.` |
| "Checking again" | No change has been checked twice yet. | `Spotlight is checking each change a second time.` |
| `<n> of <m> changes flipped`, marked | The check passed once and failed once on some changes. | `The check passed once and failed once on these changes. Please fix the flaky tests, or take these tasks out of the set.` |
| `None of <m> changes flipped` | Every change checked twice got the same answer both times. | `The check gave the same answer both times.` |

`<m>` counts the changes checked twice, both times passing or failing. The

### Replay with the answer

After a replay of the live config over every run of the set finishes, other
than a search's, Spotlight starts a replay of the same live config handed each
run's answer, when:

- the station still runs that config, at the same
  [config fingerprint](/docs/reference/glossary#config-fingerprint);
- the station has not left its line;
- at least one of the set's original runs was "Accepted" or "Sent back" (see
  [Outcomes](#outcomes));
- the set has no replay with the answer of that config that is queued,
  running or finished.

Nobody starts it, and it cannot be started from the app or the API. Its
candidate is named `With the answer, <date>`, and it shows under "Replays"
like any other replay. It replays only the set's runs whose original was
"Accepted" or "Sent back", among the runs that live replay replayed and that are
still in the set, with the repeats and a ceiling of its own equal to those of
the live replay whose finishing started it. Set [health](#room-to-improve)
reads it against that live replay, on the runs it replayed. That live replay
is also its [counterpart](#counterparts): on the replay page and in the API,
its tasks and gain are compared with it, shown as `the live config`, or as
`the baseline` while it is the set's baseline. When that live replay is gone,
it is compared with nothing. It is never set [side by side](#side-by-side). A
stopped one
reads `A person stopped the replay. No more runs start.`, also when Spotlight
stopped it.

Each replay run's briefing ends with a section headed `## The answer`:

| Original | The answer |
| --- | --- |
| Accepted | `People accepted this change for the task. Make the same change.`, then the original run's change as a diff. |
| Sent back | `A person sent an earlier attempt at this task back and said:`, then what people wrote on the task after the run, up to the task's next run, each quoted, then `Do the task so that it meets what they asked for.` |

Which kind of answer each run gets is fixed when the replay starts; a run
whose original change has no hunks, or whose sending back came with no words,
is left out. The hunks and people's words are read again when each run is
queued, and the answer is cut at 60,000 characters. If a run's answer is gone
by then, the run is not replayed and reads `answer-gone` (see
[Why a run cannot be replayed](#why-a-run-cannot-be-replayed)).
If the station's config changes while it is queued or running, Spotlight stops
it.

### Checking the set

Nobody starts a check, and it cannot be started from the app or the API. A
baseline of the live config checks the set when both hold:

- the set holds 5 runs or more;
- no replay of the live config at its current
  [config fingerprint](/docs/reference/glossary#config-fingerprint) over the
  whole set has checked it, or is checking it, while queued, running or
  finished.

This applies to a "Live config" replay that becomes the baseline, and to a
baseline that starts beside a proposed candidate. A search's replay of the
live config and the baseline of a
[replay check](/docs/reference/api/replay-checks) never check the set.

The checking baseline replays each run 3 times, or the repeats asked for when
more. Its ceiling grows in step: the ceiling asked for, times its repeats,
divided by the repeats asked for, and at most `1,000`. One repeat at `5.00`
becomes 3 repeats at `15.00`. Its 3 copies measure the set's [noise](#noise).

Once it finishes, every change whose check passed or failed is checked a
second time, and every change the judge gave a verdict on is judged a second
time. Each change is weighed on its own, in order: it is judged again when what
its first judging cost still fits under the ceiling, on top of what is spent
and set aside so far. A change that does not fit is not judged again, a later,
cheaper one still can be, and a change whose first judging cost nothing always
fits. A second judging or check never changes a run's result. Its finishing
then starts the [replay with the answer](#replay-with-the-answer), as any
replay of the live config over the whole set does.

## Counterparts

A replay's counterpart is the replay of the set it is compared with. Its
task-by-task rows and its gain are measured against it, and the API names it
in `comparedWith`. These replays keep a counterpart, chosen when the replay
starts:

| Replay | Counterpart |
| --- | --- |
| Under a proposed candidate, or under the live config when it does not become the baseline | The baseline that starts beside it, else the set's baseline standing when it starts that covers its runs with at least as many copies, a finished one first. |
| A search's replay of a candidate, on the searched or the held-out tasks | The search's replay of the live config it started from. A search's replay of the live config is a baseline. |
| A [replay check](/docs/reference/api/replay-checks) of a planned change | The baseline that starts beside it, else the set's standing baseline, as for a proposed candidate. |
| A [replay with the answer](#replay-with-the-answer) | The replay of the live config whose finishing started it. |

The first three also hold it in `pairedWith`, the replay their changes are set
[side by side](#side-by-side) with. A replay whose kept counterpart is gone has
none, and is compared with nothing.

A replay that keeps none, such as a baseline, has as its counterpart the set's
baseline as it stands when it is read: the newest replay of the live config the
set started as a baseline, while it is queued, running or finished. The
baseline itself has none. A stopped or over-budget baseline is not compared
with, and the next replay of the set starts a new one.

The counterpart is shown, and labelled, as:

| Counterpart | Shown | Label |
| --- | --- | --- |
| The set's baseline now, for any replay | `the baseline` | "Baseline" |
| Another, for a replay with the answer | `the live config` | "Live config" |
| Another, for a search's replay of a candidate | `the search's starting config` | "Search's starting config" |
| Another, for any other replay | `an earlier baseline` | "Earlier baseline" |

The shown form names it in running text, as in the "Tasks" ⓘ. The "Closer"
column and the judge hover capitalise it, as in "The baseline". The label heads
its column under "Tasks" and starts its success on the set page's "Gain"
hover. In lower case, it follows the verdict on the "Gain" tile, and on the
[success line](#success-line) it follows `vs` after the gain, or `·` without
one.

## Regressions

A task regressed when the counterpart's [success](#success) on it is higher
than this replay's by more than 50 points (0.5), or when this replay's judge score, averaged over its
copies, is more than 0.01 below the counterpart's. With one copy each, that is
the counterpart succeeding and this replay failing. Either is enough: a task
whose copies all succeeded still regresses when its judge score is lower. A task
can regress only once every copy of it, on both sides, has settled and has its
result. A copy that has neither a scored result nor a judge's verdict cannot
make a task regress.

### Score comparisons

Judge scores are compared only when both runs were judged, under the same
rubric version, either both or neither against the original's accepted
change, and on the same scale. Scores on different scales are not compared,
and the cell reads `–`. Otherwise the "Judge" column says why:

| Code | Shown |
| --- | --- |
| `unjudged` | `One side wasn't judged` |
| `other-rubric` | `Judged by different rubrics` |
| `other-reference` | `Only one judged against the accepted change` |

## Why a run cannot be replayed

`409`. A run in a set that can no longer be replayed carries a red warning sign

`not-a-task-run`, `task-gone`, `still-running`, `no-starting-point`,
`no-briefing` and `archive-gone`. The dialog shows these for the runs it lists.
It leaves out runs that are no longer in the workspace, so it never shows
`unknown-run`.
The other refusals of an added run show only as the `409`. A run refused when its replay comes to start it is unscored, with
`Couldn't be replayed or started: <refusal>`, the refusal in lower case.

| `repository-gone` | `Repository has left the line` |
| `not-at-the-station` | `Run wasn't at this station` |

| `forgone` | `Never started` |
| `dispatch-failed` | `Failed to start after several tries` |

`attachments-gone`, `repository-gone` and `not-at-the-station` can be refused
both when a run is added and when its replay comes to start it. `answer-gone`,
`candidate-unfit`, `cannot-start`, `forgone` and `dispatch-failed` arise only
when a replay comes to start the run. `candidate-unfit` means the candidate was
removed, or its block no longer fits the line as it is now. `cannot-start`
means the candidate's station runs no harness a runner can start.
`dispatch-failed` follows 10 failed attempts to queue the run. `unchecked`
means checking the run met an unexpected error when it was added, with the
reason `It could not be checked just now. Please try again later.`; adding it
again checks it again.

A workspace archive is kept for at least 30 days after the latest run that
started from it, and while a run that started from it is in a replay set. Once
the run's task is deleted, the replay set no longer keeps it. See
[Workspace archives](/docs/reference/limits-and-timeouts#workspace-archives).

## Spend and ceiling

A replay's spend is the cost of its runs, every copy included, of drafting their change stacks and of
judging them, counted in the ceiling's currency. A drafting or judging attempt
that failed counts what it was billed. A cost in another currency is summed
apart and does not count toward the ceiling, nor does a cost that was never
reported, for a replay started from the app or the API. Replays a search or a
replay check starts, and their baselines, count such a run at a fixed amount
per run against the ceiling; a replay with the answer does the same when the
live replay that started it does. Side-by-side judging counts against the ceiling, but not toward
the spend; see [Side by side](#side-by-side). Each replay has its own ceiling. A baseline started beside a replay has a ceiling of its own, equal to
the replay's, or larger when it [checks the set](#checking-the-set). The second judgings of a baseline that [checks the set](#checking-the-set)
count against its ceiling, but not toward its success or what its runs cost.

Once a replay's spend reaches its ceiling, it ends as `over-budget`: nothing
more of it starts, its runs not yet started are withdrawn, and its runs already
running finish. What they spend still counts, so a replay can end above its
ceiling. The replay page then reads `Over the ceiling by <amount>`, and
`spotlight replay status` adds `, over the ceiling by <amount>, spent by runs
already running when it was reached`.

## Replay runs

A replay run's Run page opens at `/w/<slug>/team/<teamId>/runs/<runId>`, like
any run, from "Open the run" in a task's [details](#task-details). Its
breadcrumb ends with the original run's task title and `Replay at <station>`,
or `Replay at a removed station`. Above the run's briefing and steps, a banner
shows:

- `A replay of <task title>`, linked to the original run;
- `Under <candidate>`, with `(the baseline)` for a baseline; for a search's
  replay, `· candidate <name> in its search`, or `· the live config it started
  from in its search`, linked to the search; then `in a replay of <set>`,
  linked to the replay page.

When the replay cannot be read, the second line reads `Sorry, the replay
couldn't be loaded. Please try again later.` The run's result, claims and
side-by-side judging show in the task's details on the replay page.

The message box is disabled, with `The agent runs autonomously. It can't
receive messages.` A replay run can be read, with its config and its event
stream, only by those who may read the team it replayed for, recorded when it
was queued, even after its station is removed. Anyone else is answered `404`,
and the page reads `This team has no such run.`

A replay run differs from a task run:

| | Replay run |
| --- | --- |
| Task | Holds no task. The task's state, notes, board and inbox do not change. |
| Workspace | The exact archive the original run restored, or none if it restored none. A replay that cannot restore it fails. |
| Checkouts | Each repository at the commit the original run started from. |
| Briefing | The task as briefed to the original run, with its notes, attachments and decisions then. The memories it was briefed with are looked up again when the replay run is queued: a memory deleted since is left out, and each one reads as it stands now. `spotlight history` and `spotlight recall` read as of the original run's start. A [replay with the answer](#replay-with-the-answer) adds the answer. |
| Agent commands | `spotlight trace`, `spotlight remember` and answering a pull request's remarks are refused. |
| Git | Fetch only. A push is refused with `this run may only fetch`. |
| Tools, MCP servers, secrets | None. |
| Hooks | None run for it. |
| Asking a person | Ends the run, counted as asked. Handing the task to a person, or to nowhere, does the same. |
| Change stack | Drafted when the candidate sets `diffs: true`, checked, and never sent to GitHub. |
| Archive | None is kept for a later run. |
| Outcomes | Not recorded among the station's outcomes or in the Insights figures of the team's runs; its replay shows under [Candidates](/docs/reference/app/insights#candidates) on the Insights Stations tab. No memories are drafted. |
| Priority | Below every task run and chat run. At most 2 of a team's replay runs, other than a search's, are queued or running at once. A search's replay runs are held to its own limit; see [Spend and ceiling](/docs/reference/app/searches#spend-and-ceiling). |

See [Inside a sandbox](/docs/reference/hosts/sandbox) for the phases every
run goes through.
