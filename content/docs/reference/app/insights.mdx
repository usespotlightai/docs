The Insights page sums up how a team's runs, tasks and pull requests went over
a period, against the period before it. It is "Insights" in the team's
sidebar, at `/w/<slug>/team/<teamId>/insights`. The same figures are read
through the [Insights API](/docs/reference/api/insights), and the Candidates
section of the Stations tab through the
[Replayed candidates API](/docs/reference/api/replayed-candidates).

Only people on the team, the workspace's owners and admins, and workspace
tokens with the `read` scope can read Insights, on every tab. Anyone else is
answered `404`, and the page reads "Only team members can see Insights". See
[Team outcomes](/docs/reference/roles-and-permissions#team-outcomes).

The tabs, in order:

| Tab | `?tab=` |
| --- | --- |
| Overview | `overview`, the default |
| Cost | `cost` |
| People | `people` |
| Productivity | `productivity` |
| Stations | `stations` |
| Tools and skills | `tools` |
| Runs | `runs` |
| Traces | `traces` |

## Period

The period picker, at the top of the page, offers "Past 7 days", "Past 30
days" and "Past 90 days", and starts at 30 days. A period is whole UTC days,
up to and including today. The period before is as long and ends where the
period starts. The page's address keeps the tab and the period as
`?tab=<tab>&period=<7d|30d|90d>`, leaving out either while it is the default.
Changing the period keeps the tab and its filters.

A figure with a change against the period before shows it beside the figure,
with "Against the previous period" on hover:

| Change | Reads |
| --- | --- |
| A count, time or amount | A whole percent, as in `+12%` or `-8%`. |
| A rate | Points, as in `+5 pts`, with one decimal under 1 point, as in `+0.4 pts`. |
| None | `No change`. |
| From nothing | `Up from 0`. |

An arrow beside a change is green when the change is good and red when it is
bad. A change in "Spend" and "Cost", in a station's runs, and in a station's
tasks is neither. A change in spend is shown only when both periods are priced
in the same currency.

Each tab's figures sit in cards. An ⓘ beside a card's title describes
it on hover, and a card with a table under its chart has a "Chart" and "Table"
switch. On People, Productivity, Stations and Tools and skills, the figures
are grouped in sections whose heading folds them away.

## What is counted

A run is counted in a period when it ended in it. Except on the Runs tab, only
runs that ran are counted: every run except cancelled ones. See
[Run endings](/docs/reference/app/tasks-runs-and-the-inbox#run-endings).
Only task runs at a station are recorded; chat runs are not.

| Term | Meaning |
| --- | --- |
| p50 | The median. With an even count, the mean of the two middle values, rounded to a whole number, with a half rounded up. |
| p75, p90, p95 | The nearest-rank 75th, 90th and 95th percentiles. |
| Next act | The first thing a person did with the task after the run: the act names the run, or else it follows the task's last run at that station. It is one of Started, Parked, Closed, Answered and Sent back. Of acts at the same moment, the first of Sent back, Closed, Answered, Parked and Started counts. Approving or refusing an approval is never a next act. |
| Accepted | A run whose next act was Closed. |
| Sent back | A run whose next act was Sent back. |
| Person act | A person moving a task, answering, approving, refusing or sending a run back. |
| Activity | A person opening a task, acting on one, or starting an agent chat on the team. |

Outcomes are recorded as runs end and as people act. Nothing that happened
before recording began is counted. A deleted task's runs, pull request and acts
are removed.

Overview and "Where work waits" count a task's pull request when the task had
one of the team's runs that ended in the period, the period before, or the
last 30 days where that reaches further. They also count the pull request of
one of the team's tasks when it opened before the period ended and, in that
time, it closed, or it is still open and it opened or had its first review by
a person.

A station that no longer exists shows as "A removed station", a person without
an account as "A former member", and a task no person opened as "No one".

With nothing to count in the period, these read "No runs in this period",
with "Create a task", which opens the team's first line, and a line of their
own:

| Tab or section | Line |
| --- | --- |
| Overview | `Cost and delivery show here once stations run tasks.` |
| Cost | `Cost by harness, model, station and repository shows here once stations run tasks.` |
| People | `Load on people shows here once they open tasks, answer the inbox or chat with the agent.` |
| Where work waits | `Where tasks wait shows here once they move through the stations.` |
| Runs at each station | `Each station's runs show here once stations run tasks.` |
| Config changes | `Config changes and results by harness, model and effort show here once stations run tasks.` |
| Skills and tools | `Skills read and MCP servers called show here once stations run tasks.` |
| Runs | `Runs that end in this period show here, newest first.` |

A part that could not be read reads `<part> could not be loaded.`, with
"Try again".

Figures open the Runs tab, narrowed by the pills listed under [Runs](#runs),
or narrow the Productivity tab's pull request list:

| Selecting | Opens |
| --- | --- |
| A tile's figure | The Runs, Cost or People tab, or the pull request list, narrowed to what the tile counts where it can. |
| A day's "Runs" in "Output against cost", `<n> runs` and `Runs with config` on Overview, a cost slice, a person's name in "What each person did", "Tasks" in "Where tasks wait", "Runs" and "Failed" in "By station", a failure reason, a skill's week, "Given", "Read" or station, an MCP server's counts, and a refused tool's count | The Runs tab, narrowed to those runs. |
| A count in "Spotlight's share", "Week by week", "By repository", "Spotlight against people", "What Spotlight ships" and "Review depth" | The pull request list, narrowed to those pull requests. |

## Overview

| Figure | Counts | A rise is |
| --- | --- | --- |
| Spend | The cost of the runs, when every priced run is in one currency, with `Over <n> runs`. Otherwise it reads `–`, with `No priced runs` or `Prices in more than one currency`. | neither |
| PRs merged | Task pull requests merged in the period, with `<n> closed unmerged`. | good |
| Merge rate | Merged, of the task pull requests merged or closed unmerged in the period. Its change is in points. | good |
| Cost per merged PR | Spend divided by PRs merged. | bad |
| Task to merge | For pull requests merged in the period, the p50 time from the task opening to the merge, and the p90. | bad |
| Human touches per task | Person acts in the period on the tasks the period's runs worked, per task, with `<acts> over <tasks> tasks`. | bad |
| Active people | People with an activity in the period. | good |

"Spend" and "PRs merged" each draw their figure day by day under it. A tile's
figure opens the Runs, Cost or People tab, narrowed to what it counts where it
can be.

"Output against cost" charts spend and merged pull requests per UTC day. Spend
is charted only when every priced run in the period is in one currency;
otherwise the card's description reads
`Merged pull requests per day. Spend not shown. <reason>.`, with the reason
`No priced runs` or `Prices in more than one currency`. Hovering over a day
shows `<spend> spent over <n> runs`, `<n> PRs merged` and
`Config changed at <station>` for each config change that day. Its table lists
"Day", "Runs", "Spend", "PRs merged" and "Config changes".

A diamond under a day, and a dashed line across it, marks a config change: a
station's run that started with a config fingerprint other than that of the
station's run started before it. Runs are taken in the order they started,
and the diamond is dated from when the run started. A station's first config
is not marked, and a return to an earlier config is marked like any other
change. A run that never started marks nothing. Hovering over a diamond shows
`Config changed on <day>` and, for each station, its name, linked to the
station, "Impact" (see [Impact](#impact)), and
`Runs with config <fingerprint>`, the first 8 characters, which opens the Runs
tab at the station's runs with that config.

"Stations worth improving" lists stations with at least 3 runs in the period
where a signal is worse than the station's own in the period before, or worse
than all stations' together in the period:

| Signal | Rate |
| --- | --- |
| Sent back | Runs whose next act was Sent back, of runs. |
| Checks failed | Failed checks, of passed and failed checks. |
| Run failures | Failed runs, of runs. |
| Task failures per run | Task failures raised at the station, per run. |
| Cost per run | Spend, per run. Not compared across currencies. |

A signal is worse when it is more than 1.25 times the value it is compared
with and, for every signal but cost, also at least 0.05 higher: 5 percentage
points for a rate, 0.05 failures per run for task failures.
Stations are ordered by how many signals are worse, then by how far the worst
exceeds its comparison, then by runs.

Each station's row shows its name, linked to the station, its line,
`<n> runs`, which opens the Runs tab at the station, and "Improve", which
opens the Agent page with the station attached to a new chat. Unfolding a row
lists each worse signal:

| Column | Shows |
| --- | --- |
| Signal | The signal. |
| Compared | A dot for this period, a ring for the period before, a line for all stations, and a dashed line where the station gets flagged. |
| This period | The station's value. |
| Period before | The station's value in the period before. |
| All stations | The value over all stations in the period. |
| Flagged above | The lowest line the signal crossed: 1.25 times the value it is compared with, or, for every signal but cost, 0.05 above it where that is higher. |

A station whose spend came in more than one currency adds
`Cost isn't compared. Prices are in more than one currency.` With none listed, the
card reads `No station needs attention this period.`

## Cost

| Figure | Counts |
| --- | --- |
| Spend | The cost of the runs, when every priced run is in one currency. Otherwise `–`, with `No priced runs` or `Prices in more than one currency`. |
| Runs with no price | Runs whose harness reported no cost. |
| Cache share | Cache-read tokens, of input, cache-read and cache-write tokens together, over the runs whose harness reported input and cache-read tokens. Otherwise `not reported`. |

While the spend is in one currency, "By harness", "By model", "By station" and

`No station reported tokens in this period.` See
[Spend](/docs/reference/app/tasks-runs-and-the-inbox#spend) for which
harnesses report tokens.

## Productivity

The Productivity tab, `?tab=productivity`, has the sections "Where work
waits", "What the agents ship", "Review and approval" and "Pull requests".

### Where work waits

"Where tasks wait" shows, for each station in the order its first run ended,
the p50 of:

| Wait | From | To |
| --- | --- | --- |
| Queued | A run is queued. | The run starts in its image on a runner. |
| Running | The run starts in its image on a runner. | The run ends. |
| In the inbox | The station asks a person. | The first person act on the task after the ask, at any station, before the task's next ask. |

Its table adds the p90 of each on hover, "Tasks" with its change, "Runs",
"Asks" (times the station asked a person) and "Unanswered".

"Past the last station" follows each task's pull request:

| Figure | Counts | Time shown |
| --- | --- | --- |
| PRs opened | Pull requests opened in the period. | Task to PR: from the task opening to the pull request opening. |
| First reviews | First reviews by a person in the period. Reviews by bots are not counted. | PR to review: from the pull request opening to its first review. |
| PRs merged | Pull requests merged in the period. | Review to merge: from the first review, or from the opening where no person reviewed it, to the merge. |

Times show as p50 and p90. A task tracks one pull request at a time. A task
that opens another pull request is tracked on the new one.

### What the agents ship

This section and "Review and approval" count the pull requests described under
[Pull requests](#pull-requests) over the period and the one before, together
with the team's runs. When none of Spotlight's pull requests and none of people's alone merged in the period,
none waited on a review and no person reviewed one, it reads "No pull requests in this period", with "Connect a repository", which
opens the team's Integrations settings, and "Review and approval" does not
show.

Spotlight's pull requests are set against people's alone: those people opened
with no Spotlight review task, in the repositories Spotlight merged into in
the period. Bots' pull requests are left out of both.

"Flow through the pipeline", "Time to merge", "Time to merge by PR type" and
"Time to first review" each have a percentile picker, "p50", "p75", "p90" or
"p95", which starts at "p75". Each time shown is that percentile of its own
times.

#### Flow through the pipeline

"Flow through the pipeline" follows Spotlight's pull requests merged in the
period whose task opened in the period, the period before, or the last 30 days
where that reaches further, from the task opening to the merge:

| Stage | From | To |
| --- | --- | --- |
| Coding | The task opens. | The pull request opens. |
| A station | The time the task spent at the station: the time its ended runs there were queued and running, and its waits in the inbox there, from ask to answer. | |
| Awaiting review | The pull request is ready for review. | Its first review by anyone but its author, bots' included. Time as a draft is left out. |
| In review | That first review. | Its first approval that was not dismissed, or its closing where that came first. |
| Awaiting merge | The first approval, or the closing. | The merge. |

"Show coding as" picks "Stations", the default, which shows each station the
tasks ran at, in the order they were first used, in place of Coding; or
"Stages", which shows Coding as one stage. The card's header reads
`<n> PRs merged`. The legend lists each type of pull request; picking one
shows that type's times alone and reads `<n> <type> PRs merged`, and picking
it again shows every type.

A stage's colour runs from "flows freely" to "jammed": its time against the
longest stage's, at the percentile, for the same type. The longest stage is
the worst jam: its name is red, a badge under it reads
`Worst jam | <time>`, with `mostly <part>` at a station, and in the table a
red dot marks it, `Worst jam: the stage with the longest wait` on hover. Hovering over a station's name shows its
time queued, running and in the inbox. "Play" sets the chart moving, and
"Pause" stops it. Its table groups the stages under "At the stations" and "On
the pull request", with "Stage", "Time", and for stations "Queued", "Running"
and "In the inbox".

#### Time to merge

"Time to merge" gives the time from opening to merge of Spotlight's pull
requests, "Spotlight's", and of people's alone, "People's alone", merged in
the period, each with its change against the period before, where a fall is
good. The chart draws both day by day. Its "Smoothing" switch picks "7-day
rolling", the default, which takes the pull requests merged in the 7 days
ending each day, or "Daily", those merged that day. "Time to first review"
has the same switch.

"Time to merge by PR type" lists each [type](#types) with a pull request
merged, as `<n> merged` over both groups, with Spotlight's time and people's,
slowest first by Spotlight's time. A type Spotlight has no time for comes last.

#### Review depth as throughput climbs

"Review depth as throughput climbs" gives, for each week from Monday, UTC, the
share of the two groups' pull requests merged that week in the period that
took "No review", "One round", "Two rounds" and "Three or more"
[review rounds](#spotlight-against-people), with "Merged that week" as a line.
Beside the chart, each bucket's count and share over the period.

### Review and approval

"Review and approval" counts the team's pull requests, less those written by
`bots`; a pull request a bot opened that has a Spotlight review task is
counted:

| Card | Shows |
| --- | --- |
| Time to first review | Day by day, the time from a pull request being ready for review to its first review by anyone but its author, bots' included, less any time as a draft, for those first reviewed that day ("Daily") or in the 7 days ending that day ("7-day rolling", the default). |
| PRs awaiting first review | At the end of each day, the pull requests ready for review, not drafts and not closed, with no review yet by anyone but their author. |
| AI review agents | Each bot that commented on or reviewed the team's pull requests, those bots opened included, that were open at any time in the period, most comments first: "Agent", "Comments" (inline and in the conversation, less those deleted), "Reviews", and "Resolved", the share of the review threads it started that are now resolved. |
| Human reviews | Reviews people submitted each day. |

### Pull requests

Spotlight records every pull request in the repositories the GitHub App is
installed on, as GitHub reports it opening, changing, being reviewed and
closing. What a report says about a pull request is ignored when the pull
request's address disagrees with the report's repository or number. The
section counts the pull requests a task of the team opened, and those in a
repository one of the team's lines names. With none, it reads "No pull requests in this period", with "Connect a repository".

Each pull request is written by one of:

| `author` | "Written by" | The pull request |
| --- | --- | --- |
| `spotlight` | Spotlight | A task opened it. |
| `touched` | Others, with a Spotlight review task | Someone else opened it, and a Spotlight review task was opened on it. |
| `bots` | Bots alone | A bot opened it, with no Spotlight review task. |
| `people` | People alone | Any other. |

#### Spotlight's share

| Figure | Counts |
| --- | --- |
| PRs merged | Pull requests merged in the period, bots' included. |
| Made by Spotlight | Of those, the ones a task opened. |
| Reviewed by Spotlight | Of those, the ones others opened with a Spotlight review task. |
| Spotlight's share | Made or reviewed by Spotlight, of all merged. |

"Week by week" splits the merged pull requests by who wrote them, for each
week from Monday, UTC. "By repository" gives Spotlight's share week by week
for each repository the team's lines name, and any other its tasks merged
into, most merged first, with "Merged" and "Share" over the period.

#### Spotlight against people

"Spotlight against people" sets Spotlight's pull requests merged in the period
against people's alone, merged in the same period in the repositories
Spotlight merged into, which its description names. Bots' pull requests and
those with a Spotlight review task are left out of people's. With nothing
Spotlight merged, its description reads
`Spotlight merged no pull requests in this period. There is nothing to compare people's pull requests with.`

| Row | Measures |
| --- | --- |
| Merged | How many merged. |
| Time to merge | From opening to merge: p50, with the p90 on hover. |
| Time in review | From the first review by a person to merge: p50, with the p90 on hover. Pull requests no person reviewed are left out. |
| Review rounds | Mean rounds per pull request. |
| Review comments | Mean inline review comments by people per pull request, less those deleted. |
| Revert rate | Pull requests since reverted, of those merged. |

Each approval or request for changes by a person is a review round. Reviews by
people after the last of them, such as reviews that only comment, make one more
round, so a pull request with only comments has 1. Reviews by bots and
dismissed reviews do not count.
"Review depth" gives how many merged pull requests took "No rounds", "1
round", "2 rounds" and "3 or more rounds", for the same two groups.

A pull request is a revert when its description has a line
`Reverts <owner>/<repository>#<number>` naming a pull request of the same
repository, or else when its title is `Revert "<title>"`. When a revert merges,
the pull request it names, by number or by the latest merged one with that
title, is marked reverted, and the list shows its state as
`<state>, reverted`.

#### Types

"What Spotlight ships" counts merged pull requests by type, Spotlight's against
people's alone, with "Spotlight spent": what all the runs of the tasks behind
Spotlight's pull requests cost, or `–` with the reason on hover. People's here
are counted only in the repositories Spotlight merged into, as in "Spotlight
against people" and "Review depth".

A pull request's type is the first of these that gives one:

1. For Spotlight's, its task's latest change stack: each `change` cohort is
   typed by its title, or else its intent, by the title rules below, and the
   most common type wins. A tie goes to the earlier of Feature, Fix,
   Refactor, Tests, Chore and Other.
2. Its title, by a conventional prefix such as `fix:` or `feat(api)!:`:

   | Prefix | Type |
   | --- | --- |
   | `feat`, `feature` | Feature |
   | `fix`, `bugfix`, `hotfix` | Fix |
   | `refactor`, `perf` | Refactor |
   | `test`, `tests` | Tests |
   | `chore`, `build`, `ci`, `docs`, `style`, `deps`, `revert` | Chore |

3. Its title, by its first words, tried in this order:

   | First words | Type |
   | --- | --- |
   | `revert`, `bump`, `chore`, `upgrade`, `release`, `doc`, `docs` | Chore |
   | `update` then a word starting `dependenc`, `deps` or `lock` | Chore |
   | `add`, `write` or `cover`, then optionally `more`, then optionally `unit` or `e2e`, then `test` or `tests`, as in `add unit tests` | Tests |
   | `test`, `tests` | Tests |
   | `fix`, `fixes`, `fixed`, `hotfix`, `patch`, `resolve`, `correct`, `repair` | Fix |
   | `refactor`, `restructure`, `rename`, `extract`, `simplify`, `split`, `inline`, `tidy`, `clean up`, `move` | Refactor |
   | `add`, `implement`, `introduce`, `support`, `allow`, `create`, `build`, `enable`, `show`, `let`, `offer` | Feature |

4. Its branch, by a prefix followed by `/` or `-`:

   | Prefix | Type |
   | --- | --- |
   | `feat`, `feature`, `features` | Feature |
   | `fix`, `bugfix`, `hotfix`, `bug` | Fix |
   | `refactor`, `refactoring` | Refactor |
   | `test`, `tests` | Tests |
   | `chore`, `deps`, `dependabot`, `renovate`, `release`, `docs`, `ci`, `build` | Chore |

5. Otherwise, Other.

Prefixes and words are matched without regard to case.

#### The list

"Pull requests" lists every pull request opened or closed in the period, or
still open, 50 to a page. The latest is first, by when it closed or, while it
is open, when it opened. Pull requests with the same time are in order of
their address, by character code:

| Column | Shows |
| --- | --- |
| Pull request | Its title and `#<number>`, linked to it on GitHub. |
| Repository | Its repository. |
| Written by | "Spotlight", linked to the task, with "Runs", which opens the Runs tab at the task; or its author, or "Someone", with "Spotlight review", linked to the review task, when it has one. |
| Type | Its type. |
| State | "Merged", "Closed unmerged" or "Open". |
| Opened | When it opened. |
| To merge, In review | The time to merge and in review. |
| Rounds, Comments | Its review rounds and comments. |
| Size | `+<added> −<deleted>`. |
| Cost | For Spotlight's, what its task's runs cost. |

"Repository" ("Every repository"), "Written by" ("Anyone"), "Type" ("Every
type") and "State" ("Every state") narrow it. Following a figure elsewhere on
the tab narrows it further, shown as a pill: "Week of", "Reverted", "Review
rounds" (as above) or "Repositories" ("Where Spotlight merged"). Narrowed to
nothing, the list reads `No pull requests match.`, with "Show every pull
request"; with none in the period, `No pull requests in this period.`

#### Retention

A pull request is forgotten 180 days after it closed, or, while open, 180 days
after it last changed. One already past that when first heard of is not
recorded. Spotlight's pull requests, and those with a Spotlight review task,
stay counted after that. Removing the GitHub App's installation forgets every
pull request of the workspace in the same way, trying again for any that could
not be forgotten at once. Closing a workspace disconnects it from GitHub
before its pull requests are removed.

A forgotten pull request is recorded again only when GitHub reports it updated
later than the last update Spotlight had before forgetting it. Spotlight keeps
that last update until 210 days after it.

## Stations

The Stations tab, `?tab=stations`, has the sections "Runs at each station",
"Config changes" and "Candidates". With `&stationId=<stationId>` it shows
[one station](#one-station) instead.

### Runs at each station

"The whole team" sums up the team's runs, counted as for
[station outcomes](/docs/reference/app/tasks-runs-and-the-inbox#station-outcomes):

| Tile | Counts | A rise is |
| --- | --- | --- |
| Runs | Runs that ran, drawn day by day. The other figures count only these. | neither |
| Failed | Runs that ended Failed, with `<share> of runs`, drawn day by day. | bad |
| Accepted | Runs whose next act was Closed. Shown when above 0 in the period or the period before. | good |
| Sent back | Runs whose next act was Sent back. Shown in the same way. | bad |
| Merged | Tasks among the runs whose pull request merged, at any time. Shown in the same way. | good |
| Cost | The runs' cost, when all are in one currency. | neither |
| Median run | The median time the runs took, with the p90. | bad |

"By station" lists each station with a run ending in the period, in the order
each one's first run ended, and each station with task failures and no runs.
A station's name opens [its own view](#one-station). "Runs per day" draws its
runs per day, failures in red, beside the change in its runs. Then:

| Column | Counts |
| --- | --- |
| Runs | Runs that ran. |
| Failed | Runs that ended Failed. |
| Stopped | Runs a person stopped. |
| Checks passed, Checks failed | Runs whose check passed or failed. |
| Accepted | Runs whose next act was Closed. |
| Sent back | Runs whose next act was Sent back. |
| Passed | Runs that passed their task to another station. |
| Merged | Tasks among the runs whose pull request merged, at any time. |
| Cancelled | Runs cancelled before they ran. |
| Cost | The runs' cost, when all are in one currency. |

| --- | --- |

they are all in one currency. The setups are compared in the currency most of
them are priced in, or the first in alphabetical order on a tie.

`No priced runs to chart. Show the table for outcomes alone.`

| Small | Up to 50 | Up to 20 |

| Large | More | More |

### Candidates

"Replayed candidates" sets the station configs the team replayed on past tasks
against the station's live config, replayed on the same tasks, before any of
them is applied. It counts [replays](/docs/reference/app/replays), and it has
no filters but the period.

A replay set contains runs, and a task may have more than one run in it. Success
rates average over the set's runs, and comparisons count them. Scored counts
count replay runs, so a replay that replays each run 3 times scores up to three
times the set's runs.

#### Which candidates show

| Candidate | Shows when |
| --- | --- |
| Searched | Its [search](/docs/reference/app/searches) started in the period. |
| Proposed | A replay of it started in the period. With more than one over a set, the newest finished one shows, or else the newest. |

The live config shows only as the replays it was compared with, and the
candidates of
[replay checks](/docs/reference/app/searches#guarding-a-stations-changes) do
not show: a check's verdict is on its pull request and on its
[replay set page](/docs/reference/app/replays#replay-set-page). A set's health
and baseline are current, whatever the period.

The section reads the newest 500 replays started in the period. When there
were more, it shows `Only the latest replays in this period are counted.`

With none, it reads "No candidates replayed in this period", with "Open the
line", which opens one of the team's lines.

## Tools and skills

The Tools and skills tab, `?tab=tools`, has the sections "Skills and tools"
and "Memory". "Skills and tools" counts the runs that ran and ended in the
period. With no skills, unused skills, MCP servers or refusals to list, it
reads "No skills or MCP servers used in this period", with "See the team's
skills".

### Skills

A run is given a skill when its station's config gave it. A run reads a skill
when one of its tool calls does either of these:

- Reads, searches or runs a command on a path inside the skill's folder,
  `.claude/skills/<key>/` or `.spotlight/skills/<key>/`, whatever the run's
  harness. Listing that folder counts; a path to the skills folder itself,
  writing or editing a skill's file, and MCP calls do not.
- Asks Claude Code's `Skill` tool for the skill by its key.

Spotlight's built-in skills are not counted. A key the team does not define is
counted, and shown without a link.

"Skills" lists each skill, most read first, with "Read per week" (the share of
all runs that read it, week by week from Monday, UTC), "Given", "Read" and
"Trend"; its "Runs" is left empty. Unfolding a skill lists each station with
"Runs", "Given", "Read" and "Trend", and no chart. A skill's trend
compares the share of all runs that read it in the last 2 weeks with the weeks
before:

| Trend | When |
| --- | --- |
| Spreading | The share rose by 20 points or more. |
| Fading | The share fell by 20 points or more. |
| Steady | Neither. |

A skill has no trend when the period touches 2 weeks or fewer, or when either
side has fewer than 5 runs. A station's trend is worked out the same way from
its own runs.

"Unused skills" lists the skills the team defines that no run read in the
period. Each links to the skill on the team's Skills page.

### MCP servers

A tool call belongs to an MCP server when Claude Code names the tool
`mcp__<server>__<tool>`, or, for a harness that does not name its tools, when
the call's title is `Tool: <server>/<tool>` or `mcp__<server>__<tool>`. The
title of a call that runs a shell command is not read for a server. The tools
Claude Code names `mcp__acp__Read`, `mcp__acp__Write`, `mcp__acp__Edit`,
`mcp__acp__MultiEdit`, `mcp__acp__Bash`, `mcp__acp__BashOutput` and
`mcp__acp__KillShell` belong to no server.

| Column | Counts |
| --- | --- |
| Runs | Runs that called the server. |
| Calls per run | Calls to it, per run that called it. |
| p50, p95 | How long a finished call took, from when it started working until it completed or failed, so a wait for approval is left out, and so is any time the run was paused. Approximate: each call is counted in one of fixed time ranges, from under 10 ms to 10,000 seconds and over, and the percentile is given as the geometric middle of its range; in the first range, under 10 ms, as 5 ms, and in the last as 10,000 seconds. |
| Error rate | Failed calls, of calls. A call that never finished counts as failed. |
| Failing runs | Runs that failed where the run's last call to the server failed or never finished. |
| Refused | Runs in which a person refused to approve one of its tools. |

Refused calls are left out of every column but "Refused". With no server
called, the card reads `No run called an MCP server in this period.`

A call is refused when the harness asked permission for it and Spotlight's
answer was anything but allow: a refusal, the call being put to a person, or
no answer because the control plane could not be reached. What the tool's
output says does not make a call refused.

### Refused approvals

"Refused approvals" counts, for each tool and server, under "Tool", "Server"
and "Refused", the runs that ran in the period in which a person refused to
approve it. A tool is named by its own name, as in `linear.comment`, or for a
harness permission that names no tool, as `<harness> <kind>`. A tool of no
server reads `–` under "Server".

### Memory

| Tile | Counts |
| --- | --- |
| Active memories | The [memories](/docs/reference/glossary#memory) the team keeps now, whatever the period. |
| Briefed | Memories briefed to the runs that ended in the period, cancelled runs included, each counted once, with `to <n> runs`, the runs that ran they were briefed to. |
| Read | Memories the runs that ended in the period read with [`spotlight recall`](/docs/reference/cli/agent-commands#spotlight-recall), cancelled runs included, each counted once, with `by <n> runs`, the runs that ran that read them. |
| Flagged wrong | Memories a person retired in the period. A memory replaced by a correction is not counted. |
| Solved with memories | `–`, with `No benchmark yet`. |

"Runs with memories and without" sets the period's runs that were briefed or
read a memory against its other runs, under "Without", "With" and "Change",
with the rows of [Impact](#impact) but "Judge score". Only runs that ran are
counted. "Change" reads as under Impact, `Too few runs` and `No change`
included.

"Flagged wrong" lists each memory flagged wrong, the latest first: "Memory",
its handle, linked to the memory, and its text; "Reason", or `–`; "Flagged
by", or "A former member"; and "Date". With none, it reads
`No memory flagged wrong in this period.`

With no active memories, and none briefed, read or flagged wrong in the
period, the section reads "No memories yet", with "Open the team's memory".

## Traces

The Traces tab, `?tab=traces`, lists the team's task
[traces](/docs/reference/glossary#trace), one for each task with a run created,
that is queued, in the past 7, 30 or 90 days, as the period picker says. The span counts back
from now rather than in whole UTC days, and has no period before it. The
traces are not part of the [Insights API](/docs/reference/api/insights).

A chart of "Traces" and "Faults" over the span sits above the list. Each row
shows "Started", "Stations", "Task", "Asked", "Answered", "Faults", "Took" and
"Cost", and opens the task's trace at `/w/<slug>/team/<teamId>/tasks/<taskId>/trace`.
Each row starts with a checkbox. Ticking rows shows a bar reading
`<n> selected`, with "Discuss with the agent", which opens the Agent page with
those traces attached to a new chat, and "Clear selection".

With nothing traced in the span, the tab reads "No traces" and
`No traces in the <span>. Create a task to leave one.`, as in
`No traces in the past 30 days.`, with "Create a task", which opens the
team's first line.
