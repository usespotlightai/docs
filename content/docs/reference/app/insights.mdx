The Insights page sums up how a team's runs, tasks and pull requests went over
a period, against the period before it. It is "Insights" in the team's
sidebar, at `/w/<slug>/team/<teamId>/insights`. The same figures are read
through the [Insights API](/docs/reference/api/insights), and the Candidates
tab through the [Replayed candidates API](/docs/reference/api/replayed-candidates).

Only people on the team, the workspace's owners and admins, and workspace
tokens with the `read` scope can read Insights, on every tab. Anyone else is
answered `404`. See [Team outcomes](/docs/reference/roles-and-permissions#team-outcomes).

## Period

The period picker offers "Past 7 days", "Past 30 days" and "Past 90 days", and
starts at 30 days. A period is whole UTC days, up to and including today. The
period before is as long and ends where the period starts. The period and the
tab are kept in the page's address, as `?tab=<tab>&period=<7d|30d|90d>`.

A figure with a change shows it as a whole percent with `vs last period`, or
`No change`, or `Up from 0`. The change is green when it is good and red when
it is bad. A change in "Spend", in a station's runs and in a station's tasks is
neither.

## What is counted

A run is counted in a period when it ended in it. Except on the Runs tab, only
runs that ran are counted: every run except those withdrawn before they
started. Only task runs at a station are recorded; chat runs are not.

| Term | Meaning |
| --- | --- |
| p50 | The median. With an even count, the rounded mean of the two middle values. |
| p90 | The nearest-rank 90th percentile. |
| Next act | The first thing a person did with the task after the run: the act names the run, or else it follows the task's last run at that station. |
| Person act | A person moving a task, answering, approving, refusing or sending a run back. |
| Activity | A person opening a task, acting on one, or starting an agent chat on the team. |

Outcomes are recorded as runs end and as people act. Nothing that happened
before recording began is counted. A deleted task's runs, pull request and acts
are removed.

The figures on every tab except Pull requests, Candidates and Runs are worked out from the team's latest
20,000 runs that ended in the period and the period before, or the last 30
days where that reaches further. The team's task pull requests, tasks people
acted on, tasks with failures and agent chats over that time are each counted
up to 20,000 too. When any of them was more, the page shows
`Only the latest 20,000 runs over this period and the one before are counted.`

A station that no longer exists shows as "A removed station", a person without
an account as "A former member", and a task no person opened as "No one".

## Overview

| Figure | Counts | A rise is |
| --- | --- | --- |
| Spend | The cost of the runs, when every priced run is in one currency. Otherwise it reads `Nothing was priced` or `Prices came in more than one currency`. | neither |
| PRs merged | Task pull requests merged in the period, with how many closed unmerged. | good |
| Merge rate | Merged, of the task pull requests merged or closed unmerged in the period. | good |
| Cost per merged PR | Spend divided by PRs merged. | bad |
| Task to merge | For pull requests merged in the period, the p50 time from the task opening to the merge, and the p90. | bad |
| Human touches per task | Person acts in the period on the tasks the period's runs worked, per task. | bad |
| Active people | People with an activity in the period. | good |

"Output against cost" charts spend and merged pull requests per UTC day. Spend
is charted only when every priced run in the period is in one currency;
otherwise the card reads
`Merged pull requests per day. <reason>, so spend is left out.`, with the
reason `Nothing was priced` or `Prices came in more than one currency`. A
diamond under a day marks a station's first run with a config it had not run
before, when the station had run with another config earlier. Runs are taken in
the order they started, and the diamond is dated from when that run started, or
when it ended where it never started. A station's first config is not marked.
Hovering over a diamond names each station, with "Before and after" (see
[Before and after](#before-and-after)) and the station's runs with the new
config.

"Stations worth improving" lists stations with at least 3 runs in the period
where a signal is worse than the station's own in the period before, or worse
than the whole team's in the period:

| Signal | Rate |
| --- | --- |
| Sent back | Runs whose next act was Sent back or Refused, of runs. |
| Checks failed | Failed checks, of passed and failed checks. |
| Run failures | Failed runs, of runs. |
| Task failures per run | Task failures raised at the station, per run. |
| Cost per run | Spend, per run. Not compared across currencies. |

A signal is worse when it is more than 1.25 times the value it is compared
with and, for every signal but cost, also at least 5 percentage points higher.
Stations are ordered by how many signals are worse, then by how far the worst
exceeds its comparison, then by runs. Each row shows each worse signal as
`<signal> <now> (was <before>, team <team>)` and "Improve this station", which
opens the Agent page with the station attached. With none, the card reads
`Nothing stands out this period.`

## Flow

"Where tasks wait" shows, for each station in the order its first run ended,
the p50 and p90 of:

| Wait | From | To |
| --- | --- | --- |
| Queued | A run is queued. | The run starts in its image on a runner. |
| Running | The run starts in its image on a runner. | The run ends. |
| In the inbox | The station asks a person. | The first person act on the task after the ask, at any station, before the task's next ask. |

Its table adds "Tasks", "Runs", "Asks" (times the station asked a person) and
"Unanswered".

"Past the last station" follows each task's pull request:

| Figure | Counts | Time shown |
| --- | --- | --- |
| PRs opened | Pull requests opened in the period. | Task to PR: from the task opening to the pull request opening. |
| First reviews | First reviews by a person in the period. Reviews by bots are not counted. | PR to review: from the pull request opening to its first review. |
| PRs merged | Pull requests merged in the period. | Review to merge: from the first review, or from the opening where no person reviewed it, to the merge. |

A task tracks one pull request at a time. A task that opens another pull
request is tracked on the new one.

## Pull requests

Spotlight records every pull request in the repositories the GitHub App is
installed on, as GitHub reports it opening, changing, being reviewed and
closing. What a report says about a pull request is ignored when the pull
request's address disagrees with the report's repository or number. The tab
counts the pull requests a task of the team opened, and those
in a repository one of the team's lines names. At most the newest 20,000 in a
period are counted; past that, the tab shows
`Only the newest 20,000 pull requests in this period are counted.`

Each pull request is written by one of:

| Written by | Label | The pull request |
| --- | --- | --- |
| `spotlight` | Made by Spotlight | A task opened it. |
| `touched` | Reviewed by Spotlight | Someone else opened it, and a Spotlight review task was opened on it. |
| `bots` | Bots alone | A bot opened it, with no Spotlight review task. |
| `people` | People alone | Any other. |

### Spotlight's share

| Figure | Counts |
| --- | --- |
| PRs merged | Pull requests merged in the period, bots' included. |
| Made by Spotlight | Of those, the ones a task opened. |
| Reviewed by Spotlight | Of those, the ones others opened with a Spotlight review task. |
| Spotlight's share | Made or reviewed by Spotlight, of all merged. |

"Week by week" splits the merged pull requests by who wrote them, for each
week from Monday, UTC. "By repository" gives Spotlight's share week by week
for each repository the team's lines name, and any other its tasks merged
into, most merged first.

### Spotlight against people

"Spotlight against people" sets Spotlight's pull requests merged in the period
against people's alone, merged in the same period in the repositories
Spotlight merged into. Bots' pull requests and those with a Spotlight review
task are left out of people's.

| Row | Measures |
| --- | --- |
| Merged | How many merged. |
| Time to merge | From opening to merge: p50 and p90. |
| Time in review | From the first review by a person to merge: p50 and p90. Pull requests no person reviewed are left out. |
| Review rounds | Mean rounds per pull request. |
| Review comments | Mean inline review comments by people per pull request, less those deleted. |
| Revert rate | Pull requests since reverted, of those merged. |

Each approval or request for changes by a person is a review round. Reviews by
people after the last of them, such as reviews that only comment, make one more
round, so a pull request with only comments has 1. Reviews by bots and
dismissed reviews do not count.
"Review depth" gives how many merged pull requests took no rounds, 1, 2, or 3
or more, for the same two groups.

A pull request is a revert when its description has a line
`Reverts <owner>/<repository>#<number>` naming a pull request of the same
repository, or else when its title is `Revert "<title>"`. When a revert merges,
the pull request it names, by number or by the latest merged one with that
title, is marked reverted, and the list shows its state as
`<state>, reverted`.

### Types

"What Spotlight ships" counts merged pull requests by type, Spotlight's against
people's alone, with "Spotlight spent": what all the runs of the tasks behind
Spotlight's pull requests cost. People's here are counted only in the
repositories Spotlight merged into, as in "Spotlight against people" and
"Review depth".

A pull request's type is the first of these that gives one:

1. For Spotlight's, its task's latest change stack: each `change` cohort is
   typed by its title, or else its intent, by the title rules below, and the
   most common type wins. A tie goes to the earlier of Feature, Fix,
   Refactor, Tests, Chore and Other.
2. Its title, by a conventional prefix such as `fix:` or `feat(api)!:`:

   | Prefix | Type |
   | --- | --- |
   | `feat`, `feature` | Feature |
   | `fix`, `bugfix`, `hotfix` | Fix |
   | `refactor`, `perf` | Refactor |
   | `test`, `tests` | Tests |
   | `chore`, `build`, `ci`, `docs`, `style`, `deps`, `revert` | Chore |

3. Its title, by its first words, tried in this order:

   | First words | Type |
   | --- | --- |
   | `revert`, `bump`, `chore`, `upgrade`, `release`, `doc`, `docs` | Chore |
   | `update dependencies`, `deps`, `lock` | Chore |
   | `add`, `write` or `cover` then `test` or `tests`, as in `add unit tests` | Tests |
   | `test`, `tests` | Tests |
   | `fix`, `fixes`, `fixed`, `hotfix`, `patch`, `resolve`, `correct`, `repair` | Fix |
   | `refactor`, `restructure`, `rename`, `extract`, `simplify`, `split`, `inline`, `tidy`, `clean up`, `move` | Refactor |
   | `add`, `implement`, `introduce`, `support`, `allow`, `create`, `build`, `enable`, `show`, `let`, `offer` | Feature |

4. Its branch, by a prefix followed by `/` or `-`:

   | Prefix | Type |
   | --- | --- |
   | `feat`, `feature`, `features` | Feature |
   | `fix`, `bugfix`, `hotfix`, `bug` | Fix |
   | `refactor`, `refactoring` | Refactor |
   | `test`, `tests` | Tests |
   | `chore`, `deps`, `dependabot`, `renovate`, `release`, `docs`, `ci`, `build` | Chore |

5. Otherwise, Other.

Prefixes and words are matched without regard to case.

### The list

"Pull requests" lists every pull request opened or closed in the period, or
still open, the latest first, 50 to a page: its repository, who wrote it, type,
state ("Merged", "Closed unmerged" or "Open"), when it opened, the time to merge
and in review, review rounds and comments, its size as `+<added> −<deleted>`,
and, for Spotlight's, cost. "Repository", "Written by", "Type" and "State"
narrow it; following a figure elsewhere on the tab narrows it by week, reverted,
review rounds or the repositories Spotlight merged into.

### Retention

A pull request is forgotten 180 days after it closed, or, while open, 180 days
after it last changed. One already past that when first heard of is not
recorded. Spotlight's pull requests, and those with a Spotlight review task,
stay counted on this tab after that. Removing the GitHub App's installation
forgets every pull request of the workspace in the same way, trying again for
any that could not be forgotten at once. Closing a workspace disconnects it
from GitHub before its pull requests are removed.

A forgotten pull request is recorded again only when GitHub reports it updated
later than the last update Spotlight had before forgetting it. Spotlight keeps
that last update for 210 days.

## Stations

"The whole team" and "By station" show each station's tally, counted as on the
Station page, with runs and failed runs per day. Rows are in the order each
station's first run in the period ended. A station with task failures and no
runs is listed too.

| Figure | Counts |
| --- | --- |
| Runs | Runs that ran. The other figures count only these. |
| Failed | Runs that ended Failed. |
| Stopped | Runs a person stopped. |
| Checks passed, Checks failed | Runs whose check passed or failed. |
| Accepted | Runs whose next act was Closed or Approved. |
| Sent back | Runs whose next act was Sent back or Refused. |
| Handed on | Runs that passed their task to another station. |
| Merged | Tasks among the runs whose pull request merged, at any time. |
| Withdrawn | Runs withdrawn before they ran. |
| Cost | The runs' cost, when all are in one currency. |
| Median, p90 | The time the runs took. |

Each row also lists its task failures, by source (`run` or `hook:<key>`) and
code, as `<source> · <code> × <count>`, with `· <n> in a row` when one task
raised it more than once; and its failed runs by reason, as `<reason> × <n>`.
A hook the loop guard stopped shows only among task failures.

## Changes

"Config changes" lists the times a station started a new config in the period,
the latest first, by the same rule as the diamonds under "Output against cost".
Each row shows the day, the station, the [changes](/docs/reference/app/tasks-runs-and-the-inbox#config)
from the config of the station's last run before it, or
`No earlier config to compare with`, how many runs came before and after it as
`<n> runs before · <n> runs after`, and "Before and after". With none, the card
reads `No station changed its config in this period.`

### Before and after

"Before and after", on a row of "Config changes" or a diamond on Overview,
opens a panel beside the page, titled `<station>: before and after`. It stays
open across tabs.

The panel counts the station's runs that ended in the period and the period
before, or the last 30 days where that reaches further, by when each started,
or ended where it never started:

| Window | Runs that started |
| --- | --- |
| Before | From the station's previous config change, or its earliest counted run, up to this change, with the config the station ran last before it. |
| After | From this change up to the station's next config change, with the new config. |

| Part | Shows |
| --- | --- |
| What changed | The changes, or `There is no earlier config to compare it with.`, and `Config <fingerprint>, first run on <day>`. |
| Runs before and after | "Before", "After" and "Change" for the rows below. |
| Judge | Only when the station has a judge. While it is trusted, "Before" and "After" each read `<score> over <n> judged`, or `Not judged`. Otherwise `Its scores stay hidden until it agrees with people often enough.` "How often the judge agrees with people" opens the Station page at its judge. |

| Row | Counts |
| --- | --- |
| Runs | Runs that ran. The other rows count only these. |
| Sent-back rate | Runs whose next act was Sent back or Refused, of the runs whose next act is known. |
| Accepted rate | Runs whose next act was Closed or Approved, of the runs whose next act is known. |
| Checks-failed rate | Failed checks, of passed and failed checks. |
| Failed rate | Runs that ended Failed, of runs. |
| Merged rate | Tasks whose pull request merged, of the tasks of the runs whose pull request merged or closed unmerged. |
| Cost per run | The cost of the priced runs, per priced run. |

Each row but "Runs" counts, on each side, the runs settled for it, as for
[station alerts](/docs/reference/app/tasks-runs-and-the-inbox#station-alerts).
"Change" gives each row's verdict: the change as a whole percent, green when
it is better and red when it is worse, or `No change`. It reads `Too few runs`
when either side has fewer than 5 settled runs, and for cost per run when the
two sides are priced in different currencies.

A judge score is the mean of the judge's scores on the station's current
rubric, as a share of its scale: Yes is 100% and No 0%; on 1 to 5, 1 is 0% and
5 is 100%. See [Agreement](/docs/reference/app/tasks-runs-and-the-inbox#agreement)
for when a judge is trusted.

The panel ends with "Open the station" and "Improve this station". A change
no longer in the period reads `This change is not in the period any
more.`

### Harness, model, effort and profile

This card sets how runs turned out against what they cost, for each setup: a
harness, model, effort and [harness profile](/docs/reference/glossary#harness-profile)
together, as each run recorded them. It counts the runs that ran and ended in
the period; a run with no recorded setup is left out.

| Filter | Narrows to |
| --- | --- |
| Outcome | The outcome charted: "Accepted", the default, "Sent back", "Handed on", "Checks passed", "Merged", or "Judge score" when any setup has judged runs. |
| Station | "Every station", or the runs at one work station. |
| Task size | "Every size", or the runs of one size. |

| Outcome | Of a setup's runs |
| --- | --- |
| Accepted | Runs whose next act was Closed or Approved, of runs. |
| Sent back | Runs whose next act was Sent back or Refused, of runs. Lower is better. |
| Handed on | Runs that passed their task to another station, of runs. |
| Checks passed | Passed checks, of passed and failed checks. |
| Merged | Tasks whose pull request merged, of the tasks the runs worked. |
| Judge score | The mean judge score, as in [Before and after](#before-and-after). |

Judge scores are counted only with a station picked, and only while that
station's judge is trusted. With "Every station", the card reads
`Pick a station to compare judge scores.` With a station picked that has a
judge and runs in the period, the card adds
`Judge scores count only where a station's judge agrees with people often enough.`
and names the station, linked to its judge, as `trusted` or `hidden`.

A setup's cost per run is the cost of its priced runs, per priced run, when
they are all in one currency. The setups are compared in the currency most of
them are priced in, or the first in alphabetical order on a tie.

For each outcome, a setup is on the frontier when it has at least 3 runs, a
cost per run in that currency and a value, and no other such setup costs no
more and does as well or better, with either a lower cost or a better value.

The chart plots each setup priced in that currency, cost per run across, the
outcome up and its size by runs, and joins "On the frontier" with a dashed
line. Hovering over a setup shows `<outcome> <value> · <cost> a run` and its
runs. With no runs, the card reads
`No runs match these filters in this period.`, and with none priced,
`No priced runs to set against their cost. Show the table for the outcomes alone.`
The table lists every setup, most runs first, with "Runs", "Cost per run" and
each outcome; a setup on the frontier of the charted outcome is marked
`frontier`. A setup reads as harness, model, `<effort> effort` and
`<profile> profile`, as far as each is set.

A run's size is told by the lines it changed: the lines taken out and put in
across its file changes, each file compared from before its first change to
after its last. A run that changed no lines is told by its steps, over the
attempts it kept.

| Size | Lines changed | Steps, for a run that changed none |
| --- | --- | --- |
| Small | Up to 50 | Up to 20 |
| Medium | Up to 400 | Up to 80 |
| Large | More | More |

A run whose cost was never worked out has no size and is left out when a size
is picked.

### Replayed candidates beside the setups

With a station picked, the chart also draws the station's replayed candidates,
the same points the [Candidates](#candidates-chart) tab draws, as a series of
its own. They are drawn hollow and listed after `Replayed:` in the legend, by
shape:

| Shape | Point |
| --- | --- |
| Diamond | "Live config, replayed": the live config replayed, as on the Candidates tab. |
| Circle | "Searched": a candidate a search proposed. |
| Square | "Proposed": a [replay candidate](/docs/reference/api/replay-candidate) proposed by a person or Terraform. |

A replayed point's height is its replay success: the share of the past runs
it was scored on that succeeded, scored by the candidate's own checks and
judge, whatever outcome the card charts. It is not the live outcome the setups
show. While replayed points are drawn, the side of the chart is labelled
`<outcome> · replay success`, the card's description adds `replayed points show
replay success on past tasks instead`, and the note under the chart reads
`Replayed points' height is replay success on up to <n> runs of past tasks,
scored by each candidate's own checks and judge`, then says it is not the live
outcome and that the task-size filter does not apply to them. `<n>` is the
most runs any replayed point was scored on.

A searched candidate's height is its search score. Its held-out score is never
drawn; hovering over it shows `held out <share> of <n> held-out runs` once it
has one. Hovering over a replayed point also shows `Replayed <name>`, `Replay
success <share> of <n> scored runs · <cost> a run`, and the replay set as
`over <set>`.

Only replayed points whose replay has finished and that have a cost per run in
the currency the setups are compared in are drawn. "Task size" does not narrow them, and they are not
joined to the setups' frontier. While the card charts "Sent back", where lower
is better, replayed points are not drawn.

| Note under the chart | When |
| --- | --- |
| `Pick a station to see its replayed candidates beside its live setups.` | "Every station" is picked and the team has replayed candidates in the period. |
| `Replayed points show success, so they're hidden while the chart shows Sent back.` | "Sent back" is charted. |
| `Not priced, so not shown: <names>` | Replayed points with no cost per run. |
| `Priced in another currency, so not shown: <names>` | Replayed points priced in another currency than the setups. When the setups have no currency, it reads `Nothing here is priced to set them against, so not shown: <names>`. |
| `Not finished, so not shown: <name> (<state>)` | Replayed points whose replay has not finished, with its state in lower case, as in `(running)` or `(over budget)`. |
| `Not scored yet, so not shown: <names>` | Replayed points whose replay finished with no run scored. |
| `This station's replayed candidates are not drawn, as no live setup here has a priced outcome to set them beside. The table lists them.` | No live setup at the station has a priced outcome to chart. |
| `The replayed candidates could not be loaded.`, with a way to try again | Reading them failed. The rest of the tab still shows. |

"Show table" adds a "Replayed" table under the setups', with "Replayed" (the
candidate's name, or the live config's), "Kind", "Replay set", "Past tasks
scored" (the runs scored), "Cost per run", "Replay success" and "Held out", for
the points the chart draws.

With no config changes and no setups in the period, the tab reads
`Once stations run tasks, their config changes and how each harness, model and effort did show here.`

## Candidates

The Candidates tab sets the station configs the team replayed on past tasks
against the station's live config, replayed on the same tasks, before any of
them is applied. Nothing on it was applied to a station. It counts
[replays](/docs/reference/app/replays), not the team's runs, so the
20,000-run limit does not apply, and it has no filters but the period.

A replay set holds runs, and a task may have more than one run in it. Success
rates average over the set's runs, and comparisons count them. Scored counts
count replay runs, so a replay that replays each run 3 times scores up to three
times the set's runs.

### Which candidates show

| Candidate | Shows when |
| --- | --- |
| Searched | Its [search](/docs/reference/app/searches) started in the period. |
| Proposed | A replay of it started in the period. With more than one over a set, the newest finished one shows, or else the newest. |

The live config shows only as the replays it was compared with, and the
candidates of
[replay checks](/docs/reference/app/searches#guarding-a-stations-changes) do
not show: a check's verdict is on its pull request and under "Checks" on its
[replay set page](/docs/reference/app/replays#replay-set-page). A set's health
and baseline are as they stand now, whatever the period.

The tab reads the newest 500 replays started in the period. When there were
more, it shows
`Only the latest replays over this period are counted; the oldest are left out.`

With none, the tab reads "No candidates replayed in this period", with "Open
the line", which opens one of the team's lines.

### Station cards

One card per work station with a candidate in the period, the station with
the newest replay first. A card is titled by the station, or "A removed
station", and reads `<line> · Replay success on past tasks against cost per
run, scored by each candidate's own checks and judge. Nothing here was applied
to the station.` Within it, each replay set the candidates were replayed over
has a part of its own, the newest replayed first, headed by its health:

| Part | Shows |
| --- | --- |
| Name | The set's name, linked to its [page](/docs/reference/app/replays#replay-set-page). "Guards changes" when the set [guards the station's changes](/docs/reference/app/searches#guarding-a-stations-changes), and "Station gone" when its station has left the line. |
| Health | `<n> tasks`, the different tasks its runs worked, with `(<m> runs)` when it holds more runs than tasks, then when its runs ended, then `last added <when>`, joined by `·`, as in `24 tasks (27 runs) · ended 3–41 days ago · last added 2 days ago`. "No tasks yet" for an empty set. |
| Noise | The set's [noise](/docs/reference/app/replays#noise), as `Success moved <n> pts between <m> copies, ` followed by `more than the <min_gain> the line counts as real, so one copy can't tell a real gain from chance` or `within the <min_gain> the line counts as real`, or `Noise not measured`. |
| No baseline | `The live config was never replayed over it, so nothing is compared with live.` when the set has no [baseline](/docs/reference/glossary#baseline). |

When the runs ended reads `ended today`, `ended <n> days ago`,
`ended today to <n> days ago`, or `ended <newest>–<oldest> days ago`, counted
in UTC days, from the newest and oldest of the set's runs.

### Candidates chart

Each set's chart plots its candidates and the live config, cost per run along
the bottom and replay success up the side, from 0 to 100%. Replay success is
a replay's [success](/docs/reference/app/replays#success), scored by the
candidate's own checks and judge: with one copy of each run, the share of the
runs it was scored on that succeeded:

| Shape | Point | Height |
| --- | --- | --- |
| Diamond | "Live config, replayed (the search's tasks)": the live config a search started from. One per search; with more than one search over the set, `(tasks of the search on <day>)`. | Its search score: the live config's success on that search's searched runs. |
| Diamond | "Live config, replayed (whole set)": the set's baseline. Drawn only when the set has a proposed candidate. | Its success over the whole set. |
| Circle | "Searched". | Its [search score](/docs/reference/app/searches#scores), on its search's searched runs. |
| Square | "Proposed". | Its replay's success over the set. |

So a searched candidate is drawn beside the live config on the same runs, and a
proposed candidate beside the baseline. A searched candidate on its search's
[frontier](/docs/reference/app/searches#frontier) is highlighted, as "On the
search's frontier" in the legend. The frontier of each search, its live
config diamond among them, is joined by a dashed line, one line per search.

Hovering over a point shows `Replayed <name>`, `Replay success <share> of <n>
scored runs · <cost> a run`, the set as `over <set>`, its held-out score as
`held out <share> of <n> held-out runs` once it has one, and `on the
search's frontier` for a frontier candidate.

The chart is in the set's currency: its baseline's, or else that of its newest
candidate. Only candidates whose replay has finished are drawn. Points left out
are listed under the chart: `Not priced, so not shown: <name> (<success>)` for
those with no cost per run, because some of the replay's spend went unpriced;
`Priced in another currency, so not shown: <name> (<success>)`;
`Not finished, so not shown: <name> (<state>)`, with the replay's state in
lower case; and `Not scored yet, so not shown: <name>` for a finished replay
with no run scored. With nothing
to draw, the chart reads `Nothing replayed over it has a priced score yet.
Show the table for what there is.`

### Candidates table

"Show table" lists each set's health, then its baseline and candidates. The
first row, "Live config, replayed (whole set)", is linked to the baseline's
[replay page](/docs/reference/app/replays#replay-page), with
`<share> (<low>–<high>%) of <n> runs scored`, or "Not scored yet", and
`<cost> a run`, or "Unpriced". Then
each candidate, the newest replayed first, shows:

- its name, "Searched" or "Proposed", "On the frontier" for a frontier point,
  and its replay's [state](/docs/reference/app/replays#replay-states) until

- for a searched candidate, its agent's hypothesis;
- `Changed from live:` with one phrase per change, as the Run page's

  "The same as the live config.";
- "Replayed": the tasks its replay covers, with the runs when there are more,
  as for a set's health;
- "Search score" for a searched candidate, "Replay success" for a proposed
  one, as `<share> (<low>–<high>%) of <n> runs scored`, with its 95% range,
  or "Not scored yet";
- for a searched candidate, "Held out", apart from its search score:
  `<share> (<low>–<high>%) of <n> held-out runs`, "Replaying" while its held-out replay is queued or running,
  "Not held out" when it was not replayed on the held-out tasks, or `–`;
- "Cost per run", or "Unpriced";
- once it has runs compared with the baseline, its success against the live
  config's on those runs alone, as
  `72% (60–84%) vs live 56% (40–70%) on the same 18 runs`, then its

- `<n> regressions over <m> runs compared`, counting the runs it
  [regressed](/docs/reference/app/replays#regressions) on of those compared
  with the baseline, or "No runs compared yet", or "No baseline to compare
  with";
- links:

## Tools

The Tools tab counts the runs that ran and ended in the period.

### Skills

A run is given a skill when its station's config gave it. A run reads a skill
when one of its tool calls does either of these:

- Reads, searches or runs a command on a path to a file inside the skill's
  folder, `.claude/skills/<key>/` or `.spotlight/skills/<key>/`, whatever the
  run's harness. Listing a skills folder, writing or editing a skill's file,
  and MCP calls do not count.
- Asks Claude Code's `Skill` tool for the skill by its key.

Spotlight's built-in skills are not counted. A key the team does not define is
counted, and shown without a link.

"Skills" shows, for each skill, most read first, the runs that read it out of
all runs, week by week from Monday, UTC, with how many runs read it and how
many were given it, in all and at each station. A skill's trend compares the
share of all runs that read it in the last 2 weeks with the weeks before:

| Trend | When |
| --- | --- |
| Spreading | The share rose by 20 points or more. |
| Fading | The share fell by 20 points or more. |
| Steady | Neither. |

A skill has no trend when the period touches 2 weeks or fewer, or when either
side has fewer than 5 runs. A station's trend is worked out the same way from
its own runs.

"Unused skills" lists the skills the team defines that no run read in the
period. Each links to the skill on the team's Skills page.

### MCP servers

A tool call belongs to an MCP server when Claude Code names the tool
`mcp__<server>__<tool>`, or, for a harness that does not name its tools, when
the call's title is `Tool: <server>/<tool>` or `mcp__<server>__<tool>`. The
title of a call that runs a shell command is not read for a server. The tools
Claude Code names `mcp__acp__Read`, `mcp__acp__Write`, `mcp__acp__Edit`,
`mcp__acp__MultiEdit`, `mcp__acp__Bash`, `mcp__acp__BashOutput` and
`mcp__acp__KillShell` belong to no server.

| Figure | Counts |
| --- | --- |
| Runs | Runs that called the server. |
| Calls per run | Calls to it, per run that called it. Refused calls are left out. |
| p50, p95 | How long a finished call took, from when it started working until it completed or failed, so a wait for approval is left out, and so is any time the run was paused. Approximate: each call is counted in one of fixed time ranges, from under 10 ms to over 10,000 seconds, and the percentile is given as the geometric middle of its range. |
| Error rate | Failed calls, of calls. A call that never finished counts as failed. |
| Failing runs | Runs that failed where the run's last call to the server failed or never finished. |
| Refused | Runs in which a person refused to approve one of its tools. |

A call is refused when the harness asked permission for it and Spotlight's
answer was anything but allow: a refusal, the call being put to a person, or
no answer because the control plane could not be reached. What the tool's
output says does not make a call refused.

### Refused approvals

"Refused approvals" counts, for each tool and server, the runs that ran in the
period in which a person refused to approve it. A tool is named by its
own name, as in `linear.comment`, or for a harness permission that names no
tool, as `<harness> <kind>`.

## Memory

| Figure | Counts |
| --- | --- |
| Standing memories | The [memories](/docs/reference/glossary#memory) the team keeps now, whatever the period. |
| Briefed | Memories briefed to the runs that ended in the period, each counted once, with how many of those runs they were briefed to. |
| Read | Memories the runs that ended in the period read with [`spotlight recall`](/docs/reference/cli/agent-commands#spotlight-recall), each counted once, with how many of those runs read them. |

"Runs with memories and without" sets the period's runs that were briefed or
read a memory against its other runs, under "Without", "With" and "Change",
with the rows of [Before and after](#before-and-after). Only runs that ran are
counted.

"Flagged wrong" lists each memory flagged wrong, the latest first: its handle,
linked to the memory, its text, the reason in quotes or `No reason given`, who
retired it, or "A former member", and the day. With none, it reads
`Nobody flagged a memory wrong in this period.`

"Memory benchmark" reads `No benchmark yet.` Spotlight does not run a memory
benchmark yet.

With no standing memories, and none briefed, read or flagged wrong in the
period, the tab reads "No memories yet", with "Open the team's memory".

## Runs

The Runs tab lists every run that ended in the period, withdrawn runs included,
newest first, 50 to a page. Each row shows the outcome, linked to the run, the
failure, station, the person who opened the task, harness, model, how long the
run took, cost and when it ended.

"Station" (work stations only) and "Outcome" (Completed, Failed, Stopped,
Abandoned, Withdrawn, Superseded) narrow the list. Following a figure on
another tab narrows it further, shown as a pill:

| Pill | Narrows to runs |
| --- | --- |
| Line | On the line. |
| Pull request | Whose task's pull request is now Merged, Closed unmerged or Open. |
| Then | Whose next act was the one named. |
| Asked a person | Of tasks that asked a person in the period. |
| Harness | Run by the harness. |
| Model | Run with the model. "Harness default" is a run with no model set. |
| Repository | On the repository. "No repository" is a run on none. |
| Config | With the [config fingerprint](/docs/reference/glossary#config-fingerprint). |
| Task, Tasks | Of the task, or of up to 200 tasks. |
| Person | Of tasks the person opened. |
| Day | That ended on the UTC day. |
| Week of | That ended in the week starting that Monday, UTC. |
| Given skill, Read skill | Whose station gave the skill, or that read it. |
| Called | That called the MCP server. |
| A call failed on | With a failed call to the MCP server. |
| Last call failed on | That failed where their last call to the MCP server failed. |
| Refused, Refused on | Where a person refused the tool, or a tool of the MCP server. |

Every filter narrows the others. The skill, MCP server and refusal filters
leave out withdrawn runs.
