A replay check replays a planned change of a work station on the
[replay set](/docs/reference/app/replays#how-spotlight-keeps-the-set) Spotlight keeps for the
station, compares it with the live config, and
gives a result under the line's [`replay_check`](/docs/reference/terraform/line#replay-check-fields).
[`spotlight replay check`](/docs/reference/cli/replay-command#spotlight-replay-check)
calls these endpoints from CI. They sit under `/api/teams/{teamId}`, answer
JSON, and answer errors as `application/problem+json`, as on the
[resource API](/docs/reference/api/resource-api#errors).

## Endpoints

| Method and path | Returns |
| --- | --- |
| `POST /replay-checks` | `201` and a [check](#check), or `200` and the check this change already has. See [Start a check](#start-a-check). Requires `Idempotency-Key`. |
| `GET /replay-checks/{checkId}` | A [check](#check) and its result. |

## Start a check

```json
{
  "lineId": "<line id>",
  "stationKey": "build",
  "station": {
    "key": "build",
    "name": "Build",
    "kind": "work",
    "harness": "claude-code",
    "prompt": "Build it, then drain the queue.",
    "passesTo": ["ship"]
  },
  "line": {
    "repositories": [{ "name": "acme/api", "setup": "npm ci" }]
  },
  "reference": { "commit": "4f7c2a9e1b3d", "pullRequest": 42 },
  "repeats": 1
}
```

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `lineId` | string | required | The line the station is on. |
| `stationKey` | string | required | The station the change plans, by its key. |
| `station` | object | required | The station block as the plan would apply it, in the shape of one entry of a line's `stations`. |
| `line` | object | none | The line's repositories as the plan would apply them, each with its `image` and `setup`, as `{ "repositories": [...] }`. At most 64,000 characters. Without it, the live line's. |
| `reference.commit` | string | none | The commit that plans the change, a hex sha of 7 to 64 characters. |
| `reference.pullRequest` | number | none | The pull request that plans the change. |
| `repeats` | number | `1` | How many times the check replays each run of the set, 1 to 5. The line's ceiling covers every repeat. |

The check:

1. Reads `replay_check` from the line as it is applied, never from the plan.
2. Replaces the planned block's `check`, `judge`, `diffs` and `runners` with
   the live station's, and records in `scoringPinnedToLive` each one the plan changed.
3. Checks the block as the line would be with the station replaced, by every
   rule of [`spotlight_line`](/docs/reference/terraform/line), each problem at
   its path under `station`.
4. Replays it, under the planned repositories, images and setup commands, on
   every run of the station's set, `repeats` times, on the team's runners. When
   the set has no baseline of the current live config with at least as many
   repeats, it also starts a baseline replay of the live config with the same
   `repeats`. See [Ceiling](#ceiling).

A change that changes nothing about how the station's runs go fails with
`409` and the type `urn:spotlight:problem:nothing-to-replay`.

A change already checked is answered with that check, `200` and `reused:
true`, while the earlier check is running, passed or failed, and only if it
replayed the same runs of the set against the same live config, the same
threshold, the same scoring and the same `repeats`. Otherwise a new check starts, with the next
`attempt`. A repeated request with the same `Idempotency-Key` answers `201`
with the check it started and the header `Idempotent-Replayed: true`.

## Ceiling

The line's `replay_check.ceiling` caps each replay a check starts, each on its
own:

- the replay of the planned change, which every check starts;
- the baseline replay of the live config, only when the station's set has no
  baseline for the current live config with at least as many repeats of each
  run. A baseline already there costs the check nothing.

So one check spends at most twice the ceiling, plus what runs already running
spend after a replay reaches it. A run whose cost is not reported, or is in
another currency, counts as the ceiling divided by the number of runs in the
set times `repeats`: `threshold.unpricedRun`. When a replay reaches its ceiling, no more of its
runs start, and runs already running finish, so it can end a little over. A
check whose replay reached its ceiling is `undecided`, `over-ceiling`, unless
it has already `failed`.

The check replays a candidate Spotlight names `Planned change, PR #<n>`, or
after the commit's first 7 characters, or the date.

## Check

| Field | Type | Description |
| --- | --- | --- |
| `id`, `teamId`, `lineId`, `stationId`, `stationKey` | string | |
| `setId` | string | The replay set Spotlight keeps for the station. |
| `candidateId`, `replayId` | string | The planned candidate and its replay. |
| `baselineReplayId` | string or null | The replay of the live config it is compared with. Null while it is being started. |
| `attempt` | number | Counts checks of the same change against the same live config, from 1. |
| `reference` | object | `{ commit, pullRequest }`. |
| `liveFingerprint`, `candidateFingerprint` | string | The [config fingerprints](/docs/reference/glossary#config-fingerprint) of the live and planned station. |
| `scoringPinnedToLive` | array of strings | What the plan changed of `check`, `judge`, `diffs` and `runners`, which the check pinned to the live station's values. |
| `threshold` | object | `{ maxRegressions, minGain, ceiling, unpricedRun }`, from the live line when the check started. `minGain` is its `replay_check.min_gain`; `ceiling` caps each replay of the check; `unpricedRun` is what an unpriced run counts against it, or null once the replay is gone. |
| `repeats` | number | How many times the check replays each run of the set. |
| `gain` | object or null | The candidate's gain in success over the baseline, `{ gain, low, high, significance, minGain, tasks }`: the gain and its 95% interval as shares, `better`, `worse` or `within-noise` as in [Gains](/docs/reference/app/replays#gains), the line's `min_gain`, and the tasks scored on both sides. It does not decide `result`. Null with no baseline or no replay, and while no task was scored on both sides. |
| `result` | string | See [Results](#results). |
| `undecidedBecause` | string or null | See [Results](#results). |
| `taskCount` | number | How many tasks the set replays. |
| `compared` | number | How many were scored on both sides. |
| `candidate`, `baseline` | object | Each `{ state, entries, scored, succeeded, successRate, interval, tasksScored, spent }`. `state` is the replay's state, `queued`, `running`, `finished`, `stopped` or `ceiling-reached`, or null once it is gone. `entries`, `scored` and `succeeded` count repeats; `successRate` is the share of scored repeats that succeeded, `interval` its 95% interval `{ low, high }`, and `tasksScored` counts tasks with a scored repeat. |
| `tasks` | array | Each task of the set, the regressed tasks first: `{ taskId, originalRunId, title, regressed, live, candidate }`. See [Task rows](#task-rows). |
| `reused` | boolean | `true` when starting a check answered one this change already had. Always `false` on a read. |
| `createdAt` | string | An RFC 3339 time. |

## Task rows

Each item of `tasks` gives the task's `title` (null once the task is deleted),
`regressed`, `true` when the candidate did worse than the live config on the
task as in [Regressions](/docs/reference/app/replays#regressions), and one side
each for the live config and the candidate:

| Field | Type | Description |
| --- | --- | --- |
| `result` | string | `succeeded` or `failed` when every repeat agrees; `mixed` when the repeats disagree; `unscored` when nothing scored the run; `pending` while the replay runs; `absent` when the side did not replay the task. |
| `successRate` | number or null | The share of the scored repeats that succeeded, from 0 to 1. |
| `reason` | string | Why the side got its result, in one line of at most 200 characters, as in `Judge failed it: The tests do not cover the new branch.` |

`reason` is one [result reason](/docs/reference/app/replays#results) of a
repeat that shows the side's result: a failed repeat for `failed` and `mixed`.
It reads the reason, then a colon and its detail when it has one:

| Code | Reads |
| --- | --- |
| `unreplayable` | `Spotlight could not replay or start the run` |
| `not-run` | `The run did not start` |
| `run-failed` | `The run failed` |
| `run-stopped` | `The replay stopped before the run finished` |
| `asked-a-person` | `The run asked a person, and a replay cannot answer` |
| `check-failed` | `Checks failed` |
| `check-skipped` | `Checks could not run` |
| `change-not-generated` | `Spotlight could not make the change` |
| `no-change` | `The run changed no files for the checks` |
| `no-change-stack` | `The change did not get to Spotlight` |
| `judged` | `Judge passed it` |
| `judge-failed` | `Judge failed it` |
| `unjudged` | `Judge could not judge it` |
| `nothing-judges` | `No check or judge scores this station` |

Without a reason, it reads `Checks passed.`, `The run failed.`, `The repeats
did not agree.`, `Nothing scored the run.`, `The replay has not finished.` or
`Not replayed.`, by `result`. The same rows make up the task-by-task table of
[`spotlight replay check`](/docs/reference/cli/replay-command#output) and of a
[config pull request](/docs/reference/app/searches#the-pull-request).

## Results

| Result | When |
| --- | --- |
| `failed` | More tasks regressed than `maxRegressions` allows. Decided as soon as it happens, while replays still run. A task counts only once each of its repeats, on both sides, has ended. |
| `running` | The change's replay or its baseline is queued or running, or the baseline is still being started. |
| `undecided` | See below. |
| `passed` | None of the above. |

| `undecidedBecause` | When |
| --- | --- |
| `replay-gone` | The change's replay is gone. |
| `stopped` | The change's replay was stopped. |
| `over-ceiling` | The change's replay reached its ceiling. |
| `no-baseline` | There is no replay of the live config to compare with. |
| `baseline-unfinished` | The live config's replay did not finish. |
| `too-few-scored` | Fewer than half the tasks were scored on both sides. |

## Who may read and change

Reading needs a person on the team or an owner or admin of its workspace, or a
[workspace token](/docs/reference/api/workspace-token) of the team's workspace
with the `read` scope. Anyone else is answered `404`. Starting a check also
needs `plan`. See
[Team outcomes](/docs/reference/roles-and-permissions#team-outcomes).

Starting a check is recorded as a
[configuration change](/docs/reference/api/resource-api#configuration-changes)
of the kind `replay-check`.

## Errors

| Status | Cause |
| --- | --- |
| `401` | No session or token, or an unknown token. |
| `403` | A change by a caller who may read the team but not plan. |
| `404` | The team, line, station or check is not one the caller may see, as in `Replay check <checkId> not found.` |
| `409` | A line with no `replay_check` (`Line <lineKey> has no replay_check block. Please add one with max_regressions, ceiling and currency.`). A station with no replay set yet, or whose set's station has left its line (`Station <stationKey> has no replay set yet. Spotlight keeps one after a run of the station ends.`). A station whose set has no runs (`Station <stationKey> has no runs in its replay set yet.`). A change with nothing to replay, `nothing-to-replay`: `There is nothing to replay. The plan changes nothing that affects how the station's runs go.`, or `There is nothing to replay. A check pins these changed fields to their live values: <fields>`. |
| `422` | The planned block is not one the line takes, each problem at its path under `station`. A missing `lineId` (`Line ID must name the line of the station.`) or `stationKey` (`Station key must be the key of the planned station.`), or a `reference` or `line` not in its form. `repeats` not a number (`Repeats must be a number.`) or out of range (`Replay check repeats must be from 1 to 5.`). The `409` causes are checked first, so a check of a line with no `replay_check`, of a station with no set or an empty set, or with nothing to replay answers `409` whatever its `repeats`. |
