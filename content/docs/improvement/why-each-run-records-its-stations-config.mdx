A station's config is everything it supplies to a run: the prompt, the harness,
model and effort, the harness profile, the line's image, repositories and setup
commands, skills, tools, whether decisions are generated and memories are
drafted, and the judge that scores its runs. Changing any of it is how a team
makes a station better. Whether a change helped only shows in the runs after it,
and only if each run says which config it ran. So every task run records its
station's config as it is queued, and a SHA-256 of it, the [config
fingerprint](/docs/reference/glossary#config-fingerprint).

## Measure before improving

Without that record, a run that went badly after a prompt edit might be down
to a harder task rather than the edit, and nothing would tell the two apart.
With it,
Insights can set the runs of one config beside the runs of the config
before it, and a person or an agent can read the difference in how they turned
out. The agent that improves a station starts from the same record, through
`spotlight history`, and is told to check what changed between configs before
it blames the model.

Spotlight's own loop that improves a station keeps a person in it: Spotlight
searches for a better config and opens a pull request, and a person merges it.
See [How Spotlight improves a station](/docs/improvement/how-spotlight-improves-a-station).
In the docs' view, such a loop needs this record to measure each change
against, so the record comes first.

## What the fingerprint leaves out

The fingerprint describes the station alone. A task's title, description and
marks do not affect it, so runs on different tasks at an
unchanged station share one fingerprint and can be compared.

Spotlight's built-in skills are left out too. They change with Spotlight
releases, and counting them would start a new group with every release although
nothing about the station changed.

Values in a harness profile's MCP server environment are stored only as SHA-256
hashes. A changed value still changes the fingerprint, and the value itself is
never stored in the recorded config.

## Groups follow changes

Insights groups a station's runs that started one after another with the same
config, under "Runs by config". A config that comes back after another starts
a new group, because the view answers what happened after each change.

Outcomes are recorded as they happen: when a run ends or is superseded, when
its change is checked, when a person acts on the task, and when its pull
request opens, merges or closes. Nothing is reconstructed afterwards, so a run that ended before
recording began has no outcome.

## Where each run started

A task's run also records where it started: the workspace archive it restored,
if any, and the commit each repository was checked out at. The config says
what the station supplied to the run; the starting point says what the run began
from. With both stored, a past task can be run again from the same start under
another config, which is what a
[replay](/docs/improvement/why-changes-are-replayed-on-past-tasks) does. A change can
then be tried on tasks whose outcome is already known, before it reaches new
ones.

## The agent proposes, a person applies

The agent in a planning chat about a station proposes one change at a time, as a diff of the
station's Terraform. With one change per config, the next group's tally speaks
to that change alone. The agent cannot apply it, because a station's
configuration is written only through Terraform or the resource API.
[Why configuration lives in Terraform](/docs/configuration/why-configuration-lives-in-terraform)
gives the reasons.
