title: Search for a better station config
description: Have an agent propose changed configs for a work station, replay each on the station's past tasks, act on what it finds when it stalls, and open a pull request for the one you pick.
---

Use this when you want Spotlight to look for a better config for a work
station, instead of writing each change yourself. A search is a series of
rounds. In each round an agent studies how the station's past runs went and
proposes a few changed configs, called candidates, and Spotlight
[replays](/docs/improvement/replay-past-tasks-against-a-station-change) each
one on most of a replay set's tasks. Nothing is applied: when you pick a
candidate, Spotlight opens a pull request in the repository that holds the
line's Terraform. You need:

- To be on the team, or an owner or admin of the workspace.
- A replay set at the station with runs of at least 5 different tasks. See
  [Pick the tasks to replay](/docs/improvement/replay-past-tasks-against-a-station-change#pick-the-tasks-to-replay).
  [Check the set's health](/docs/improvement/replay-past-tasks-against-a-station-change#check-the-sets-health)
  first, so you know whether its results can be trusted.
- A host serving the workspace with the station's harness, and the harness you
  want the search's agent to run on. See [Install a host](/docs/hosts/run-a-host).
- To open pull requests from it: the line's Terraform in a GitHub repository
  that Spotlight's GitHub App is installed on, and a `source` block on the
  line that names the file. See
  [Name the file that holds the line](#name-the-file-that-holds-the-line).

## Name the file that holds the line

Do this once per line, before you pick a candidate.

<Steps>
<Step>

Add a `source` block to the line's `spotlight_line` resource, naming the
repository and the `.tf` file, from the repository's root, that holds the
resource:

```hcl
resource "spotlight_line" "core_delivery" {
  # ...

  source {
    repository = "acme/platform"
    path       = "teams/core/delivery.tf"
  }
}
```

</Step>
<Step>

Run `terraform apply`. On the Station page, under **Searches**, the last line
now reads **A picked candidate opens a pull request against** the repository
and file.

</Step>
</Steps>

If the station's `prompt`, or another attribute a search may change, is read
from a file, write it as `file("${path.module}/<path>")`, so Spotlight can
follow it.
See [`source`](/docs/reference/terraform/line#source-fields) for the rules.

## Start a search

<Steps>
<Step>

Open the line's board and select the station's name. Under **Searches**,
select **Start a search**.

If the button is greyed out, the line under it says why, such as **No replay
set covers 5 different tasks yet.** Add runs of more tasks to a set, or wait
for the station's search under way to end.

</Step>
<Step>

Under **Search on**, choose the replay set. A set with runs of fewer than 5
different tasks can't be chosen: a search keeps about 30% of the tasks back to
check its results on, and needs some left to search on. See
[Why a search holds tasks back](/docs/improvement/why-a-search-holds-tasks-back).

</Step>
<Step>

Set the budget:

- **Iterations**: how many rounds, so how many times the agent runs, from 1
  to 10.
- **Candidates per iteration**: how many candidates each round may propose,
  from 1 to 5.
- **At once**: how many of the search's replay runs run together, from 1 to
  10. They run beside the team's other replays, below every task run.
- **Repeats**: how many times each of its replays replays each run, from 1 to
  5. The live config's replay, every candidate's and the held-out replays all
  take this many copies. More copies narrow the range around each score, and
  the runs and spend grow with them.
- **Ceiling**: the most the whole search may spend, its replays and its
  agent's runs, and its currency, as in `20.00` and `USD`.

</Step>
<Step>

Under **Aim for**, choose what counts as better:

- **More success**: candidates that succeed more often.
- **The same success for less**: candidates that succeed as often as the live
  config, within noise, and cost less a run.

If the live config already succeeds on more than 95% of the set, **The same
success for less** is chosen for you, with a note saying so. You can change it.

</Step>
<Step>

Under **Its agent**, choose the harness, and the model and effort if you want
other than the harness's own defaults. This is the agent that proposes
candidates, not the station's own.

</Step>
<Step>

Read the estimate under the fields. It gives how many tasks are searched and
held out, how many copies of each run, the most runs the search may start,
what each replay may spend, and roughly how long it takes, from how long the
set's runs took. If the estimate says the ceiling is too low to give each
replay run at least 0.01, raise the ceiling or lower the iterations,
candidates or repeats.

</Step>
<Step>

Read any warning under the estimate:

- If nobody has measured how much the set's success moves by chance,
  [check the set](/docs/improvement/replay-past-tasks-against-a-station-change#check-the-sets-health)
  first, or set **Repeats** above 1.
- If the set's success moves more than the line counts as real, select the
  button under the warning, as in **Replay each run 3 times**, to set
  **Repeats** to what it suggests, and raise the ceiling if the estimate asks.
  If the warning says even 5 copies won't bring it under, read small gains
  with care, or raise the line's
  [`min_gain`](/docs/reference/terraform/line#replay-check-fields).
- If the live config already succeeds on almost all of the set, aim for the
  same success for less, or add runs of tasks the live config fails.
- If the judge gave the same verdict too rarely when it judged the same change
  twice, make its rubric more specific before you search.
- If the check passed once and failed once on the same change, fix the flaky
  tests, or take those tasks' runs out of the set. The set's page lists them.
- If a stronger model did not do clearly better on the set, look at the tasks
  it did worse on, listed on the set's page: their rubric or checks may be
  wrong.

The search starts with a warning all the same, but a gain it finds may be
chance.

</Step>
<Step>

Select **Start search**. The search's page opens.

</Step>
</Steps>

While the search runs, its replay set can't change: runs can't be added or
taken out, and the set can't be deleted. A station has one search at a time.

## Follow the search

The search's page shows its state beside its name:

1. **Replaying the live config**: the station as it is now is replayed on
   every task of the set. The agent waits for this to finish.
2. **Searching**: the agent runs once per iteration and proposes candidates.
   Each candidate is replayed on the searched tasks, and the next iteration
   starts once those replays have ended, so the agent sees how they did. If
   two iterations in a row find nothing better, the next one may look into
   why instead. See [If the search stalls](#if-the-search-stalls).
3. **Checking on held-out tasks**: once it stops searching, the best
   candidates are replayed on the tasks the agent never saw.
4. **Finished**, or **Stopped**, with the reason under the name, such as **It
   ran every iteration it was given**.

**Progress** counts the iterations run and candidates proposed, and **Spent**
what the search has spent against its ceiling. Under **Candidates**, each
iteration lists what its agent proposed, with the agent's hypothesis, what the
candidate changes from the live config, and how it scored. Select **Its
agent's run** to see what the agent read and did.

To stop a search, select **Stop**, then **Stop search**. The agent's run
stops and nothing more is replayed. Candidates whose replays finished keep
their scores and can still be picked.

## If the search stalls

A search stalls when two iterations in a row propose nothing better than the
best config before them. If it has at least 2 iterations and enough of its
ceiling left, the next iteration proposes nothing: its agent looks into each
searched task the best config so far still fails, and records what caused
the failure. When a change to the config could fix some of them, the search
goes on and its next agent is told what was found. Otherwise the search ends.
See [Stalls](/docs/reference/app/searches#stalls).

If you started the search, you get an inbox notice when it ends this way, and
when it goes on but found something to fix outside the config.

<Steps>
<Step>

Open **Inbox**. A notice about the search reads, for example, **The search
for a better Build config stalled: nothing left the config can fix**. Open
it, and it moves under **Resolved**. Under **Details**, it says what happened, then names each task with what
to fix. Select **Open the search**.

</Step>
<Step>

On the search's page, under **Why it stalled, looked into in iteration
`<n>`**, the tasks are grouped by cause. Each shows what in the runs showed
the cause and what the agent suggests. Select **Open the failed replay run**
to check it yourself.

</Step>
<Step>

Fix what each group asks:

- **The task itself**: take the task's run out of the replay set, or reword
  the task. See [Pick the tasks to replay](/docs/improvement/replay-past-tasks-against-a-station-change#pick-the-tasks-to-replay).
- **The judge**: fix the judge's rubric. See
  [Set a station's judge and alerts](/docs/improvement/set-a-stations-judge-and-alerts).
- **The check**: fix the broken or flaky test the station's check runs.
- **Around the work**: replay the task again. If it keeps failing, fix what
  the run needs, such as a tool or a service.
- **The station's config**: nothing. The search keeps trying configs for
  these.
- **No cause recorded**: open the failed replay run and decide for yourself.

</Step>
<Step>

If the search ended, start a new one once the fixes are in.

</Step>
</Steps>

If the notice reads **stalled, with no budget left to look into why**, the
search had fewer than 2 iterations or too little of its ceiling left. Start
a new search with more iterations or a higher ceiling.

## Read the results

Each score comes with the range it likely falls in, as in `72% (50–89%)`, and
each candidate with its gain over the live config on the searched tasks and,
once replayed there, on the held-out tasks: the gain in points, its range, and
**Better**, **Worse** or **Within noise**. A gain reads **Better** only when
its whole range is above no change and it reaches the gain the line counts as
real, which the header gives under **Live config**. See
[Every result comes with a range](/docs/improvement/why-changes-are-replayed-on-past-tasks#every-result-comes-with-a-range).

**Success against cost** plots each candidate's success on the searched tasks
against what it spent a run. The candidates joined by the line are the
frontier: for each, no other candidate succeeded as often for less. The live
config is always on it. Select **Show table** to read the same as a table.

**Best**, in the header, is the candidate that succeeded most: by its score on
the held-out tasks once it has one, else by its score on the searched tasks.
It reads **Live config** when nothing beat the station as it is.

If the search aims for the same success for less, the frontier holds only
candidates whose gain over the live config reads **Better** or **Within
noise**, only those cheaper than the live config are replayed on the held-out
tasks, and the header reads **Cheapest** in place of **Best**: the cheapest of
the live config and the candidates whose gain reads **Better** or **Within
noise**.

If the station has a judge, each gain is followed by the candidate's wins,
losses and ties against the live config, once its replay has finished, as in
`Side by side with the search's starting config: 4 wins, 1 loss, 2 ties`: on
each task, whether the judge, not knowing
which change was which, found the candidate's change or the live config's
better. They do not change the scores, the frontier or **Best**. See
[Side by side with the live config](/docs/reference/app/searches#side-by-side-with-the-live-config).

Give the held-out score the most weight. A held-out gain that reads **Better**
is the strongest sign a candidate helps. A candidate whose gain reads
**Better** on the searched tasks but not on the held-out ones is marked **Only
on seen tasks**: it has likely fitted the tasks the agent saw, and its gain may
not carry over to new work. Above the chart, a note counts how many frontier
candidates are marked. When fewer than 5 held-out tasks were scored for both
the candidate and the live config, its held-out gain reads **Within noise**
whatever it is, so such a candidate reads **Too few held-out tasks to tell**
instead of being marked. **Best** in the header, and the search's row on the
Station page, show either for the best candidate. A candidate not on the frontier when the search stopped
reads **Not held out**. Select **Its replay** or **Its held-out replay** beside a
candidate to see its result task by task. See
[Replays](/docs/reference/app/replays#replay-page).

To set the search's candidates beside the station's other replayed candidates
and the live config, open the team's **Insights** page at **Candidates**. See
[Compare the station's candidates](/docs/improvement/replay-past-tasks-against-a-station-change#compare-the-stations-candidates).
There, **Pick on the search** beside a candidate opens this page at it.

## Pick a candidate

<Steps>
<Step>

Beside the candidate, select **Pick**. You can pick any candidate whose replay
on the searched tasks has finished, while the search runs or after, and more
than one.

If the candidate is marked **Only on seen tasks**, a warning above **Pick**
says its gain may not carry over to new work. You can still pick it.

</Step>
<Step>

The candidate reads **Opening a pull request…**, then **Pull request opened**.
Select it to open the pull request on GitHub.

</Step>
<Step>

Review the pull request. Its description has the agent's hypothesis, the
candidate's scores beside the live config's with their ranges, whether each
gain is more than noise, and its side-by-side wins, losses and ties when it
has any. For a candidate marked **Only on seen tasks**,
a paragraph under the opening one warns that its gain showed only on the
searched tasks and gives both gains. It says instead when too few held-out
tasks were scored to tell, or when the held-out replays had not finished as
the pull request opened. The plan of the change runs in
your Terraform workflow as for any other pull request; if the line
[checks pull requests](/docs/configuration/check-terraform-pull-requests-for-station-regressions),
that check runs too.

</Step>
<Step>

Merge it and apply it as you would any change to the line.

</Step>
</Steps>

Picking a candidate again opens no second pull request; it shows the same one.

## If no pull request opens

The candidate reads **No pull request opened**, the reason, and what
Spotlight found. Fix the cause, then select **Retry**.

| Reason | What to do |
| --- | --- |
| The line does not say which repository holds its Terraform | Give the line a `source` block. See [Name the file that holds the line](#name-the-file-that-holds-the-line). |
| Spotlight's GitHub App cannot reach the line's repository | Install the GitHub App on that repository, or correct `source.repository`. |
| The line's Terraform file is not in its repository | Correct `source.path`. Spotlight reads the file on the repository's default branch. |
| The station's block was not found in the file, or was found more than once | Spotlight looks for exactly one `spotlight_line` resource whose `key` is the line's, and in it exactly one `station` block whose `key` is the station's, both written as plain text. Write them that way, or make the change by hand. |
| An attribute it would change is computed in Terraform, so it must be set by hand | The attribute is built from a variable, a local or another expression. The reason names the attribute, the expression and the value to set: make the change by hand. |
| The file changed since the search began | The station's block in the repository no longer matches the config the search started from, such as after another change was applied. Make the change by hand, or start a new search. |
| The branch for the pull request is taken already | The branch `spotlight/search-<id>-<name>` holds commits Spotlight did not write. Delete the branch, then retry. |

[Config pull request reasons](/docs/reference/app/searches#config-pull-request-reasons)
lists every reason.
