A work station gets better when its config gets better: its prompt, its model,
its skills, its tools. Spotlight looks for those changes itself. It keeps a set
of the station's past runs, has an agent propose changed configs, replays each
one on those runs, and opens a pull request for a config that did better. A
person reviews and merges the pull request. Nothing changes at the station
before that.

This page explains each part and the reasons for it. The labels and fields are
in [Searches](/docs/reference/app/searches),
[Replays](/docs/reference/app/replays) and the line's
[`search` block](/docs/reference/terraform/line#search-fields).

## The replay set Spotlight keeps

A [replay](/docs/improvement/why-changes-are-replayed-on-past-tasks) starts a
past run again under another config and scores what it does. To compare two
configs, both must be replayed on the same runs. These runs are the station's
replay set.

Spotlight keeps exactly one replay set for each work station. It creates the
set when a run of the station ends for the first time, and then refreshes it
from the station's newer runs:

- every 7 days when the set is full, at 30 runs,
- every day when it is not full,
- and just before a replay or a search of the set starts.

A refresh takes out runs that ended more than 90 days ago, and adds the newest
run of each task that has no run in the set. When it can choose, it adds runs
whose outcome the set has few of, so that the set does not hold only runs that
went well, or only runs that failed. The set has one run of each task. See
[How Spotlight keeps the set](/docs/reference/app/replays#how-spotlight-keeps-the-set)
for the exact rules.

A refresh never runs while the set is in use: while a replay of it runs, while
a search of it runs, or while a [replay check](/docs/configuration/check-terraform-pull-requests-for-station-regressions)
waits for its baseline. A set that changed while a search used it would make
the search's scores meaningless, because the candidates would not all have
been replayed on the same tasks.

In the docs' view, a set that people choose by hand goes stale: the tasks of
last quarter stay in it, and the tasks of this week never come in. A set that
follows the station's own runs measures a config against the work the station
does now. The same set is what the line's
[`spotlight replay check`](/docs/reference/cli/replay-command#spotlight-replay-check)
replays a planned change on, so a search and a check measure against the same
tasks. A check of a station whose set has no runs yet fails with an error, and
does not pass.

A person can take a run out of the set, for example a task that is unclear or
that no config can do. Spotlight then never adds a run of that task again,
because otherwise the next refresh would add it back. Nobody creates, renames
or deletes a set, or adds runs to it by hand.

## When a search starts

A search is a series of iterations. In each one, an agent reads how the
station's past runs went and proposes changed configs, called candidates, and
Spotlight replays each candidate on the set. See
[Why a search holds tasks out](/docs/improvement/why-a-search-holds-tasks-out)
for how a search is built.

Spotlight starts a search of a work station for two reasons:

- The `period` of the line's search policy ran out since the station's last
  search started. By default, this is 7 days.
- One of the station's [alerts](/docs/improvement/set-a-stations-judge-and-alerts#set-alerts)
  fired, and the policy has `on_alert` set. An alert does not wait for the
  period, but it waits for the `cooldown`, by default 3 days after the last
  search started.

The policy is the [`search` block](/docs/reference/terraform/line#search-fields)
of the line, and a station's own `search` block changes it for that station.
Automatic improvement is on by default: a line without a `search` block
searches each of its work stations with the defaults. The block also sets what
one search may spend, its `ceiling`, and what all the line's searches may spend
in one calendar month, its `monthly_ceiling`. With `enabled = false`,
Spotlight does not search the line or the station.

A station has one search at a time. Nobody starts a search by hand: the
policy decides when a search is due, so the spend stays inside the ceilings
that the team wrote in Terraform.

## When Spotlight skips a search

A due search does not always start. Spotlight first checks whether the search
can give a result that people can trust and act on. When it cannot, Spotlight
skips the search, records the reason, and checks again later. The station's
[improvement status](#the-improvement-status) and the Searches card of its
replay set show the last reason. The reasons are of four kinds:

- No way to score a config: the station has no judge and no check, so a
  replay cannot say whether a candidate did better.
- A set that cannot tell configs apart: the set has too few tasks (a search
  needs at least 5), its success moves too much between repeats of the same
  runs, its judge does not give the same verdict twice, its check flips on the
  same change, or the live config does no better when it is given the answer,
  so a better config has no room to show.
- No fresh tasks to hold out: a search keeps about 30% of the set's tasks
  away from its agent, to check its result on. A task that an earlier search of
  the station searched on is never held out again, because its runs may have
  shaped the candidates. When too few of the set's tasks are fresh, the search
  waits for new runs.
- Limits that the team set: the search policy is off, the cooldown has not
  passed, a config pull request of the station is still open, the line's
  searches spent their monthly ceiling, the search ceiling is too low to replay
  each task once per candidate, or no harness can run the search agent.

Some reasons also send the team an inbox notice with advice, because the team
can fix them: no judge and no check, a set that is too small, no room to
improve, a search ceiling that is too low, and no harness for the search
agent. [Skip reasons](/docs/reference/app/searches#skip-reasons) lists
every reason, its text, and when Spotlight checks again.

A skip costs nothing. A search on a set that cannot tell configs apart costs
money and can report a gain that is only chance. In the docs' view, a skip that
names its reason is more useful than such a result.

## Which candidate becomes a pull request

When a search finishes, Spotlight ranks its candidates by what the search aims
for, more success or the same success for less, and takes the first candidate
that meets all of these rules:

- On the held-out tasks, it did better than the live config, by at least the
  line's [`min_gain`](/docs/reference/terraform/line#replay-check-fields) and
  by more than noise. A search that aims for the same success for less asks
  instead that the candidate did as well as the live config, within noise, and
  cost less per run.
- It did not regress on more tasks than the line's regression limit,
  `max_regressions`.
- It has no overfit mark: its gain did not show only on the tasks the agent
  saw.
- No person closed a config pull request for the same config on GitHub while
  the station's live config was the same as it is now.

The held-out tasks decide, because the agent never saw them. A gain on the
searched tasks alone can come from a config that fits those tasks and nothing
else. See [Overfit](/docs/reference/app/searches#overfit).

When a candidate meets the rules, Spotlight edits the station's block in the
line's Terraform, commits it to a branch of its own, and opens a config pull
request. The repository and file come from the line's
[`source`](/docs/reference/terraform/line#source-fields) block. When no
candidate meets the rules, the search ends with no pull request, and the reason
is recorded. See [Spotlight's pick](/docs/reference/app/searches#spotlights-pick).

Either way, each finished search sends the team one inbox notice. It links to
the pull request, or says why there is none or why the pull request could not
be opened. Every person on the team sees it. See
[Answer the inbox](/docs/inbox/answer-the-inbox).

A station has at most one open config pull request. While one is open,
Spotlight starts no new search of the station, and a search that finishes
then opens no second pull request. A new search would compare its candidates
with a live config that is about to change.

## What happens to the pull request

Spotlight follows each config pull request after it opens, until it is merged
or closed:

- A person merges it. Spotlight records that the station improved. The status
  of the station then reads improved until the next search starts.
- The station's live config changes, for example because someone applied
  another change to the line. When the live config matches neither the config
  the pull request started from nor the config it proposes, the pull request
  is stale: its scores no longer describe a change to the station as it is.
  Spotlight closes it on GitHub, with the comment `Spotlight closed this pull
  request. The station's live config changed after this pull request opened.`
  A merged pull request is never closed as stale.
- A person closes it on GitHub. Spotlight takes this as a no to that config.
  The station's cooldown starts again from the close, and Spotlight does not
  propose the same config again while the station's live config stays the
  same. When the person reopens the pull request, the config can be proposed
  again.

When GitHub refuses to close a stale pull request, Spotlight tries again a few
times. If the error does not go away, Spotlight records the pull request as
closed, with the reason it could not close it. Spotlight hears about merges and closes from GitHub's
webhooks, and also reads the state of each open pull request from GitHub every
6 hours, in case a webhook did not arrive.

A merged pull request and a pull request closed as stale send no inbox notice.
In the docs' view, the person who merged it, or who changed the line, knows
already. See
[Config pull request states](/docs/reference/app/searches#config-pull-request-states).

## The improvement status

A work station's page opens with "What needs attention". Beside that title,
one short line says what Spotlight does to improve the station now, with a
link and more detail on hover:

- Searching: a search of the station runs.
- Choosing a config, or opening a pull request: a search finished, and
  Spotlight picks its candidate or opens the pull request for it.
- Pull request open: a config pull request waits for review.
- Improved: a merged config pull request improved the station since the last
  search started.
- Waiting: nothing is wrong, and Spotlight checks again later. The cooldown
  has not passed, a pull request is open, the set has too few tasks or too few
  fresh tasks to hold out, the line spent its monthly ceiling, or the live
  config has no room to improve on the set. These go away by themselves, as
  time passes and the station has new runs.
- Not improving: a person must act. The search agent has no harness, the
  station has no judge and no check, the search ceiling is too low, the set
  is noisy, the judge is unstable, the checks are flaky, or the last config
  pull request could not be opened.
- Off: the search policy of the station is off.
- Not started: the station's replay set has no runs yet.

The split between waiting and not improving tells a person when to act. In
the docs' view, a status that asks for action on something that fixes itself
teaches people to ignore it. See
[Improvement status](/docs/reference/app/searches#improvement-status) for
the exact texts.

## What a person does

One step needs a person: merging the config pull request. The pull request
describes the agent's hypothesis and the candidate's scores beside the live
config's, with their ranges. The change goes through the same review and the
same `terraform apply` as any other change to the line. If the line
[checks its pull requests](/docs/configuration/check-terraform-pull-requests-for-station-regressions),
that check replays the change again. The station changes only when the pull
request is merged and applied. [Why configuration lives in Terraform](/docs/configuration/why-configuration-lives-in-terraform)
gives the reasons the repository stays the record.

A person can also:

- Stop a running search, on its page. A stopped search gets no pull request.
- Close a config pull request on GitHub, to say no to its config.
- Take a run out of the replay set, on the set's page. Its task never comes
  back.
- Change the search policy in the line's Terraform: turn it off, change its
  ceilings, period or cooldown, or set the search agent, iterations, repeats
  or aim for a station.
- Fix what a search found outside the config, such as an unclear task, a judge
  that scores the wrong thing, or a flaky test. A search that stalls looks into
  why its tasks fail, and the search's inbox notice names what it found. See
  [Stalls](/docs/reference/app/searches#stalls).

Nobody picks a candidate by hand. In the docs' view, a fixed rule for which
candidate goes forward keeps each pull request comparable with the next, and
the review of the pull request remains the place where a person decides.
