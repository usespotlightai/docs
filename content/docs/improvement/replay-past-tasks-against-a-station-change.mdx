title: Replay past tasks against a change to a station
description: Run some of a work station's past tasks again under a changed config, compare the results with the station as it is now, and then make the change in Terraform.
---

Use this to try a change to a work station, such as a new prompt or another
model, on tasks the station has already worked, before you apply it. A replay
starts each chosen task again from where its run started, under the changed
config, and scores what it does. Nothing a replay does reaches the task,
GitHub or anyone's inbox. You need:

- To be on the team, or an owner or admin of the workspace.
- Runs at the station that can still be replayed. Spotlight keeps where a run
  started for 30 days. See [What a replay can start from](/docs/improvement/why-changes-are-replayed-on-past-tasks#what-a-replay-can-start-from).
- A host serving the workspace with the station's harness. Replays run on the
  workspace's runners, after any task run that is waiting. See
  [Install a host](/docs/hosts/run-a-host).
- A [workspace token](/docs/administration/issue-a-workspace-token) with the
  `plan` scope, and the `spotlight` binary to propose the change. You don't
  need a host on your own computer; see
  [Install](/docs/reference/cli/replay-command#install).
- The team's configuration in Terraform, to apply the change afterwards. See
  [Manage Spotlight with Terraform](/docs/configuration/manage-spotlight-with-terraform).

## Check the tasks to replay

Spotlight keeps one replay set for each work station: up to 30 of its past
runs, one run of each task, refreshed from the station's newer runs. A replay
replays every run in the set. See
[The replay set Spotlight keeps](/docs/improvement/how-spotlight-improves-a-station#the-replay-set-spotlight-keeps).

<Steps>
<Step>

On the line's board, select the station's name to open the Station page. At
the right of **What needs attention**, hover over the ⓘ beside the improvement
status, and select **Replay set**. If the status itself links to the set, as
**Waiting for next check** does, select the status. The set's page opens.

If the status reads **No runs yet**, the station's replay set has no runs.
Wait for a run of the station to end.

</Step>
<Step>

Under **Runs**, read the runs the set contains. A run that cannot be replayed
has a red warning sign. Hover over it for the reason, such as **Run recorded
no starting point**. See
[Why a run cannot be replayed](/docs/reference/app/replays#why-a-run-cannot-be-replayed).

</Step>
<Step>

If a run's task should not count, such as a task that is unclear or that no
config can do, hover over its row, select the X, then **Take it out**.
Spotlight never adds a run of that task to the set again, and you cannot undo
this. While a search of the set runs, or a replay of it is in progress, no run
can be taken out.

</Step>
</Steps>

Above the set's runs, a bar shows how they turned out. Hover over the ⓘ
beside **Runs** for where their tasks came from and when they ended. If a
warning sign shows at the right of the panel's title, most of the set's runs
turned out one way. Spotlight adds runs that turned out other ways when the
station has them. See
[What a set is made of](/docs/reference/app/replays#what-a-set-is-made-of).

## Propose the change

A candidate is the station's config as you want to try it. You write it as
JSON, in the shape of one entry of a line's `stations`, and propose it with
`spotlight replay propose`. Spotlight checks it as it would check the line with
the station replaced, and never applies it.

<Steps>
<Step>

Give the command your Spotlight address and token:

```bash
export SPOTLIGHT_URL=https://app.usespotlight.ai
export SPOTLIGHT_API_TOKEN=<workspace token>
```

On a [self-hosted Spotlight](/docs/reference/glossary#spotlight-address), use
your deployment's address.

</Step>
<Step>

Save the station's block as it is now. A workspace token sees one workspace, so
its id is the only one listed:

```bash
WORKSPACE=$(curl -s -H "Authorization: Bearer $SPOTLIGHT_API_TOKEN" \
  "$SPOTLIGHT_URL/api/resources/workspaces" | jq -r '.items[0].id')

curl -s -H "Authorization: Bearer $SPOTLIGHT_API_TOKEN" \
  "$SPOTLIGHT_URL/api/resources/workspaces/$WORKSPACE/lines/import?address=core/delivery" \
  | jq '.definition.stations[] | select(.key == "implementation")' > implementation.json
```

Replace `core/delivery` with the team and line keys, and `implementation` with
the station's key.

</Step>
<Step>

Edit `implementation.json` to make the change, such as a new `prompt`, `model`
or `effort`. Keep `key` as it is. [Station fields](/docs/reference/terraform/line#station-fields)
lists every field.

</Step>
<Step>

Propose it, with a name that tells it from the station's other candidates:

```bash
spotlight replay propose --station core/delivery/implementation \
  --name "Higher effort" implementation.json
```

The command prints the candidate's address and what it changes from the
station's live config, the config the station runs with now. The candidate is
then one of the choices under **Replay under** when you start a replay.

</Step>
</Steps>

If Spotlight rejects the block, each message names its field under `station`,
as in `station.effort`. The command rejects a `.tf` or `.hcl` file: give the
block as JSON. See
[`spotlight replay propose`](/docs/reference/cli/replay-command#spotlight-replay-propose).

## Start a replay

<Tabs items={['Web app', 'Command line']}>
<Tab value="Web app">

<Steps>
<Step>

Open the station's replay set, as in
[Check the tasks to replay](#check-the-tasks-to-replay). On the set's page, under **Replays**, select **Start a
replay**.

If the button is greyed out, hover over it for the reason, such as an empty
set.

</Step>
<Step>

Under **Replay under**, choose the candidate.

</Step>
<Step>

Under **Repeats**, enter how many times to replay each run, from 1 to 5. More
repeats narrow the range around the result, and cost as many more runs. See
[Read the set's health](#read-the-sets-health).

</Step>
<Step>

Under **Ceiling**, enter the most the replay may spend and its currency, as
in `5.00` and `USD`. The ceiling covers the replay's runs, every repeat of them,
the change stacks that Spotlight generates for their changes, and the judging
of these changes.

</Step>
<Step>

Select **Start replay**. The replay's page opens.

</Step>
</Steps>

</Tab>
<Tab value="Command line">

```bash
spotlight replay start --station core/delivery/implementation \
  --candidate "Higher effort" --ceiling 5
```

The ceiling is in `USD` unless you add `--currency`. To replay each run more
than once, add `--repeats` and a number up to 5. The command prints the
replay's id and the command to follow it.

</Tab>
</Tabs>

A replay you start is compared with the set's baseline: the station's live
config replayed on the same runs. Before the replay starts, Spotlight
refreshes the set, unless a replay, a search or a check uses it. If the set
has no baseline covering all its runs, because it was never replayed or a
refresh added runs since:

- Under **Live config**, the replay becomes the baseline.
- Under a proposed candidate, a baseline starts beside it, with a ceiling of its
  own the same as yours, so the two may spend up to twice the ceiling. At 1
  or 2 repeats, they may spend more when that baseline is also a calibration,
  as below.

If the set has a baseline covering its runs, with at least as many repeats of
each as you asked for, a **Live config** replay runs beside it, and no new
baseline starts. Otherwise a new baseline starts as above, with your number of
repeats.

The first baseline of the live config as it is now is also a calibration of the set, when
the set contains 5 runs or more. At fewer than 3 repeats, it replays each run 3
times, and its ceiling can be larger than yours. Once it finishes, each change is
judged and checked a second time, within its ceiling. A set of fewer than 5
runs is never calibrated. Before you set the ceiling, see
[Calibration](/docs/reference/app/replays#calibration) for that
baseline's ceiling, and
[Replay set page](/docs/reference/app/replays#replay-set-page) for what the
replay and its baseline may spend together and which notes the dialog shows.

At most 2 of a team's replay runs run at once. See
[Limits and timeouts](/docs/reference/limits-and-timeouts#replays).

## Follow the replay

The replay's page shows its success, its gain over the replay it is compared
with, and what it has spent of its ceiling. From the command line:

```bash
spotlight replay watch --team core <replay id>
```

It prints progress every 15 seconds until the replay and the replay it is
compared with have ended, then the result for each task. It exits `2` if the candidate regressed on
any task, so a CI job that runs it fails on a regression. See
[`spotlight replay watch`](/docs/reference/cli/replay-command#spotlight-replay-watch).

To stop a replay, select **Stop**, then **Stop replay**, on its page, or run
`spotlight replay stop --team core <replay id>`. Nothing more of it starts, and
its running runs are stopped. A replay that spends its ceiling ends as **Over
budget**: nothing more starts, and runs already running finish.

## Read the result

**Success** gives the replay's success rate; hover over its ⓘ for the range it
likely falls in. **Gain** gives its gain in points over the replay it is
compared with, as in `+12 pts`, with a significance of **Better**, **Worse** or
**Within noise** and that replay's success on the tasks both scored, as in
`Better · baseline 50%`. Its ⓘ gives the gain's range. See
[Gains](/docs/reference/app/replays#gains) for when each significance shows.

Act on **Better** or **Worse**. If a result you expected to matter reads
**Within noise**, replay with more repeats. To change the smallest gain that counts, see
[Set how large a gain must be](#set-how-large-a-gain-must-be).

Under **Tasks**, the replay's page lists each task, regressions first. A
regressed task has a red warning sign beside its title. See
[Regressions](/docs/reference/app/replays#regressions) for when a task
regresses. Hover over a result for its reasons, such as **Checks failed**.
With more than one repeat, a task shows how many repeats succeeded; hover over it
for each repeat's result.

Select a task to open its details beside the list: each run's result, why it
succeeded, failed or went unscored, its checks and what it changed. Select
**Open the run** to open that replay run, or **Original run** for the run it
replayed. See [Results](/docs/reference/app/replays#results) for every result,
**Unscored** included, and every reason.

If the station has a judge, a **Side by side** tile shows its wins, then its
losses and ties, once the replay has finished and any task was compared.
Under **Tasks**, the **Closer** column says which change the judge found
closer to the accepted change: **This one**, the replay it is compared with,
as in **The baseline**, or **Neither**.
Select the task to read the judge's reasons in its details. Read the wins and
losses beside the success rate. See
[Side by side](/docs/reference/app/replays#side-by-side) for how the judge
compares the changes.

If the candidate did worse, propose another candidate and replay the set.
To see what a replay with a gain is compared with, hover over its **Gain** on
the set's page. Once that replay's success is known, the hover names it, as in
`Baseline: 50%` or `Earlier baseline: 50%`. A replay without a gain reads `–`.

## Read the set's health

Read whether a set can tell a better config from a worse one before you read
small gains on it. Spotlight
[skips a search](/docs/improvement/how-spotlight-improves-a-station#when-spotlight-skips-a-search)
of a set that fails one of these checks. There is nothing to start: the set's first baseline checks it, then
Spotlight replays the live config with each run's answer.

On the set's page, read the rows under **Health**. Hover over the ⓘ beside a
check for its advice. A check marked with a warning sign found a problem:

- **Noise** more than the gain the line counts as real: replay candidates
  with more repeats, set more `repeats` in the station's
  [`search` block](/docs/reference/terraform/line#station-search-fields), or
  [raise `min_gain`](#set-how-large-a-gain-must-be).
- **Room to improve** reads **Little** or **Almost none**: give the station
  harder tasks, or set the station's search `objective` to `cost`, for the
  same success for less. See
  [Read the room to improve](#read-the-room-to-improve).
- **Judge agreeing with itself** below 80%: make the judge's rubric more
  specific. See [Set a station's judge and alerts](/docs/improvement/set-a-stations-judge-and-alerts).
- **Flaky checks** lists tasks whose check flipped: fix the flaky tests, or
  take those tasks' runs out of the set. Their tasks never come back.

The checks belong to the station's config as it is now. Once an applied
change gives the station a new config fingerprint, they read **Not
measured** or **Not checked** until the first baseline of the new config
calibrates the set. A replay of the live config with 2 or more repeats, started
any other way, measures the noise too once it finishes.
See [Health](/docs/reference/app/replays#health) for every check.

### Read the room to improve

There is nothing to start. Once a replay of the live config over the whole set
finishes, such as the first baseline, Spotlight replays the live config once more on
the set's accepted and sent-back runs, handed each run's answer: the change
people accepted, or what a person said when they sent it back. It does this
once for each config the station has. The replay is named **With the answer**
and its date, and shows under **Replays** like any other. It has a ceiling of
its own, the same as the live replay's.

While it runs, **Room to improve** reads **Measuring with the answer**. Once
it finishes:

- If it reads **Little**, give the station harder tasks, or set the
  station's search `objective` to `cost`.
- If it reads **Too few runs to tell**, wait until people accept or send back
  more of the station's runs. Spotlight adds them when it refreshes the set.
- If it reads **Couldn't measure with the answer** because the replay with the
  answer was stopped or ran over its ceiling, replay the live config over the
  whole set again.

Hover over the ⓘ for the live config's success and the success with the
answer. See [Room to improve](/docs/reference/app/replays#room-to-improve) for
what each check means.

See [Why a set is replayed with the answer](/docs/improvement/why-changes-are-replayed-on-past-tasks#why-a-set-is-replayed-with-the-answer).

## Set how large a gain must be

If a gain of a few points is not worth a change to your team, raise the
smallest gain the line's replays, searches and checks count as real. Give the line's
`replay_check` block a `min_gain`, as a share from above 0 to 1, and apply it:

```hcl
replay_check {
  max_regressions = 0
  ceiling         = 10
  currency        = "USD"
  min_gain        = 0.1
}
```

Without it, a gain counts as real from 0.05, which the app shows as `+5 pts`.
The same block is what lets `spotlight replay check` check the line's pull
requests; see
[Check Terraform pull requests for station regressions](/docs/configuration/check-terraform-pull-requests-for-station-regressions).

## Compare the station's candidates

Use the team's Insights page to set every candidate replayed at the station,
yours and those of any search, beside the live config.

<Steps>
<Step>

In the sidebar, open the team and select **Insights**, then **Stations**.
Choose a period that covers when the replays started.

</Step>
<Step>

Under **Replayed candidates**, find the station. Its row starts expanded,
and selecting it collapses it.
Each candidate's row sets its **Replay success** beside the live config's,
**Against live** gives its gain over the live config in points, and **Cost per
run** and **Live cost** give what each spent per run. Select **Changes** on a
row to open its replay, its search or its pull request.

</Step>
<Step>

To plot success against cost, choose **Chart**. Each station's replay set has
a chart of its candidates, with replay success up the side and cost per run along the
bottom. The diamonds are the live config replayed: one on each search's
tasks, beside that search's candidates, and one on the whole set, beside the
proposed candidates. A candidate above its diamond and no further right did
better for no more cost.

</Step>
<Step>

To see the candidates beside the agent configs that the station's live runs used, go to
**Harness, model, effort and profile** under **Config changes** and choose the
station under **Station**. The replayed candidates are drawn hollow. Their
height is replay success on past tasks, not how live runs turned out. They are
not drawn while **Sent back** is charted.

</Step>
</Steps>

See [Candidates](/docs/reference/app/insights#candidates) for every figure in
the section.

## Make the change

A replay never changes the station. To keep a change that did better:

<Steps>
<Step>

Make the same change in the station's block of the line's `spotlight_line`
resource, or in its prompt file. See
[Change a line's stations](/docs/lines/change-a-lines-stations).

</Step>
<Step>

Run `terraform apply`.

</Step>
</Steps>

Runs with the new config start a new group under **Runs by config** on the
station's view on Insights. See
[Check whether it helped](/docs/improvement/improve-a-station-from-its-runs#check-whether-it-helped).

To have every pull request that changes the station replayed on its replay
set before it merges, see
[Check Terraform pull requests for station regressions](/docs/configuration/check-terraform-pull-requests-for-station-regressions).
